# Conclave design log

This file records why Conclave is built the way it is: each decision, the options I weighed, how a feature is meant to work, and where it can fail. Newest entries go at the bottom of each section. Plain language, short.

## 0. The problem

You use Claude Code, Codex, OpenCode (with the Z.ai coding plan), Antigravity, Gemini and chat apps. Each one has its own harness, memory, subagent style, remote access story and usage limits. Getting a second opinion means opening another tool and re-explaining the context. Remote control only works for some of them, and there is no phone app for most. Memory does not carry between them.

Conclave is one hub that fixes this:

- one place for every chat, with any model, and other models joining the same chat (second opinion, jury, debate, switch)
- its own harness built from Claude Code's public design, so any model gets good tools
- the vendor harnesses (Claude Code, Codex, Gemini CLI, OpenCode) driven over ACP when you want their tuned loops
- persistent memory shared by everything, with a Basic Memory adapter
- agents, routines, tasks, devices, usage limits and auto-resume after limits reset
- clients: web, desktop, native Android, TUI

## 1. Name

**Conclave**: a private meeting where minds deliberate before a decision. It matches the core idea (several models in one room, jury mode) and the personal, self-hosted nature. CLI command: `conclave`.

Rejected: Quorum (taken by a well known blockchain), Hydra (THC Hydra, confusing for a security person), Fleet (the stand-in name from the earlier chat, too generic).

## 2. Architecture

```
 Web / Desktop (Tauri) / Android (Kotlin) / TUI (Ink)
                         |  HTTPS + WebSocket, bearer token
                     Hub (conclave serve) on the server
   engine: agent loop, tools, memory, routines, scheduler, usage, gateway
                         |  outbound WebSocket from each device
          Daemons (conclave daemon) on PC, Mac, other boxes
              files, shells, browser, ACP harnesses run here
```

Decisions:

- **One brain, many hands.** The agent loop always runs on the hub. Tools never touch `node:fs` or `child_process` directly. They call a `Machine` interface. The hub's own disk is the "local" machine; a paired PC is a remote machine reached over the daemon's WebSocket. Picking a device for a session is just picking which Machine tools use. Why: one database, one memory, one scheduler, and the phone talks to one place. Daemons connect outbound, so no inbound ports on your PC.
- **TypeScript on Bun everywhere except Android.** Bun gives built-in SQLite (with FTS5), a fast HTTP and WebSocket server, TypeScript without a build step, and `bun build --compile` for one binary per OS. One language for hub, daemon, TUI and web means shared types. The one exception on the computers: the device daemon the desktop app carries is also built in Rust (`packages/daemon-rs`, docs/design/DAEMON-RUST.md), because it runs all the time on every machine; it serves the same protocol, and a conformance suite holds it to the TypeScript daemon.
- **SQLite, not Postgres.** Personal scale. One file, WAL mode, easy backup. FTS5 gives full text search for chats and memory for free.
- **Anthropic-style content blocks internally.** They are the most expressive (thinking with signatures, tool_use, tool_result, images, documents). Providers translate at the edge.

## 3. Own harness vs vendor harnesses

The earlier chat argued both sides. My call: do both, behind one session model.

- **Native harness (default for any API model).** Rebuilt from Claude Code's public design: the loop, Read/Write/Edit/Bash/Glob/Grep/WebFetch/WebSearch/Task/TodoWrite/AskUserQuestion/Skill, permission rules, hooks, skills, subagents, compaction and prompt caching. This is what lets GLM, GPT, Gemini or a local model work with good tools and lets models join each other's chats.
- **ACP harnesses.** Claude Code, Codex, Gemini CLI and OpenCode run as engines over the Agent Client Protocol. Their permission prompts become Conclave approvals (so your phone can answer them). A session in bypass mode passes bypass on: a harness that offers its own bypass mode (Claude Code's bypassPermissions) is switched into it for the turn, so it does not ask at all, and a later turn that asks puts back the mode it had; a harness without one has each prompt answered yes. Use these when you want the vendor-tuned loop or a subscription login that only the official CLI may use. They are optional and off until the owner turns one on (section 40).
- Both write into the same transcript format, so a Codex turn can be followed by a GLM turn in the same chat.

Where it can fail: a model trained inside its vendor harness behaves best there. The native harness follows Claude Code's tool shapes closely so Claude models feel at home; other models get the same tools with clear descriptions.

## 4. Multi-model in one chat

Every assistant message records which model wrote it. Modes:

- **Second opinion:** pick any message, send it (plus the conversation) to another model. The reply shows inline as an "aside". When the main model continues, asides are passed as quoted user-side context (`<aside from="codex">...`), never as its own words, so it does not get confused about who said what.
- **Jury:** N models answer the same prompt in parallel, then a judge model synthesizes, votes or ranks. Juror names can be hidden from the judge to avoid brand bias.
- **Debate:** two models argue for a set number of rounds, a judge concludes.
- **Switch:** change the session's model. The transcript is converted (thinking signatures dropped, foreign tool calls flattened to text where needed). A big chat shows the price first and offers a short handover (section 44).
- **Loop:** keep going until a command passes (`bun test`) or a phrase appears, up to N iterations.
- **Plan:** read-only tools, produce a plan, approve to execute.

## 5. Efficiency

- **Prompt caching.** The system prompt is kept byte-stable within a session (no timestamps). Dynamic data (recalled memories, todo reminders) rides on the latest user message. Anthropic gets explicit `cache_control` breakpoints on tools, system and the last two user turns. OpenAI-style providers get a stable `prompt_cache_key`. On Claude models every breakpoint carries one lifetime, set by `cache.ttl` (`auto`, `5m` or `1h`). A write costs 1.25 times input at 5m and 2 times at 1h, a read 0.1 times (0.05 on Opus 5.5 and Sonnet 5.5, 0.025 on Fable 5.1 and Mythos 5.1), and a read resets the timer. Costs count each lifetime at its own price (section 44). `auto` picks 5m where nobody waits on the turn (subagents, routines, loop mode, headless `conclave run`), since those requests come seconds apart, and 1h in interactive sessions, where the next request after a reply can come minutes later.
- **A frozen system prompt.** The runner builds the system prompt once and sends it byte for byte. It is built again after a compaction or /clear, when the agent, model, mode, folder, device or switches change, when a memory it shows is removed or edited, and when the instruction files or skills, read again once per user turn, say something else. Memories that extraction adds after a turn wait for the next rebuild, so they do not break the cache. The date in it is the date the snapshot was made.
- **Tool output offload.** Results over the size limit are stored in SQLite and the model sees a view plus an id. Before the head and tail cut, the output is reduced by its kind (`tools/compress`): a test report keeps its counts and every failure, a log its error, failure and warning lines with context, a JSON list its ends and error items, a diff its hunks, grep output 5 matches per file. ReadToolOutput pages, greps, or takes a query and returns the best matching blocks (BM25). Stored outputs go after 30 days, except in pinned sessions. Idea from context-mode, reducers from caveman and Headroom.
- **Old tool result clearing, in batches.** The newest 50,000 tokens of tool output stay. When the prunable output older than that passes 30,000 tokens, all of it is cleared in one pass, and each decision is stored on the message, so every later request sends the same bytes and the cache misses once per batch instead of once per turn. Old Write and Edit payloads go too once a later call on the same path succeeded. The app still shows the full output, and ReadToolOutput reads a cleared result back by its id.
- **Auto-compaction** at 80% of the context window, with a PreCompact hook. The size estimate starts from the usage the provider reported for the last call, plus the messages stored since. The summary follows a fixed template (objective, constraints, decisions, work state, pending asks, identifiers, files, next step), merges into the previous summary instead of summarizing it again, is fed by priority instead of a middle cut, and is checked for its headings and recent identifiers, with one retry.
- **Deferred MCP schemas.** With more MCP tools than `mcp.deferAbove` (30), requests carry a ToolSearch tool instead of their schemas, and a tool loads once a ToolSearch result in context names it.
- **Small model for chores.** Titles, summaries, memory extraction run on the configured small model.
- **Response cache** for deterministic chores (same input, same output).

## 6. Limits and auto-resume

Every provider error is classified (rate limit, quota, overloaded, auth, context length). Short waits are retried with backoff. Long ones (a 5 hour subscription window) put the session in `waiting_reset` with the reset time, enqueue a durable `session.resume` job, and notify you. When the window resets the session continues with a configurable resume prompt. Optional fallback chains switch to another model instead of waiting, except when the limit resets within 5 minutes and the chat holds `context.switchBriefAt` tokens or more: then the session waits (`limits.waitShortResets`, on by default, section 44).

Limit sources: response headers, error bodies, Claude Code and Codex local logs, the Z.ai quota endpoint, and an opt-in Claude OAuth usage read.

## 7. Providers and the model layer

Four provider wire types cover everything: Anthropic Messages (also MiniMax, CLIProxyAPI `/v1/messages`), OpenAI Chat Completions (Z.ai `/api/coding/paas/v4`, OpenRouter, DeepSeek, Groq, local), OpenAI Responses (GPT-5.x and Codex models), and Gemini. Internally everything is Anthropic-style blocks; each provider translates at the edge. Z.ai moved off its `/api/anthropic` shim: with a long tool list the shim keeps only the last tool and adds its own MCP tools. On CLIProxyAPI one provider id splits by model (`providers/split.ts`): Claude over Messages, GPT over Responses, Gemini over the native Gemini wire, the rest over Chat Completions, so the gateway never has to translate tool results, images or thought signatures between wires.

Decisions and sharp edges found while building:

- **Usage is normalized.** `inputTokens` always excludes cache reads and writes, on every provider, so cost math is one formula. Gemini's output count includes thought tokens; we keep that.
- **Thinking signatures are model-bound.** Anthropic signatures are stored raw. Other providers store a tagged form `cv1|<kind>|<model>|<payload>` and each provider replays only its own, same-model blocks. This is why a switch to another model drops foreign thinking: it would be rejected or meaningless. Thinking in the turns a compaction keeps after its summary is never replayed either (section 46).
- **Refusals are a stop reason, not a guess.** Anthropic `stop_reason: "refusal"`, OpenAI refusal content and `finish_reason: "content_filter"`, Gemini `finishReason` SAFETY, PROHIBITED_CONTENT and the like or a blocked prompt, and Z.ai's `sensitive` all map to `refusal`. Reply text is never read to decide it. Refusal fallback walks on it (section 47).
- **Claude 5 thinking is adaptive.** The 5 family and Opus 4.7/4.8 use `{type:'adaptive'}` plus `output_config.effort`, not a token budget. Older models use `enabled` + `budget_tokens`. This lives in one function so it is easy to update when the API moves.
- **Errors are classified for the limit logic.** 429 vs quota-exhaustion, 529/503 overloaded, context-length by message, plus provider-specific reset-time parsing (Anthropic `anthropic-ratelimit-*-reset`, OpenAI `x-ratelimit-reset-*` like "6m0s", Gemini RetryInfo, Z.ai error codes 1302/1303/1304/1308/... with reset times in UTC+8). A long window sets `resetAt`, which drives auto-resume.
- **Pricing** comes from a built-in catalog, refreshed daily from LiteLLM's price JSON into the cache dir, so costs stay current without a release.

## 8. The gateway

External CLIs (Claude Code, Codex, OpenCode) can route their model calls through the hub at `/gw/anthropic`, `/gw/openai`, `/gw/gemini`. The gateway is a pass-through: it forwards the body untouched and tees the stream to parse usage and rate-limit headers, so an external tool's spend shows up in Conclave's usage page. It holds provider keys per gateway key (one per device or agent, revocable), or relays a subscription login header without storing it. The only body edit is a model alias (`fast`/`smart`/`deep`). This is the small, stable part of what CLIProxyAPI does; the hard, fast-moving translation part is skipped by letting each model talk to the provider it was built for. Subscription logins are the exception: there the hub runs CLIProxyAPI itself and lets it do that part (section 24). Claude Code's own `/usage` is rebuilt from the local JSONL logs and an opt-in OAuth read, and via OTLP ingest at `/v1/metrics`.

## 9. Memory

Three layers: a small profile always in the system prompt, facts and procedures retrieved per turn (FTS5 BM25, blended with embeddings when configured), and episodes (session summaries). A small model extracts durable facts after a session goes idle, dropping anything that looks like a secret and treating the transcript as data. An external adapter mirrors to Basic Memory (markdown notes over MCP) so the same memory is readable and editable outside Conclave, and so the user's existing setup keeps working. The nightly "librarian" routine tidies and links those notes.

## 10. Devices and security

Daemons connect out to the hub over a WebSocket (the same network, the hub's own Cloudflare tunnel, Tailscale or a reverse proxy; see section 14), so no inbound ports on the user's machines. Device and client pairing use one-time codes shown as a QR. Tokens are stored hashed. Risky tool calls raise an approval that can be answered from the phone, with a signed one-tap action link in the push. Everything a tool changes is audited. A dangerous-command guard forces approval for `rm -rf /`, `mkfs`, fork bombs, force-pushes to main and similar, in every mode.

**Several people.** Every app, device, pairing code and token belongs to one account, and the hub's own computer is the owner's alone: a member's tools never run on it (section 35, docs/design/ACCOUNTS.md).

**Devices and apps.** A device is a computer that runs the device agent; sessions run there. Phones, browsers, the desktop app's window and the terminal app are apps: they only talk to the hub. The Devices page and every device picker list computers only, and Devices ends with one line ("3 phones and browsers signed in") that opens Settings, Your account, Signed in: each app with a plain name ("Chrome on Mac", "Pixel 8"), what it is, online or when it was last seen, This browser marked, and Sign out (`DELETE /api/clients/:id`). Any of a person's apps may sign out the others or itself; signing this browser out goes back to the sign in. The owner sees a member's apps in People and can sign them out (`GET` and `DELETE /api/people/:id/clients`). Setup's Devices step still shows the phone that paired, but neither it nor Done counts it as a device.

**Untrusted sessions.** A session reads untrusted input when its agent is marked `untrusted` (email, web), when an untrusted session started it as a subagent, or when a webhook payload reached it (the routine run is marked `meta.untrusted`, a reused session included). Text from outside can try to steer the model, so before this round a crafted payload could have read `~/.ssh` with Read and sent it out with WebFetch: read-only tools ran without asking. Now such a session:

- is offered only the tools its routine's allow list or its agent's tools list names (wildcards do not count; `mcp__server` names that server's tools), plus TodoWrite, AskUserQuestion, ReadToolOutput and the plan mode tools. Bash, Write, Edit, memory writes, goals, past chats and the other tools in `UNTRUSTED_DENY` come back only through a routine rule with content, such as `Bash(zpool status -x)`.
- gets no allow rule but its routine's own: config, Claude Code and project allow rules do not reach it. Deny and ask rules all apply. Every other call asks, read-only ones too, and bypass and acceptEdits modes allow nothing on their own (`askReadOnly` in `checkPermission`). A scheduled or webhook run refuses what needs approval, as before.
- ignores a hook's "allow" and a PermissionRequest hook's answer (their denies still count), asks when a runner extension's check throws, and never runs an ACP harness in auto mode.
- is never offered "always allow" (`noAlways` on the approval), and an answer that says it counts once.
- leaves no trace in memory: no profile, no recall, no extraction. Past-chat search and read, the daily digest, the day view and the reflection skip it. The same memory switch now works for any session (`chat.memory: false`), not only chats.
- gets framework tags (`<system-reminder>`, `<subagent_result>`, `<routine-payload>` and the rest) in outside text defused to `&lt;tag`: webhook payloads, hub data, web pages, its tool output, and the briefs and reports of its subagents.

Where it can fail: a routine allow rule is the owner's contract, so a broad one (`Bash(curl:*)`) still lets a payload send data out; an ACP harness in default mode follows its own rules for reads; routines made from the alert triage suggestion before this round keep their old allow list and lose `hostname`, `df -h`, `free -m`, MemorySearch and Notify on webhook runs until the owner adds them again.

## 11. Clients

The web app, desktop app and TUI all speak the same typed client (`packages/core/src/client`), which is the HTTP contract the server implements. The Android app mirrors it in Kotlin. Live state comes from one WebSocket that replays missed events by sequence number after a reconnect, so a phone that was asleep catches up without refetching everything. Android is native (Kotlin + Compose) rather than only a PWA, for notifications from its own background connection (no Firebase), QR pairing with the camera, biometric lock, and a share target.

Notifications stay inside Conclave, with no outside service to set up. The hub puts every notice on the event stream, so open apps show it as a toast, and the Inbox holds approvals, questions and alerts (section 28). Notices that pass the owner's rules (Settings > Notifications) carry `alert: true`, and devices show those: browsers and the installed web app through Web Push (the hub makes its own VAPID keys, and approvals carry signed Allow and Deny links), the desktop app as native notifications while it sits in the tray, and the Android app from its own connection. Each app tells the hub whether it is in use: `{type:'presence', active:true}` on coming to the front and again on input or as a heartbeat, `active:false` on going to the background. While some app said true within `notifications.idleSeconds` and has not gone to the background since, the hub holds everything but approvals, questions and errors, so a phone stays quiet while you are at the desk. Going to the background ends the hold at once, and a window left in front with nobody at it stops counting once its heartbeat runs out. The terminal app reports presence too: it connects as in use and says so again when you type, at most every 20 seconds, so a terminal left open while you are away stops holding notifications. Clients that never report presence (an older app, `conclave run` while it runs) count as in use on every frame.

## 12. How the build was done

The contracts in `packages/core/src` (types, config, client, machine, provider, tool, extension interfaces) were written first and frozen. Then the subsystems were built in parallel against those contracts: providers, tools, ACP bridge, memory and scheduler, extensions, server and gateway, web, Android, desktop and packaging. The engine was written last to wire them together. Integration took a handful of small fixes (a renamed method, a widened enum, a test env leak), which is the payoff of fixing the interfaces up front. The full agent loop is proven end to end with a mock model: user turn, a Read tool call, the tool result, and the final answer, with usage and cost recorded.

## 13. Interface

**Why.** The first web UI worked but looked machine-made: chips with colored dots, uppercase micro-labels, mono for every bit of metadata, an icon on every row, cards inside cards, colored dots standing in for models, background grids and glows, and spinners everywhere. The owner said so after seeing the screenshots, so the interface was redone from the ground up.

**The contest.** Three directions were built as working mocks of Home, chat, jury, onboarding and phone, in dark and light: Lab console, Quiet instrument and Ink and paper (screenshots in `docs/design/directions/`). They were scored on not reading as AI-made, craft, density, signature, owner taste, effort and accessibility. Lab console won (115 of 140). It is the only one that shows dense live state calmly, and it matches the owner's references (oxide.computer, Trail of Bits, Linear). A few ideas were grafted in from the other two: the three-tier logo rule and the Inbox from Quiet, the verdict as one large sentence and errors that explain from Ink. The result is `docs/design/SPEC.md`.

**Banned.** Pills and chips, uppercase letter-spaced labels, mono for anything but code, commands, ids and aligned numbers, an icon on every row, nested bordered boxes, colored dots as identity, grids, crosshairs, noise and glows, purple gradients and glass, KPI tile rows with sparklines, lists of rows ending in toggles, marketing copy, and spinners. State is a word in a fixed place ("running", "failed", "Waiting 2 min"). Color carries meaning only: violet for live work and focus, amber for what needs you, red for faults, green for healthy. The primary button is neutral ink. The phone layout keeps the same bans: filters are words (the Inbox), a two way switch is a segmented control (Chats), and rows carry no icon (You); the tab bar is where icons belong.

**The wave.** A field of small dots whose brightness moves like a slow wave, quantized to a few levels with ordered dithering so it reads as a dot matrix. It is our own code: one shared loop at 30 frames per second drives every instance, it scales for device pixel ratio, pauses offscreen and in hidden tabs, and draws one still frame under reduced motion. It has three uses: the hero on the welcome screen, a thin strip that stands in for a spinner while a model works (its speed follows tokens per second), and a faint field behind empty states. Nowhere else. (A fourth, the scope on Home that plotted model output for the last hour, went with the chat-first Home in section 15.)

**Logos.** Real marks from the MIT-licensed LobeHub icon set, in three tiers: the harness mark when a session runs through a CLI (Claude Code, Codex, Gemini CLI, OpenCode), the model family mark for a model (Claude, GPT, Gemini, GLM, Qwen), and the company mark for billing, keys and limits. They are mono in meta lines and take brand color only where the model is the subject (pickers, jury rows, provider rows). Brand colors that fail contrast on a theme fall back to mono, and unknown providers get a one or two letter monogram. Model ids are shown as names ("Sonnet 5.5", "GPT-5.5 Codex").

**Home.** The first version opened on one sentence about the state of things ("Two sessions running. Two are waiting on you."), with a quick start bar under it and the output scope beside it. Below were three columns split by rules, no cards: what waits on you (the approval card is the one filled box) and what is running, every usage limit with its reset, and today's routines on a 24 hour axis with the devices that are online. Home now opens on a chat and keeps that status page under it (section 15).

**Onboarding.** A hub that has not been set up opens a ten step setup, and every step can be skipped: connect the hub, add provider keys (each tested on paste, with errors that say what is wrong), find coding CLIs on each machine, pick default models per kind of work, memory and Basic Memory, import past Claude Code and Codex sessions, pair this computer and the phone, choose notifications, add starter routines, done. It can be run again from the command palette.

**Chat and motion.** Chat is a plain conversation page next to the workbench, which the nav now calls Sessions (`/chats` redirects to `/sessions`). A chat is a session with `kind: 'chat'`. It runs the `chat` agent on the hub with only the web and memory tools, and each chat turns thinking, web search and memory on or off. Its turns count under their own source on the Usage page. Motion says what the model is doing and is built from the mark. While the model thinks, the mark's seven dots ride their own sine with the violet crest on top. While it writes or runs a tool, a packet of light crosses them. Waiting is still with an amber crest, failed is still with a red one, and done settles back into the still mark. Chat replies and session turns use the same mark, words and timings. Streamed text arrives dim and comes up to full per chunk through the CSS Highlight API, so nothing lays out again. Reduced motion draws a still frame of every state and counters keep ticking. The spec is `docs/design/CHAT-AND-MOTION.md`; the review of this round is `docs/design/CHAT-AND-MOTION-REVIEW.md`. (The dot mark and its motion were later replaced by the knot; see The mark below.)

**The mark.** By October 2026 the app wore two marks: seven dots on a sine in the top bar, the app icon and the favicon, and a canvas trefoil, the Knot, for thinking and as the Home hero. The owner compared three single marks on one canvas (a knot with a light, a wave of seats, a ring of seats) and picked the knot with a light: the trefoil drawn as a ribbon with real over and under crossings in the foreground color, with one violet light on it. One mark now does both jobs. Still, the light rests on the right lobe; at work the knot dims and the light writes it (thinking) or travels it (a tool), turns amber and holds while it waits on you, holds in grey at a limit, turns red and stops on a failure, and fades when done. The crossings and the light that passes under a strand are why it reads as a knot at 16px, and nothing about it says chat bubble or AI node. Everything comes from one file, `docs/design/brand/knot.json`, and one script, `scripts/brand/knot.ts`, which writes the web, desktop, iPhone and Android icons and the geometry the web and Android code draw from. The pieces split away from the crossings, so a round end never lands on another strand and a moving light never shows a dot on top of the strand that should cover it. Rules: `docs/design/brand/README.md`.

## 14. Remote access

**Why.** The owner asked why Conclave needed Tailscale when Claude Code works anywhere with nothing else installed. It never needed it: the hub only listened on 127.0.0.1 and the docs pointed at Tailscale for everything else. Claude Code works anywhere because Anthropic runs the relay. Conclave now does the same with a relay that needs no account.

**Same network by default.** Unless `--host`, `CONCLAVE_HOST` or `server.host` pins it, the hub listens on every interface and a filter answers loopback and private networks only (RFC 1918, link-local, 100.64/10, IPv6 ULA). A phone on the Wi-Fi scans the code and connects; a hub on a VPS is not exposed to the internet by this. Off answers only this computer and the tunnel. `127.0.0.1` in config.json counts as unset because first runs used to write the whole server block there; the first run now writes only the token.

**Quick tunnel.** A Cloudflare quick tunnel (`cloudflared tunnel --url`) gives an https address with no account. The hub owns it (`packages/server/src/remote`): it downloads cloudflared into its home on first use, checks size, the SHA-256 GitHub publishes for the asset (when GitHub's API answers; a receipt next to the binary records whether it did, and Settings says so), the executable header and `--version`, writes it next to its final path and renames it in, so nothing runs from a temp dir. cloudflared gets its own HOME, config file and an environment without Conclave's secrets or `TUNNEL_*` settings, so a `~/.cloudflared` setup or a stray `TUNNEL_TOKEN` cannot change what it runs. Its pid goes in `<home>/cloudflared/pids`, and a hub that starts after a crash stops what the last one left. The hub reads the address from the log, calls it on when Cloudflare registers a connection, restarts it with backoff when it dies and stops it with the hub. Remote access is off until the owner picks it (one tap in setup step 1): a hub should not appear on the internet on its own.

**The address changes.** Every restart of a quick tunnel is a new address. On a planned change (New address, a mode switch) the new tunnel comes up first, `remote.updated` reaches every client and `{type:'addresses'}` every daemon, and the old tunnel keeps serving for 20 seconds while they move. Daemons keep every address and try the next when one fails, so a crashed tunnel still leaves the same network. Pairing codes carry the other addresses as `alt` parameters for the same reason. A page served from the old address offers a link to the new one. The desktop app goes by itself: its page moves to the new address with the app's own token in the fragment, and the shell takes that as the hub moving, saves the new address and grants it notifications (a move without that token opens in the browser as before). When the address in use stops answering without warning (cloudflared crashed, the hub restarted), daemons, the terminal app and a web app opened from another origin try the other saved addresses. The desktop shell keeps the hub's address list from pairing and `GET /api/remote`, and tries it on start when the saved address does not answer. A dropped quick tunnel address is never tried again, since Cloudflare may hand that name to someone else later. Someone away from home when the hub restarts has to scan again, which is why there is a stable option.

**Stable.** A named tunnel on the owner's Cloudflare zone, made through the API with a token that has Account, Cloudflare Tunnel, Edit and Zone, DNS, Edit. The ingress is managed remotely (config_src cloudflare) and points at 127.0.0.1 and the hub's port, refreshed when the port changes. The API token and the tunnel token live in the secrets store, and the tunnel token reaches cloudflared in its environment, not its arguments.

**Best address.** Stable tunnel, quick tunnel, the owner's own URL, then the same network. The hub sets the first one as a runtime `server.publicUrl` (a config layer that is never written to disk), so pairing codes, hub info, notification links and CORS all use it without knowing about tunnels.

**A public address is guarded.** The web app's files are public; everything else checks a token, a key, a pairing code or a signed link. Twenty different wrong tokens from one address in ten minutes block it for a minute, doubling up to an hour; ten wrong pairing codes or hub passwords do the same. The same wrong value again counts once, so a phone retrying an old token cannot lock out a household that shares one public address. Only a request from this machine with no proxy header is exempt; a request through the tunnel cannot claim to be local. Behind a tunnel or proxy the client address is the last X-Forwarded-For entry, the one the proxy added, not the first, which the client controls. The gateway no longer relays a caller's own provider login for calls from the internet without a gateway key (`gateway.relay: open` brings that back). Blocks, wrong codes, pairings and remote access changes go in the audit log.

**The hub proves who it is.** A phone on public Wi-Fi can reach a machine that is not the hub at an address the hub used to have: a reused LAN address, or a quick tunnel name Cloudflare later gave to someone else. Apps used to send their token to whatever answered. Now the hub has an Ed25519 key pair, made on first start and kept in `<home>/hub-key.pem` (mode 0600, like `secrets.json`). `GET /api/identity?nonce=...` signs `conclave-hub-identity-v1\n<nonce>` with it and needs no token. Pairing QR codes carry the key's fingerprint as `fp`, and the replies to pairing and password login carry the key. An app keeps the key with its token. Before the first request or socket to an address it checks that address with a fresh nonce, and it checks again after 10 minutes and after every reconnect. A wrong key, a bad signature, or an answer that is not a proof means it sends nothing (`HubIdentityError`). An address that does not answer is offline, not a stranger. Loopback is not checked, and neither is the web app the hub serves: that page came from the address, so a check there proves nothing. The shared TypeScript client does all this when it is given `hubKey`, with Ed25519 from WebCrypto, so it runs in browsers and Capacitor as well as Bun. Logins saved before this keep the key from their first check. The hub's key is not in backups: a restored hub on a new machine has a new key, and apps pair with it again (their tokens are not in backups either). Spec: `docs/design/HUB-LOGIN-AND-IDENTITY.md`.

**Password login.** A backup to the QR code, for a phone without a camera at hand or a hub whose Devices page cannot be opened. It is off until the owner sets a password (`conclave password set`, 12 characters or more; the routes are owner only). Only its argon2id hash is kept, in the database's key-value store, so it is in neither config.json nor a backup. `POST /api/login` gives the same reply as pairing. A wrong password and no password at all get the same message and take the same time (with no password set, the guess is checked against a stand-in hash with the same cost). Each wrong one counts like a wrong pairing code: the same limit per minute and the same block, and the audit log gets `login.failed` or `login.client`. Apps send a password only over https, or to a loopback or private address.

Where it can fail: Cloudflare can rate limit quick tunnels from one IP and gives them no uptime guarantee; networks that block outbound port 7844 stop cloudflared (the error says so); the same network is plain http.

## 16. The life assistant

**Why.** The owner liked Meta's Muse as a personal assistant and asked for the same setup, fitted to their profile and built on the memory Conclave already has. The default `assistant` agent now keeps goals, plans the day, reviews it, and can poll a checklist and reflect on how the owner likes to work. Plan and API: `docs/design/ROUND-LIFE-ASSISTANT.md`; how to use it and what it costs: `docs/ASSISTANT.md`.

**Goals are a table recalled through memory.** Goals need subgoals, dates, task links and a dated history, which neither a memory row nor a new memory kind can hold without parsing, and a new kind would ripple into every place that switches on kinds. So goals live in two small tables (created by their own module, outside the shared migration list), and each top-level goal is projected into memory as one global fact through the same path notes imported from a connection take. Every agent recalls goals with the recall it already does, at no extra cost per turn, and the projection is never mirrored as loose facts, deduped into or rewritten by extraction. When a connection writes, each goal is one Basic Memory note with its progress log.

**Preferences are a profile memory.** What to tell the owner, what never, the message hours and the format are stored in the hub and rendered as one profile memory for the assistant agent only. The notifier is wrapped so a routine's message outside the hours waits as a durable job; approvals, questions and failures do not wait.

**Cheap by default.** The heartbeat and the nightly reflection are off until turned on. Both use built-in prechecks that run in the hub: the heartbeat compares a digest of tasks due soon, goals at their date and the checklist, and skips the model when nothing changed; the reflection skips days without chats and gives the model only the owner's and the assistant's words, never tool results. Templates now carry their id and the hashes of earlier prompts, so installed routines get better prompts without losing the owner's schedule or edits.

Where it can fail: the heartbeat cannot see a calendar or mail without the model, so such checks run when something else changed and at least once a day; goals are not in hub backups yet.

### Assistant home: one thread per account

**Why.** The owner wanted the assistant to be one chat, like Hermes or Muse: separate assistant chats felt like work. Each account now has one assistant session, marked `meta.home`, pinned and titled "Assistant". `engine.assistantHome(account)` returns it or makes it (two calls at once share one promise, so they get the same session); `GET /api/assistant/home` returns it with the same shape as `GET /api/sessions/:id`, for the caller's own account. A fork of the thread is a normal session.

**Routines.** `sessionPolicy: 'home'` posts a run's prompt as one queued turn in the thread, its user message marked `meta.routine`. The routine's rules and the refusals nobody can approve hold only while that turn runs (`engine.routineTurns`, the turn's start and end hooks in the runner), and the owner's messages never join it as steering. A webhook run, a run with a payload and a watch never go there: save refuses a watch, and such a run starts a new untrusted session. The Morning brief uses home. The Heartbeat stays on new: in the thread it would run on the thread's model with all its context, past its cost cap, and post every 30 minutes.

**Long life.** The thread is a normal session, so auto compaction (`context.compactAt`) and memory recall apply as they do anywhere.

Where it can fail: a home routine runs on the thread's model, not the routine's `model`; the composer's model pick on Home does not change the thread's model; tool results a routine's turn read (mail through the email agent) stay in the thread's context until compaction.


## 17. Folders across devices

**Why.** The owner starts a chat on the PC and wants to go on with it on the Mac, where the same project sits at another path (`~/code/portfolio` against `~/Developer/portfolio`), often kept in step by Syncthing. Before this round a session on an offline device ran its tools on the hub, Bash kept the old folder after a change, and a harness session lost its whole context when it could not resume. Plan and API: `docs/design/ROUND-IMPORT-PATHS-WORKFLOWS.md` section 2.

**A project is an identity plus a folder per device.** The identity is read through the device's own shell: git root commits, HEAD, the normalized remotes (all of them, with SSH aliases resolved), the Syncthing folder the path sits in, and an optional marker file. Two folders are the same project at exact (marker, Syncthing folder, or same history and a shared remote), strong (same history, or the last HEAD is there, which covers shallow clones) or weak (name only). Different histories are a mismatch. A folder of another history that the owner uses once never changes the project's identity or its list of folders, and a shallow copy never replaces the root commits the project knows. Remote URLs lose any password or token before anything stores or shows them. The code is `packages/core/src/projects`; it makes its own tables, so the shared migration only adds `sessions.project_id` and the checkpoint columns.

**Moving finds the folder.** A move tries, in order: the same path, a pinned or known location, the same Syncthing folder on the target (read from `config.xml` by the daemon; the API key never leaves the device), a learned path pair for the two devices, and a search of the device's roots. Each hit must match at strong or better. When nothing does, Choose folder browses the target, starting at the best guess, and says in one line how each folder compares ("Same git history and remote as the arch-desktop copy"). A different history offers Use once and Use and remember. Clone here and Continue without files are the way out. A confirmed choice teaches a path pair, so the next project needs no choice; a folder chosen inside the repository saves the repository root. `PATCH /api/sessions/:id` with a new device and `/device` go through the same move. A session in the middle of a turn is not moved (a turn parked for an offline device is), and a second move of the same session waits for the first. After Continue without files the banner stays, with Look again, until the project's folder is found.

**The resumed context.** Stored history is never rewritten. One note rides on the next message ("This session moved from arch-desktop at ... to macbook at ..."), file tools map an old path to the new folder when the old one is not there and say so once, Bash gets a one line note when a command names the old folder, and compaction lists files relative to the project. A harness that cannot resume gets the conversation as context, and a resume id made on another device or folder is not tried. Project notes in memory keep their folder as the key, and recall matches every known location of the project, so a note saved on the PC is recalled on the Mac. Permission rules judge the path the tool will really touch, so a deny rule on `./.env` holds when the model names the file by its old path, and an approval card for an old path says where the call lands ("now ~/Developer/portfolio/notes.md"). A root of `/` is never an old root, since it would map every path on the device.

**Safety.** At the end of each turn the hub keeps the branch, HEAD and the number of uncommitted files. A move compares the target with that: a missing commit, commits behind, Syncthing still pulling, or uncommitted work left on the other device. The owner sees one line with Check again and Continue. `*.sync-conflict-*` files in the folder are counted too, but say so in the session's details, not in that line or the move's notice (v0.4.2: a line about two conflict files on a folder the owner had just chosen read as an error). The first change in a folder below an exact match asks once; a mismatch asks every time unless the owner chose Use and remember, and a pinned folder that now holds another history asks every time too. Harness sessions get the same question through their own permission prompts, even in bypass mode. Freshness compares only with the project's own history, never with a folder used once. Checkpoints are taken on the device that has the files, with a key built from the device and the folder, and restore only there. A session on an offline paired device parks with "macbook is offline. Wait, or run on another device." and goes on when the device is back or the session moves; the banner offers the other device when the folder is there too.

**Daemon protocol 2** adds the Syncthing RPCs (and the import RPCs). The hub accepts versions 1 and 2, and a version 1 daemon simply skips the Syncthing step.

Where it can fail: a history rewrite changes the root commits, so the remote and HEAD checks rank the folder and the owner confirms it once. Syncthing can be mid-sync during a move; the freshness line says so. Two clones of one repo on a device both match; the pinned one wins. Project files (`.claude/`, `.conclave/`, `.mcp.json`) and project hooks are still read on the hub at the session's path, harness transcripts are not copied between devices, and trust is still per path, not per device. A harness that never asks for permission (its own bypass mode) cannot be stopped by the folder check. A chat imported from a device the hub never saw has no identity to compare, so the Mac copy shows as a weak match until the owner picks it once. The Android app has the banner, the folder sheet and Run on another device, but no Devices > Folders screen.


## 18. Workflows

**Why.** The owner uses Claude Code's Workflow tool for reviews, audits and research: a script fans work out to many agents, checks what they claim, and keeps going after a restart. Conclave had subagents but no way to run a fixed plan of fifty of them, resume it, or bound what it costs. Plan and API: `docs/design/ROUND-IMPORT-PATHS-WORKFLOWS.md` section 3; how to use it: `docs/WORKFLOWS.md`.

**A script, not a prompt.** The script API is Claude Code's: a pure `meta` literal first, then `agent`, `parallel`, `pipeline`, `phase`, `log`, `workflow`, `budget` and `args`. Scripts from `~/.claude/workflows` and `<project>/.claude/workflows` run unchanged. A script runs in QuickJS compiled to WebAssembly, with no file system, process or network, a 60 s CPU limit counted only while script code runs, and 64 MB of memory. Every host call passes JSON text, so nothing from the hub leaks into the sandbox. `Date.now()`, `new Date()` and `Math.random()` throw, also through the prototype chain, because they would break resume. Waiting on the hub costs no CPU, so each run also stops at 10,000 timer and lib calls and 1,000 checks, even when the script catches the error. Scripts that set `runtime: 'conclave'` also get `lib` and per-call Conclave options (device, folder, tools, worktree setup, a worktree made from an earlier call).

**The journal.** Each `agent()` call has a key: a hash of its prompt, schema, model, effort, agent type, isolation and Conclave options, plus how many times the same key came before. A resume replays the longest unchanged run of answers and runs the rest. An edited call reruns, and so does what uses its answer. `lib.exec`, `lib.runCheck`, `lib.ask` and `lib.approve` are journaled too; a check's key includes HEAD and a hash of the diff, so a changed tree runs it again. A worktree call replays only while its branch still points at its commit. Runs a crash left behind resume once at the next boot, unless more than 3 died together, which looks like a crash loop. A usage limit parks the call and a durable job resumes it at the reset.

**Agents are Conclave sessions.** Each call is a child session of the session that started the run, so it has a transcript, usage rows and the parent's trust. It runs the `workflow` profile or the `agentType` it names (verifier, builder, tester), on a tier word (fast, smart, deep) and an effort. A schema goes through the StructuredOutput tool, with up to 5 tries; an ACP harness returns JSON in its final message, checked in code. A tier word the owner did not pin can land on `claude-code/opus`; when that harness does not start, the call runs again on the session's model and later calls skip it. Worktrees live on the session's device under `~/.conclave/worktrees`, never under a Syncthing folder. A changed one is committed, with the device's git identity (Conclave only when it has none) and the `Committed-by: Conclave (<model>)` trailer, to a kept branch that the owner can diff, merge, cherry-pick or discard. Limits: 8 calls at once per run (16 at most), 6 per provider, 16 across the hub, 8 worktrees per device, 1000 agents per run. A budget is a hard ceiling: `agent()` throws once it is spent, and what earlier attempts of the same run spent still counts after a restart.

**Checks in code, not in the prompt.** `lib` holds the parts that cut false positives: a citation check (the quote must be within 3 lines of the cited line), dedupe by file, class and a 5 line window, a refuter panel of 3 lenses kept at 2 of 3 complete votes, the median severity of the confirmations, judge panels that score both orders and call a flip a tie, loop-until-dry, and `dropDismissed`, which drops findings like 3 or more the owner dismissed before and logs how many. The owner marks a finding Fixed, Dismissed (with a reason) or Ignored. Twelve workflows ship as files: review-changes, deep-research, research-sweep, plan-implement-verify, fix-until-green, fix-issue, bug-hunt, security-audit, design-panel, ui-pass, migrate and compare-harnesses.

**Ultra.** A switch per session in the composer. With it on, the system prompt asks the agent to plan and run a workflow for each real task, one per phase, and to verify before it adds finders. The first workflow in a session asks for approval; after that, runs whose estimate is under 2M tokens start on their own, and a run with no estimate asks. A script an agent wrote cannot widen its own permissions: `meta.permissions.allow` counts only for built-in, plugin and saved workflows and for scripts the owner sends through the API. A script file anywhere outside the owner's library on the hub counts as a project script, because an agent can write one in its own folder and name it with `scriptPath`. Such a run is scoped: its agents stay on the run's device and inside its repository or this run's own worktrees (an agent inherits the session's permission mode, and acceptEdits allows edits in the agent's own folder), and its worktree setup command asks like `lib.exec`. A project's own `worktreeSetup` runs without asking only in a trusted folder. At most two nested `workflow()` sandboxes run at once in a run, since each may hold 64 MB. A `+500k` word in the owner's message sets the run's budget and, with Ultra on, counts as that approval. An allow rule `Workflow` skips the question everywhere. Chats never get Ultra.

**What the owner sees.** Workflows in the sidebar: the library by source and the runs. A run view shows a status sentence, the live step, phases with one row per call (state word, model, last tool, tokens, cost), findings with verdicts, kept worktrees, the log and each agent's transcript in a side sheet. In a session, the Workflow call is a card that opens into the same view. A call that waits on a tool approval shows waiting in amber, and the approval's card shows in the chat that started the run, under "Workflow deep-research, agent search r1 3, asks" (section 19).

Where it can fail: scripts cannot import, and a script that loops forever stops at the CPU limit; `dropDismissed` compares words, not meaning; a plugin workflow that names an agent the owner lacks runs general-purpose with a log line; `lib.exec` runs on the device and asks like Bash; Android shows runs, the run view and the Ultra switch, but cannot start a workflow from the library yet. Below 1560 px wide the Workflows link sits under More in the top bar. The progress event names the call `callSeq`, not `seq` as the plan said, because the event envelope's own `seq` overwrote it.


## 19. Specialist subagents

**Why.** The owner saw Claude Code's build, design and research subagents and asked for the same, with fewer false positives. The evidence points at structure, not personas: a tool set the agent cannot misuse, a model tier that fits the stage, a short prompt with a fixed output contract, and a fresh context that sees only the brief. Persona openers showed no accuracy gain across 162 personas (Zheng et al.). The biggest cut in false positives comes from the pipeline: finders that report everything, then a verifier in a fresh context that tries to refute each finding. Plan: `docs/design/ROUND-IMPORT-PATHS-WORKFLOWS.md` section 4; the agents: `docs/agents/README.md`.

**Twelve new profiles.** verifier (the refuter: deep tier, xhigh effort, unverifiable is never refuted), builder (one scoped change in the files it was given), tester (never changes source), debugger (root cause from a repro, diagnosis only), designer (inside the design system, checked by screenshots), refactorer (stops on a red suite), docs-writer (every fact has a source), and for research web-searcher, code-researcher, fact-checker (claims and URLs only, never the draft) and synthesizer (the one writer). workflow is the default step of a workflow script. Each prompt is one role sentence, the rules that came from a known failure, and the output contract, under 360 words, with no capital-letter emphasis. explore takes a thoroughness word, reviewer gains a finder mode, researcher leads research with web-searcher subagents, planner names a check per step.

**Harness support.** Frontmatter `model:` takes tier words (fast, smart, deep), and Claude Code's haiku, sonnet and opus map to them, so an agent can ask for a stronger model than the default; `extensions/agent-model.ts` resolves them per session. `effort:` keeps xhigh and max. `hooks:` and `recipes:` give a profile its own hooks, so the tester's write scope applies only to tester sessions; a subagent's Stop hooks run on SubagentStop. A new write-scope recipe refuses file writes outside a glob list. Task takes a `schema`, and the child returns a validated object through StructuredOutput. Review mode sends a frozen packet (the owner's brief, the answer, the diff with new files, AGENTS.md or CLAUDE.md, SPEC.md) instead of 30,000 characters of the writer's transcript. The reviewer is often another provider, so new files that usually hold secrets (.env, keys, credential files) are left out by name and tokens in the packet are redacted. A specialist whose tier lands on an ACP harness gets its profile in front of the brief, since a harness takes no Conclave system prompt, and a profile without file tools never runs the harness in auto: with no shell it runs read-only, with a shell each edit and command is asked.

**The verify gate.** HARNESS-REVIEW item 15: after a turn that edited files, the project's check runs on the session's own device, through its Machine, before the turn may end; a failure sends the agent back with the last 40 lines, at most 3 times. It replaces the stop-verify hook for coding agents, because hook commands run on the hub, and a session on arch-desktop needs its type check on arch-desktop. It runs project code without a prompt, so only in trusted folders or when the rules already allow the command. A check that cannot run to the end (it timed out after 120 s, or exit 126 or 127: the command or a tool is missing on the device) does not send the agent back; the owner gets one notice. In a monorepo package the lockfile can sit in a parent folder up to the repository root. Main sessions get it through the runner's onStop point; subagents through a SubagentStop function hook, since the runner hands a subagent's stop to its caller.

**Approvals from subagents.** A subagent and a workflow agent run in child sessions the owner is not looking at. The owner asked their assistant to find some mail, the email subagent needed approval for MailRead, and the card showed only in the Inbox while the chat waited with nothing to answer. Now every approval and question carries `rootSessionId`, the top session of the one that asks (walking `parentId`, and a workflow agent's run back to the session that started it, `core/src/engine/ask-origin.ts`), and, from below the top, `from` with the asking session, its agent, the subagent's description or the workflow agent's label, the workflow's name and the chain of sessions in between. The card shows inline in that chat, as Claude Code shows a subagent's prompt, as well as in the Inbox, under a quiet "Subagent email asks" or "Workflow deep-research, agent search r1 3, asks"; its answers work in place, and the session answer reads "Allow for this subagent" because it applies to the session that asked. Nothing about answering changed: the request keeps `sessionId`, the same id resolves it, and only someone allowed to answer for that session may. The Inbox says "from subagent email in <the chat's title>" and opens the chat. The subagent's row, the running tasks line and the chat's live line say "waiting on you". Web: `web/src/lib/asks.ts`; Android: `client/logic/Asks.kt`, the session screen and the Chat tab. Details: `docs/design/CHAT-AND-MOTION.md` 1.10.

**Checked cheaply.** A canary test (`test/engine/agent-defaults.test.ts`) pins each agent's key lines, tiers, tools and recipes, so an edit that drops the refute default or the owned-files rule fails CI. Real-model trials ran each new prompt on small scenarios with the official CLI (`bench/agents/`): 21 trials, $0.86, three prompts changed once.

Where it can fail: a deep tier with no deep model configured falls back to `claude-code/opus` when that harness is installed and turned on, else to the session's model, and a test engine must pin `models.tiers` so it never reaches a real key. write-scope covers the file tools, not Bash, and when it cannot run (jq missing on the hub) it refuses the agent's writes instead of allowing them. Hub recipes start in the hub's home when the session's folder is on another device, so the tester's scope holds on arch-desktop and the MacBook too. A user, Claude Code or OpenCode agent with the same name as a specialist replaces it, recipes included. A catalog agent file can bring `hooks:`; the Discover preview lists them with a warning. The specialists had one round of single-run trials on Sonnet only, with no blind validation and no GLM, GPT or Gemini runs. web-searcher still lists unopened sources under claims (labeled), which the fact-checker catches in deep-research runs.


## 20. Chat import and memory learning

**Why.** The owner has months of Claude Code and Codex chats and wanted them in Conclave, with the choice to teach memory from them (and through a Basic Memory connection, to the notes there too), or to import them without touching memory. The old import read the newest 100 files per tool over the WebSocket, took every user line as the owner, and lost one prompt in five on a measured 23 MB session; those errors went straight into memory as fake preferences. Plan and API: `docs/design/ROUND-IMPORT-PATHS-WORKFLOWS.md` section 1; how to use it: `docs/MEMORY.md`, Importing past chats. (Section 16 went to the life assistant, so this one is 20.)

**Readers that know who spoke.** The Claude Code reader walks the live chain from the last prompt through `parentUuid` and `logicalParentUuid`, so rewinds, edited prompts and retracted replies stay out, and queued prompts come in where they were typed. Every user message carries an origin (human, task, peer, sdk, system); task notices and peer messages become asides, so neither the list counts nor the learning job read them as the owner. Codex reads archived and zstd rollouts, titles from its index, and paginated forks with their base. Gemini CLI replays its rewind and patch records. claude.ai and ChatGPT exports arrive as uploads. Unknown line and content types are counted, never dropped in silence.

**A ledger, not a guess.** One row per chat file, keyed by a fingerprint that survives the file growing and is the same on every machine, so a Syncthing copy maps to the one session. Re-importing appends what is new, a chat that grew on both sides becomes a fork beside the old session, and a stale copy adds nothing. The ledger row is written before the session, so the durable `import.run` job resumes after a restart without importing twice. Undo keeps 30 days. A chat from a coding tool resumes with the coder agent (the default agent is the personal assistant), on its own harness model until the owner picks another. A model that does not answer stops only the learning: the copied chats stay, and the batch says which model failed and that Resume goes on.

**Learning confirmed in code.** One small model call per 30k token window returns an episode and items, and code keeps an item only when its quote is in the rendered transcript, its kind and basis are known words, and the secrets filter passes (now with the token and password shapes found in the owner's transcripts). The QA pass tightened the quote check: it must come from a row the basis allows (the owner's own words for "user said"; never an assistant line alone, and never a fetched web page), share words that matter with the item (its row at least two), and be more than one word; a number in the item must be in the chat; row labels inside tool output are neutralized so a page cannot pose as the owner. Consolidation only touches ids the prompt listed. Preferences said once wait for review; supersede keeps both rows and recall skips the old one; dedupe has an IDF veto, so "pve" never merges into "madx". The estimate prices the run before it starts.

**Device side.** Daemon protocol 2 adds `importScan`, `importRead` and `readRange`: the device runs the same readers and sends compact rows for files that changed. A v1 daemon is read from the hub once per change.

**Basic Memory notes that follow changes.** New connections keep grouped notes (per project, per host, paths, procedures, profile, a monthly session digest) rebuilt from local rows through a coalescing queue of two, so updates and deletes reach the store; older connections switch with Group notes.

**Hostile and broken input.** Readers refuse files over 512 MB (zstd unpacking is capped too), zip entries are inflated with a hard cap, history_base loops and ChatGPT branch loops end, a damaged conversation in an export is counted and skipped, a device reply is checked before storage, and a file whose conversation id changed fails closed. Undo keeps sessions the owner kept going in.

Where it can fail: vendor formats drift between releases (the unknown counts show it); a single remark can still become a wrong preference (review and undo keep it cheap); Android imports from a device but leaves export uploads to the web; mem0 and HTTP connections still get writes only, not deletes; there is no OpenCode reader yet.


## 21. Memory in claude.ai and ChatGPT

**Why.** The owner wants one memory across every chatbot, not only the coding CLIs. Claude Code, Codex and OpenCode already reached `/mcp` with a token in a header. claude.ai custom connectors and ChatGPT apps cannot: they follow the MCP authorization flow and sign in with OAuth. Plan and threat list: `docs/design/MCP-OAUTH.md`; how to set it up: `docs/MEMORY.md`, claude.ai and ChatGPT.

**The hub is its own authorization server.** A separate identity provider would be one more thing to run for one person. The hub serves the protected resource and server metadata, dynamic registration and client metadata documents (both, since Claude and ChatGPT pick whichever the metadata offers), authorize with PKCE S256 only, a token endpoint with rotating refresh tokens, and revocation. Every answer carries `iss`. Codes, tokens and secrets are stored hashed in five tables of their own.

**Consent is a web app page.** `/oauth/authorize` checks the client and the redirect URI, then sends the browser to `/oauth/consent`, where the owner is signed in with the same token as everywhere else. The page names the redirect host, not the self-given name, flags lookalikes and loopback clients, and lets the owner leave scopes out. The answer is a JSON post with the bearer token and a one time value, so another site cannot make it.

**Scopes are checked before the SDK runs.** Only an HTTP 401 or 403 makes claude.ai ask the owner again; a tool error inside a 200 does not. So `/mcp` reads the JSON-RPC body, checks each `tools/call`, `prompts/get` and `resources/read` against a small table, and answers `403 insufficient_scope` when a scope is missing. `tools/list` only shows what the token may call. A tool without a row in the table is closed to OAuth tokens.

**memory_context.** A chatbot starts each chat cold. One read-only tool returns the profile, the most important facts, active goals with their next step and today's plan in about 1,500 tokens, and its description asks to be called first. The same text is a prompt and a resource.

Where it can fail: claude.ai and ChatGPT need a stable https address, so a quick tunnel breaks the connector on every restart; their egress addresses are shared, so twenty different wrong tokens from strangers using them can block them for a while; a refresh retried after a lost answer looks like reuse and ends the grant.

## 22. Facts, past chats, skills and the daily digest

**Why.** The owner read Hermes Agent's memory rules and agreed with three of them: memory holds facts, not orders; past work is searched, not recalled every turn; and a method that worked becomes a skill the agent writes itself. They then asked for one nightly routine that turns the day's chats into Basic Memory.

**Facts, not orders.** A note saved as "Always answer short" is read back later as an instruction and can win over what the owner asks for then. The extraction, file import and learning prompts now ask for facts with a good and a bad example, and a word check in code (memory/facts.ts) looks at how each item starts and at orders aimed at "you". A simple order is rewritten ("Always use pnpm" becomes "The user uses pnpm."); anything else is dropped from extraction and sent back from MemorySave and the MCP memory_save with a short error. The check is cheap and has false positives at the edges ("Run the tests..." as a fact about a project); a nounlike first word followed by "is" or "has" passes.

**Past chats on demand.** SessionSearch and SessionRead search the hub's own transcripts: messages_fts (which already held only text), a new sessions_fts for titles kept by triggers, and episode summaries. Episodes no longer ride along with per-turn recall unless memory.recallEpisodes is on, so a turn pays for the past only when it asks. The search leaves out the session asking, subagents, chats with memory off and untrusted agents' sessions, wraps results as data, and is the same code behind the MCP chat_search and the daily digest. Reminders that rode on a user message (recalled memories) are no longer indexed, and old rows are checked again when a snippet is cut, so a hit must be in what was written.

**Skills agents write.** A learned skill is one SKILL.md in learned-skills/, loaded between plugins and the owner's own skills, so a hand-written skill of the same name wins. It is Markdown only: the loader never reads its allowed-tools, and the tool refuses command lines and file includes, which /name would run or read. Writes ask like MemorySave unless skills.learn is auto; agents can turn a skill off but never delete one. A weekly Skill review template, added off, merges duplicates and retires unused or contradicted skills.

**The daily digest is code.** A routine with builtin: daily-digest runs in the hub instead of an agent session: the import service for the day's chats per online device, extraction and summaries where they are missing, and one small model call for conclave/daily/<date>.md through the grouped-notes writer. It is a suggestion rather than a template, so the Settings switch and the Suggested list make the same routine and show the same state. It replaces the session harvester, which read transcripts with an agent and its own rules.

Where it can fail: the facts check is English-only; SessionSearch ranks with BM25 and word coverage, so a paraphrase with no shared words finds nothing; project-scoped learned skills match by folder path, not project identity, so a skill made on the PC is global-only on the Mac; learned skills are not synced to other CLIs; OpenCode has no import reader, so the digest finds no OpenCode chats; the digest note needs a Basic Memory connection in the grouped layout. The real-model trial of the coder's skill rule ended without a save (its check was blocked by the trial's own allow list), and the line was moved into the report step without a second trial.

## 23. The daemon inside the desktop app

**Why.** The owner wants two installers: the hub, and the desktop app. Before this, a PC or Mac needed the desktop app for the window and a second, separate install for the daemon (the install script, a device code, `conclave daemon install`, then a systemctl or launchctl line). Now the app carries the daemon behind one switch, **Let the hub use this computer**, and pairing the app and turning on the daemon take one press. How to use it: `docs/INSTALL.md` section 5; the contract with the binary: `docs/design/DAEMON-SIDECAR.md`.

**A sidecar, and a copy the service runs.** The bundle carries `conclave-daemon` (Tauri `externalBin`), today the CLI's daemon commands compiled with `bun build --compile` from `packages/cli/src/daemon-main.ts`, one build per target, the x64 ones on Bun's baseline runtime so an older CPU runs it. The service never points into the bundle: an AppImage mounts somewhere new on every start, and an update replaces the bundle under a running daemon. The app keeps a copy in its data folder with a stamp of the bundled file (app version, size, time). When an update brings a different file, the app swaps the copy (a rename, which Linux and macOS allow under a running process; Windows renames the running exe out of the way first) and runs `install` again, which restarts the service. A daemon is never left on an old version once the updated app has started.

**One code, one press.** The switch is on the connect form, on the first time, with one line on what it allows. Connect pairs the app, then the daemon pairs with the app's own token: `POST /api/daemon/pairing` issues a short device code to an app that is already paired, checked against that app's token, and the daemon registers with it. The token reaches the daemon on stdin, never on the command line. The hub remembers which app asked, so the device is linked to the app: pairing again from the same app gives the same device a new token (its sessions and folders keep working), and revoking the app removes its computer. The owner token can sit in several apps, so it gets codes but no link.

**One place writes the service.** The Rust side has no unit files. It runs the binary's own `pair`, `install`, `uninstall` and `status --json` and reads their JSON and exit codes. The CLI builds the service from one pure plan per OS: a systemd user unit (values quoted, `%` doubled), a LaunchAgent (booted out and in again, retried while launchd lets go of the old one), or a Run key on Windows, where the daemon is a GUI-subsystem build that opens no window and logs to a file, with a pid file standing in for a service manager. The same plans serve `conclave daemon install` from the script, so a computer has one daemon either way. This is also why a daemon rewritten in Rust is a file swap: it only has to keep the contract.

**PATH.** An app started from the Dock or a menu has a short PATH, without Homebrew, nvm or `~/.local/bin`. The service gets the login shell's PATH (read between markers, since rc files print things), then the app's own, then the usual tool folders that exist, so git, claude and codex are found as in a terminal.

**Off means off.** Turning it off stops and removes the service, and the daemon asks the hub to remove its device with its own device token (`POST /api/daemon/unpair`), so the Devices page is clean without the owner's token. The app says whether the hub confirmed it. A hub that is down does not block it: the pairing here is forgotten and the app says to remove the device on the Devices page.

**The hub page cannot turn it on.** The app's window shows the hub's own pages, and they get a small IPC grant. They may read the state and open the app's settings page (Settings > This computer does that), but not turn the daemon on: a script on a hub page would then have a shell on this computer. The switch itself lives on the app's bundled page.

Where it can fail: a Linux desktop without a systemd user session (some minimal window managers) cannot start the unit, and the switch says so with systemctl's own words; the daemon runs only while you are logged in unless linger is on; a Windows Run entry does not restart a daemon that crashed until the next sign in; the login shell PATH is read once, at install, so a tool added later needs the switch off and on; an update only reaches the daemon when the updated app starts; the Mac copy loses the download flag, but an unsigned binary can still be stopped by stricter Gatekeeper settings. The installers, the Windows no-console build and the macOS and Windows services come only from the release workflow and have not run on a real machine yet.

## 24. Subscriptions through CLIProxyAPI

**Why.** The owner pays for Claude, ChatGPT and Google plans and wants their models in Conclave without API keys. Reaching them means each vendor's OAuth login, token refresh and request shapes, which move every few weeks. CLIProxyAPI (github.com/router-for-me/CLIProxyAPI, MIT) already does all of it for nine providers and is what the owner runs today for other tools. So the hub runs it as a sidecar instead of rebuilding it, and keeps "use the one you already run" a first-class mode (`models.cliproxy.mode`: off, builtin, external; off by default so existing hubs do not change).

**A pinned program, checked like cloudflared.** `packages/server/src/cliproxy/release.ts` holds the pin: version 8.0.32, and for each OS and CPU the archive's SHA-256 and size, copied from the release's `checksums.txt`. A download must appear in that checksums file with the pinned SHA-256, have the pinned size and Content-Length, contain a program for this machine, and print the pinned version from `-h`. It lands in `<home>/bin` next to its final path. There is no "latest": a newer CLIProxyAPI reaches a hub only through a Conclave update that adds its pin, and Update keeps the old copy until the new one has started, then rolls back if it does not. Linux uses the static no-plugin build because plugins stay off and it runs in the slim Docker image and on musl.

**Run like the tunnel.** The hub writes the config on every start (127.0.0.1, a free port kept across restarts when it stays free, its own auth folder at mode 0700, control panel and LAN discovery off, plugins and request logs off), gives it an environment of PATH, locale, certificates and proxy settings with HOME set to its folder, waits for `/healthz`, restarts it with backoff, stops it with the hub and stops one a killed hub left behind (pid file, matched on its own config path so the owner's other CLIProxyAPI is never touched). `MANAGEMENT_PASSWORD` in particular never reaches it, since CLIProxyAPI treats it as permission for remote management.

**Keys.** A random management key and client key live in the secrets store. The config file gets only the management key's bcrypt hash (CLIProxyAPI accepts a hash there), so the plaintext never sits in a file. The client key is in the config because CLIProxyAPI needs it there; the folder is the hub's alone, and LocalMachine refuses file tools, searches and shell commands that name it. That is a guard against a model reading it by accident or on a web page's say-so, not a wall against a script running as the same user.

**One provider, two wires.** The models appear under one id, `cliproxy`, so `cliproxy/claude-opus-5-5` works the same in builtin and external mode and as before for owners who had pointed `providers.cliproxy` at their own CLIProxyAPI. A runtime config layer of its own (`setRuntime(…, 'cliproxy')`, next to the remote access layer) holds the entry, so nothing is written to config.json. `ProviderConfig.anthropicWire` routes ids matching `claude-*` and `*/claude-*` to `/v1/messages`, so Claude keeps its thinking and cache control, and everything else to Chat Completions. The model list comes from `/v1/models`, then what each account's own list adds (section 48); a prefix such as `neu/` names one account and stays on the wire.

**Accounts and their order** (`core/src/accounts`, docs/research/2026-10-20-next-features.md 1, phases 1 to 3). Conclave decides, CLIProxyAPI executes. Each credential (keyed by its file name; `auth_index` may change across its restarts) and each native provider with a key is an account; `models.accounts` holds the owner's, any the hub finds join with defaults, and `models.routes` holds the order per vendor (optionally per model match), subscriptions before API keys unless moved. The hub writes `routing: fill-first`, session affinity and `session-affinity-rebind-on: quota` into the config, sends `X-Session-ID` on every request so a session keeps its account and its prompt cache, and writes each credential's `priority` from the order (an external CLIProxyAPI only once the owner set an order). The registry follows the same order, so `opus`, bare Claude ids and `anthropic/claude-*` go to a signed in plan while one has room and to the key when every plan is blocked; a 429 on the gateway moves the call to the next provider in the same turn. Per account windows (5 hours, week, week Opus, week Sonnet, Fable, budget, rates) come from the signals in `/credentials` every 60 s and from the plan's usage page every 5 to 10 min with jitter, again after a 429 and on Refresh, with backoff when the usage page answers 429. Those reads go through `requests/api-call` with `$TOKEN$`, so tokens never leave CLIProxyAPI, and only to three exact addresses (OAuth usage, OAuth profile for the plan, `wham/usage` for ChatGPT); `observability/usage/api-keys` is never read, its keys are raw API keys. An API key's budget (USD per month, week or day, reset day, hour and zone, warn at, hard stop) is summed from Conclave's own cost records, which now name the account on each usage row; the spend cap errors (`enforced_spend_limit_reached`, "You have reached your specified API usage limits") are quotas. CLIProxyAPI does not say which credential served a call, so a usage row's account for the gateway is inferred the way its session affinity binds. A plan's short name is its credential `prefix`: the owner sets it on the plan's row (`PUT /api/accounts/:id/prefix`, owner only), the hub checks it (1 to 24 lowercase letters, digits and dashes, no other plan's), writes it through `credentials/fields` (empty removes it) and reads the credentials and models again, so `neu/claude-opus-5-5` shows at once. The field suggests the part of the email before @, or the plan's name, and when two or more plans of one vendor have none a line at the top of Accounts asks for them, since without one Refusal fallback and the Window starter cannot pick a plan. Phase 4, the Router (soft skips, use before reset, cache aware stickiness), builds on `accounts/policy.ts`.

**Sign-in.** The hub asks the management API for the provider's sign-in address (`/v8/management/oauth/auth-url`, falling back to the v0 paths for older versions), the browser opens it, and the page polls the hub. Claude, ChatGPT and Google end by redirecting to a localhost port. When the request comes from the hub's own computer (a loopback peer with no proxy headers) the hub listens on that port on 127.0.0.1 for the length of the sign-in, takes only the path with the session's state, and posts the address to CLIProxyAPI. Otherwise one line under the row says the last page will not load and a box takes its address from the browser bar; the hub checks it is a localhost address with a code and the right state, and posts it as `redirect_url`. Grok, Kimi and Muse use device codes and need neither. The rows come from the running version's pin plus any plugin that adds a sign-in.

**What leaves the hub.** Status, accounts (provider, email or name, state) and model ids. Never a key, a token or a refresh answer (CLIProxyAPI's refresh returns the new tokens; the hub drops them). Log lines it keeps are scrubbed of both keys and anything shaped like a token. Sign in, remove, refresh, mode changes, updates, crashes and failures go in the audit log.

Where it can fail: providers change their OAuth apps and CLIProxyAPI follows within days, so a pin can go stale until a Conclave update moves it; a provider may treat use outside its own apps as against its terms, which is the owner's call; the localhost catch needs the provider's port free on the hub's computer (the paste box is the fallback); an external CLIProxyAPI needs `allow-remote` for sign-in from the hub; Android has no sign-in screen yet.

## 25. Harness round 2

**Why.** The harness review (`docs/research/HARNESS-REVIEW.md`) ranked the changes after its first six. This round built items 8, 9, 10 (WebFetch), 11, 12, 13, 16, 17, 18, 21 and 24. The benchmark (`bench/reports/2026-10-18-run2.md`) had Conclave at cost parity with Claude Code but one turn longer, so the cache, context and turn changes come first. Section 5 has the cache and context parts; this section has the rest.

**Calls that end.** MCP calls carry the user's stop and a per-server time limit (`mcpServers.<name>.timeoutMs`, default 120 s, reset by progress up to 5 times the limit). The runner stops waiting on a tool with a limit even when the tool ignores its signal.

**Instructions where the work is.** AGENTS.md, CLAUDE.md, CONCLAVE.md and GEMINI.md in folders below the session folder, and `.claude/rules` files whose `paths:` globs match, ride on the result of the first Read, Edit or Write under them, once per session (again after a compaction).

**Read state on the transcript.** Read, Edit and Write results record the file's path, mtime and a sha256 of its text. Edit and Write judge a file by the newest mark in context: a change that kept the mtime is refused, a touch that changed nothing passes, a Read a compaction dropped no longer counts, and a hub restart keeps the marks. Edit may change a file it never read when its old_string matches exactly (no whitespace or quote fallback) and a Read of that file would be allowed: the agent saw the text another way, usually `cat` in Bash, and benchmark run 4 lost a turn to this in 11 of 36 runs. A Read deny rule still blocks it, and Write still needs a Read.

**Background tasks.** A session that started a background subagent gets TaskList, TaskWait, TaskResult and TaskContinue over its children, read from the state subagents already keep. A child that was running when the hub stopped is marked lost at boot, and its parent hears so on its next turn.

**Limits.** Each session is a node of a tree, a subagent sits under its parent and a workflow agent under its run, whose budget is a node too. A node counts output tokens, cost, model calls and working time over its subtree, and is checked before each model step, outermost first. Past 80 percent an interactive session is asked once; at the limit the step stops. Limits come from a session's meta or from config (`limits.session`, `limits.routine`, `limits.subagent`); only routine runs have one by default (1,000,000 output tokens and 120 minutes). Working time leaves out waiting for a reset, an approval or an answer.

**WebFetch and cloud metadata.** The host is resolved once per hop, and cloud metadata addresses (169.254.0.0/16, fd00:ec2::254, 100.100.100.200, 168.63.129.16) and names (metadata.google.internal and similar) are refused on every hop. Plain http connects to the address that was checked. The LAN stays reachable, as before.

**Loop guard and final answer.** `session/loop-guard.ts` hashes each call (tool name plus key-sorted input) and its result. The same call and result 3 times in a row, or a cycle of 2 to 4 calls 3 laps long (A-B-A-B-A-B), adds a short note after the results telling the model it is looping. 5 in a row, 5 laps, or the same error 3 times halts: a subagent, routine or loop-mode turn stops at the first halt, an interactive turn after one last warning. A stop runs no more tools; it posts a "Loop guard stopped the turn" notice and then one final-answer call with `toolChoice: 'none'` asking what was done, found and left. The step limit (`limits.maxSteps` 250, `limits.subagentMaxSteps` 100, or `maxSteps`/`maxTurns` in the agent file) ends the same way, with a "Stopped after N steps." notice. So a subagent hands back a report instead of "(the subagent produced no final answer)". Each detection is logged; each stop writes a `loop_guard` audit row.

Where it can fail: the final-answer call is one more provider call, so a provider error there still leaves the turn without a report; the guard sees only calls with identical results, so a loop whose output changes each time (a timestamp in it) runs until the step limit; the summary template has not been through the compaction recall eval (review item 25); a log reducer can leave out a line that mattered, though the note names the id and the query mode; an MCP server that needs more than its limit must raise `timeoutMs`; ToolSearch adds a round trip, and each load changes the tool list once; a routine that needs more than its default limit stops with a notice until `limits.routine` is raised; https fetches keep the name instead of the checked address, which is safe for metadata services but not a general rebinding guard.

## 26. Sharing a session

**Why.** `GET /api/sessions/:id/export` returned the stored rows. The reminder blocks on user messages hold hook context and the memories recall injected, so an export meant for someone else carried the owner's memory, secrets from tool output and every absolute path. And for one Conclave to hand a session to another, the receiver needs to know which hub made it.

**The sanitizer** (`core/src/session/share.ts`, `redactMessages`) walks every block. It drops reminder blocks and reminder spans inside text, `meta.recalled`, reasoning signatures and encrypted reasoning, and thinking unless asked for. It runs the memory secret rules over text, thinking, every string inside a tool input and tool result text, but never over image or document data, signatures or ids, which the hex and high-entropy rules would mangle. Paths inside the session folder become relative, in `meta.path`, in diffs, in Bash commands and in text; the device's home and any `/home/<user>`, `/Users/<user>` or `C:\Users\<user>` become `~`. Private IPv4 addresses (10/8, 172.16/12, 192.168/16, 100.64/10), emails and the names of the hub's devices become `[private ip]`, `[email]` and `[host]`. Tool results and attachments can be swapped for short placeholders. Usage, cost and every other meta key stay home. A report counts what each rule took out, for a preview before sharing.

**Exports.** Markdown and JSON go through the sanitizer by default (`?thinking=1`, `?toolOutput=0`, `?attachments=0`). `?raw=1` is the stored rows as before, for backups only: the owner token, never a paired app, and the request is audited. The CLI (`conclave sessions export`, `--thinking`, `--raw`) and the TUI `/export` follow the hub. The JSON export is `{ format: "conclave-export", version: 1, session, messages, report }`, with only the shared session fields.

**Bundles.** `GET /api/sessions/:id/bundle` (owner and paired apps) returns `{ format: "conclave-bundle", version: 1, createdAt, from: { publicKey, fingerprint }, includes, report, sessions, project?, signature }`. Sessions are the root and the subagents it started, found through Task results' `meta.sessionId` (a result naming a session the root did not start is not followed). Each keeps its title, kind, mode, mode settings, chat switches, tags, times and its agent and model as hints; never its folder, device, project, external ids, meta, permissions, routine, task or cost. Messages keep role, kind, sanitized content, model, author, group, time and stop reason, with the original id as `meta.external.id`. With `?code=1`, edit diffs stay in tool results with relative paths and `project` carries the git roots, remotes, marker and head, without local paths or clone URLs. The hub key (`server/src/identity.ts`) signs `conclave-bundle-v1\n` plus the canonical JSON of the bundle without its signature (keys sorted, no spaces); core asks through a `BundleSigner`, so the key never leaves the server package. `verifyBundle` checks it with Node's `crypto.verify`, and against an expected fingerprint when the receiver knows the hub.

Where it can fail: the text rules miss what does not look like a secret (a password said in plain words, a name), and the device names are a word list, so a device called after a common word is left alone; a recalled memory the model repeated in its own reply stays; the receiving side is built for shares between friends (section 27), and a bundle file from elsewhere still has no import.

## 27. Friends

**Why.** One owner sends chats, sessions and messages to another owner's hub, hub to hub, with no service in the middle and nothing reachable without a friend's key. The spec and the phases are `docs/design/FRIENDS.md`. Phase 1, the friendship itself, and phases 2 and 3, sharing a chat or session and what the friend does with it, are built in `packages/server/src/peer`; messaging a friend's agents (phase 4) builds on the same envelopes, outbox and blobs.

**A key is the identity.** A friend is its hub key's fingerprint (section 14). An X25519 subkey in `<home>/peer-key.pem` (0600, not in backups), signed by the hub key, receives: each body is sealed to the friend's subkey with a one time X25519 key, HKDF-SHA256 and AES-256-GCM, and the associated data names both fingerprints, the message id and its type. Tunnels and proxies see ciphertext.

**Invite and request.** An invite is `conclave://friend?fp&url&alt&s&exp`, a 128 bit secret good for one hub for 24 hours, shown as a link and a QR code, with the hub's outside addresses only unless the owner asks. The friend's hub checks the key at `url` against `fp` (`GET /api/identity`), then posts a signed friend request with its key, name and address record. The secret never travels: the request carries an HMAC of both fingerprints and the message id keyed with the secret's SHA-256, which is all the inviting hub keeps. The request is the one message not sealed, because the requester has no subkey for the other hub yet; it holds nothing secret. At most 3 requests wait, 10 a minute per address, and wrong invites count like wrong pairing codes. Both owners see the same safety code (four groups of five digits from both fingerprints) and can mark a friend verified.

**Requests between hubs.** `/peer/v1/*` never goes through the token check. Each request is signed in the shape of RFC 9421 over method, path, query, authority, content digest and a `conclave-to` header with the recipient's fingerprint, and lives 5 minutes at most. The verifier checks the shape, the clock (a minute of skew), the recipient and the digest, then the friend's key and the signature, and only then records the nonce, so strangers cannot fill the cache. Every message is also an envelope the sender's key signs, so a message pulled from another hub's outbox is as good as one pushed. The inbox is idempotent by ULID: the same id again is a 200 and nothing happens.

**Outbox and pull.** A message waits in `peer_outbox` with its body until it is delivered. Delivery checks the friend's key at each address of its signed record in order, then PUTs what is due. An address that is never a friend's hub (loopback, link local, unspecified, multicast, broadcast, the cloud metadata addresses, or this hub itself) is refused, names resolved first, when a record, an invite link or Add by address brings it and again before each request; it is kept nowhere, and one audit line names it (FRIENDS.md, "Addresses a friend gives"). Same network addresses stay. A hub that does not answer gets the next try later, with backoff and jitter at most an hour apart, for 7 days; then the item fails and the owner hears, with Retry and Cancel. Meanwhile the friend's hub can pull it (`GET /peer/v1/outbox`, acking the ids it took and naming the ones it refused, which show as not delivered with the reason), which every hub does at start, every 5 minutes while friends cannot reach it (20 while they can), on Sync, and whenever a friend's hub reaches it. A sealed body over 256 KB goes as a content addressed blob the recipient fetches. Once delivered or cancelled a message keeps only its row (a note its text, for the thread), and other rows go after 90 days, so the outbox does not grow without end. Bodies between hubs are read only up to their cap, also when they come without a length. Address changes go to every friend as `address.update`; a list with no outside address does not replace one that had it, so a tunnel restarting does not strand friends.

**Remove and key changes.** Remove cancels the outbox, sends `friend.remove` best effort (a removed friend may still pull that one message, and nothing else), and refuses all later traffic. A friend's hub that answers with a new key at its stable or own address, without a `key.rotate` its old key signed, is blocked until the owner confirms; then what waited is sealed again for the new key. A rotation the old key signed is taken without a block, and the safety code is new.

**A friend's message is data.** A note lands in the inbox, emits `friend.message` and notifies (`notifications.on.friendMessage`). Nothing runs because of it. Grants start off except `receiveShares`. The audit log names a friend's hub as `friend:<fingerprint>`. A sent note keeps its whole text in the outbox. Read marks live on the hub, one per friend (`POST /api/friends/:id/read` with the newest note or share card seen, a time on the hub's clock that never moves back), so a note read on the phone is not new on the desktop; the friend's DTO carries `unread`, `unreadNotes` and `unreadShares`.

**Sending a share** (`peer/shares.ts`). The review (`POST /api/shares/preview`) runs the sanitizer of section 26 over the session and the subagents it started, up to a message when asked, with thinking, tool output (full, summary or none), attachments and code as chosen. Each value a text rule found is an item with a stable id (SHA-256 of the rule and the value), its count and the messages it is in; a keep list sends chosen values anyway (`RedactionLog` in `session/share.ts`). Code comes from the session's device (`session/share-code.ts`): by default the diff against HEAD, paths relative to the repository, without untracked, credential (`.env`, keys, `*.pem`, `id_rsa`, `*.tfvars`, `.npmrc`, the `.ssh` folder and the like) or binary files, and through the same text rules; a git bundle of the session branch only when asked, refused when a commit in its range touched a credential file. Send signs the sessions, the share's id, revision, title and note and the code as one bundle, seals it for each friend's subkey, offers it as a content addressed blob, and queues a small `share.offer` with the card and the blob's hash. Update is a new revision from the session as it is now (`share.update`); unsend withdraws the blobs, cancels offers not delivered yet and queues `share.revoke`, which asks the friend's hub to delete its copy.

**Receiving a share.** An offer is an Inbox card, "Alice sent 'Fix flaky auth test' (session, 42 messages, diff 12 files)", with `friend.share` and a notice. Nothing is fetched until the owner accepts; an offer not accepted in 30 days expires on both sides. Accept fetches the blob, opens it, checks the bundle's signature against the key that offered it and its shape, keeps it in `<home>/peer/shares/in` (0600), and answers `share.ack`. The view (`GET .../view`) is the bundle sanitized again (reminders, reasoning blobs and secrets out, framework tags defused, attachments only as inline data), each message marked as quoted data from the friend's hub, and checked again each time. From there (`session/friend-share.ts`):

- **Fork**: a new chat or session on this hub's models with the friend's turns stored as messages marked `meta.quoted`. A request carries a run of them as one `<shared-history>` user block naming the hub and its fingerprint (`session/quoted.ts`), so the model never takes the friend's assistant turns for its own; thinking and reasoning go. The fork guard (`meta.untrusted` with `meta.friendShare.guard`) holds through the first turn: every call asks even in bypass mode, "always" and "for this session" count once, hooks cannot approve, memory stays out. It keeps the agent's tools, unlike other untrusted sessions, because the owner started it. The next turn the owner starts with a message of their own lifts it (`friendGuardTurn`, called at the start of each turn), with a notice. The quoted turns are never read for memory.
- **Handoff**: a fresh session that starts from a brief built from the text (the note, the first and last asks, where it ended, the files), which the owner edits first. Guarded like a fork, since the brief quotes the friend.
- **Reference**: a session the hub never runs (send refuses it) and memory never learns from, left out of the daily digest, but found by past chat search and SessionRead as "shared by Alice's hub, quoted data", the friend's messages with the role `friend`.
- **Code**: `POST .../apply-plan` checks where it would land on a device and folder the owner picks (`git apply --check` on a temporary index, or `git bundle verify`) and names the new branch `from-<friend>/<title>`, and the files that can run code on checkout or build. `POST .../apply` with the plan's id, within 10 minutes, is the owner's approval: a diff becomes a commit through a temporary index and commit-tree, a bundle is fetched into the branch. Every git command runs with hooks off; nothing is checked out and the working tree stays as it was.

A friend's unsend deletes the kept copy and the references made from it; forks and handoffs are the owner's own work and stay. An unsend that comes before its offer is remembered for 30 days (1000 per friend), and the offer is dropped when it comes.

**Screens.** Settings, Friends (`web/src/features/friends`) says when friends cannot reach the hub and links to Remote access, holds a friend whose key changed until the owner confirms or removes them, lists requests both ways and friends with the short key, the verified badge and when their hub was last seen, and adds a friend by invite (QR code and link) or by a friend's link, pasted or scanned on a phone. A friend's page has the notes both ways and a composer, the safety code with Mark verified, Sync, the grant and Remove. The Inbox and its counts take in requests, key changes, notes and share cards not read yet, from the hub's read marks; the phone side panel lists Friends under More. Send to friend (the session and chat menus, the conversation sheet on a phone) picks friends, then shows the review the hub makes on every change, with each value found, its count, Show and Keep anyway. A share from a friend is an Inbox card with Accept and Decline, and `/shares/:id` shows it read only, quoted, with its diff and Continue as fork, Handoff, Use as reference and Apply code (plan, then approval); `/shares` and each friend's thread list shares both ways with Update and Unsend. The Android app has the same screens (`android/app/.../ui/friends`): Friends under More, a friend's page whose title opens the details, Shares, the friend rows in the Inbox and Send to friend in the conversation sheet. It reads the invite's QR code from the hub's SVG and scans a friend's with the camera.

Where it can fail: a friend reaches the hub only through a tunnel or an own URL (Tailscale serves only the tailnet; Settings and `GET /api/friends/reachability` say so), though a hub nobody can reach still pulls; when neither hub can reach the other, messages wait 7 days and fail; quick tunnels move, and a friend that was away for both moves has only the old address until a pull or a new invite; a hub key cannot be rotated from the app yet, so `key.rotate` is only received and built, not offered. Shares: the review lists only what the text rules find, so a secret in plain words goes unless the owner sees it; a secret kept anyway is redacted again on the friend's hub; a diff applies only on the commit it was made against (no three way merge), a git bundle only where its base commit is, and binary files never go in a diff; applying code needs a POSIX shell and git on the device (a Windows device is not tested); a sender whose hub key changed between the offer and the Accept has to send an update, because the bundle no longer checks out against the key that offered it.

**Adding by address and shared projects.** Why: the owner wanted to add a friend with just their hub's address and email, then share a project with them: its context, chats when they choose, and code through GitHub. Adding by address sends a signed `friend.request` with no invite and `via: "address"`, holding a name, the hub key and the address record only; it waits in the friend's Inbox like any request. The friend's hub takes it while its owner allows requests by address (on by default), at most 5 waiting apart from the 3 for invites, 3 an hour per network address and 20 a day, 16 KB at most, never from a blocked key or one declined in the last 30 days, and answers all of those the same way. The email stays here; when a request cannot go it carries an invite in a `mailto:` link. A shared project (`peer/projects.ts`) is a star around the owner's hub: `project.invite|join|leave|meta|item|state|sync` go through the outbox like every peer message, each hub keeps its own copy, and every item (a note, a memory the owner picks, a chat sent as a phase 2 share without code) is signed by its author's hub key, so the owner's hub passes it on unchanged and every hub checks it again. Only the author edits an item; an edit is the next version and the last 50 versions stay, an older one dropped on each write and never sent on. Secrets come out before an item is signed. This hub's agents read a project through the SharedProject tool, the owner's notes plain and each friend's in a `<friend-shared-context>` fence naming their hub, framework tags defused and secrets out again. Code stays on GitHub: the project page lists each member's open pull requests and branches with this hub's token, and starts repo sessions from the same repository. The spec, the limits and the messages are `docs/design/FRIENDS.md`, "Add a friend by address" and "Shared projects as built".

Where it can fail: a request by address is trust on first use, so a hub that answers at the address with another key is taken at its word until the owners compare the safety code; the per address limit sees the address the request came from, which behind a shared proxy or tunnel is one for many people; a stranger can still fill the 5 waiting places for a while, though not a friend's invite places. In a shared project a chat reaches only members who are its author's friends, and a member who joins after the author's payload is gone (30 days) never gets it; members hear each other only through the owner's hub; a removed member keeps their copy and their items stay with everyone else; the code view knows a member by the GitHub login their hub shared on join, so a hub without a token shows its pull requests under Others; the fence keeps a friend's words marked and inert as framework text, but a model can still be swayed by plain prose inside it, which is why the tool never goes to untrusted sessions and nothing a friend sent runs on its own.

## 28. File conflicts and stuck agents

**Why.** The AOS dashboard, a read-only monitor for Claude Code, warns when two agents edit the same file and when an agent stops making progress. Conclave runs many chats, subagents and workflow agents at once and said neither. The code is `packages/core/src/alerts`.

**File conflicts.** The hub keeps, per device and absolute path, which session wrote a file and when. It learns this from the write tools (Write, Edit, MultiEdit, NotebookEdit) through a runner extension, and from the edits an ACP harness reports with its tool results. A write on a file that another live session wrote in the last 10 minutes is a conflict. Live means running now, or with a turn that ended in the last 10 minutes. The result of that write gets one line for the model: "Another chat, 'Fix login', changed this file 3 min ago." It comes once per new write of the other chat, so a run of edits does not repeat it. The Inbox gets one item and a notification (`notifications.on.fileConflict`) per pair of sessions and file per 10 minutes: "'Fix login' and 'Refactor auth' are both editing src/auth/redirect.ts", with links to both and Dismiss. Another conflicting write updates the open item instead of adding one.

- A subagent and the session that started it, at any depth, never conflict.
- Two sessions of one tree (two workflow agents, two background subagents) conflict only while both run. The parent hands out the work, so one agent after another on the same file is the plan, not a clash.
- Agents in their own git worktrees write other paths, so they never meet.
- With `permissions.onFileConflict: "ask"` the conflicting write asks for approval instead, even in bypass mode. It asks once per pair and file per 10 minutes; a denied write asks again next time. The approval is the Inbox item, so no alert is added.

**Stuck turns.** The hub watches the event stream. A running turn with no progress event (streamed text or thinking, a tool call starting or ending) for longer than its threshold raises one Inbox item and a notification (`notifications.on.stuck`): "No progress in 'Fix login' for 6 min", with Stop and Keep waiting.

- The threshold is 5 minutes (`limits.stuck.minutes`), with overrides per model ref or per provider (`"ollama/*"`) in `limits.stuck.models`. 0 turns it off.
- A tool that still runs inside its own time limit (Bash's timeout, an MCP server's limit) does not count. Tools that wait on other work (Task, Workflow, TaskWait, AskUserQuestion) never do; the subagent behind a Task is watched as its own session.
- Waiting on an approval or a question is not stuck. The clock starts over when the turn runs again.
- Keep waiting doubles the threshold for the rest of the turn. The doubled wait counts from the answer, so an owner who answers an hour late is not flagged again on the next check.
- The same tool failing with the same error 3 times in a row in one turn is a loop, with its own item. Keep waiting there waits for twice as many failures. The loop guard (section 25) tells the model; this tells the owner.
- An item clears itself when progress comes (for a loop: another outcome) or when the turn ends. The check runs every 15 seconds.

**Clients.** `GET /api/alerts`, and `POST /api/alerts/:id` with stop, wait or dismiss. `alert.raised` and `alert.cleared` ride the event stream, and a notice carries `alertId` so an open Inbox leaves its toast out. The web Inbox lists alerts next to approvals and questions, with an Alerts filter; the Android Inbox has the same rows. `liveAlerts(engine)` in `core/src/alerts/attached.ts` reads the live state for the Map view: stuck sessions since when, and pairs of live sessions on one file, whatever the owner dismissed.

Where it can fail: alerts live in memory, so a hub restart drops them with the turns they were about. A file changed by Bash (sed, a formatter, a git checkout) is not seen; only the write tools and harness diffs count. A harness that reports no diff is not seen either, and a harness write can neither ask first nor carry the line, since the harness owns its context. One folder under two paths (a symlink, a bind mount) does not match itself. The loop rule compares error text, so an error that names a changing value (a time, a temp path) never repeats. A long compaction counts as no progress.

## 29. Map

**Why.** The owner saw the live graph in the AOS dashboard (github.com/tomtomsatnav/agent-orchestration-standard, MIT) and wanted the same in Conclave, in Conclave's own look: one page that shows everything the hub is doing, with work visibly flowing. AOS was read for ideas on the layout, the streams and the drawer; the code here is our own.

**What it shows.** `/map`. The hub's knot sits in the middle and says the hub's state: written in violet while something runs, lit along the knot while a tool runs, frozen in amber while something waits on you, a grey stub while the hub is offline. Devices branch off it (a small square, online in green), projects and folders off their device, or off the hub for work on the hub itself and the chats. Every chat, session, subagent and workflow agent of the last 24 hours is a dot: violet while it runs, amber while it waits on you, the fault color when it failed, quiet grey when idle or done (done is hollow), a hollow ring when a limit paused it. A workflow run is a diamond with its agents around it. Each label is the title, then a short id and the state word. The header line counts what runs and what waits, then the tokens and cost of the day. A click opens the node's details (a side panel on desktop, a sheet on phones): state, agent and model, device and folder, what runs now and for how long, the last five tools with their target and duration, usage (in, out, cache, cost, tokens a minute, run time), subagents, and Open chat and Stop. The top bar has Map (under More below 1200 px); phones have it as the first row under More, full screen with pinch and drag.

**The snapshot.** `GET /api/map` (`core/src/map/snapshot.ts`) reads the sessions touched in the last 24 hours and builds each node in a few grouped queries: the last message times, usage sums, the latest turn, open approvals, and the tool blocks of the last 24 messages (read with SQLite's JSON functions, so big tool results are never parsed in JavaScript). Live, a node's state is its session status plus the engine's open approvals and questions. A workflow run's host session is left out and its agents hang off the run. Groups are a project per device, a folder without a project, or the chats. Past 80 nodes, everything live stays with what it hangs off, then the most recent.

**Deltas.** `MapLive` (`core/src/map/live.ts`) follows the event bus and sends `map.delta` at most twice a second: the token rate (from the streamed text at about four characters a token, smoothed with a 3 second time constant so the streams speed up and slow down instead of flickering), the tool that started, the tools that ended with their durations, usage totals, and whole nodes when one starts or its status changes. A socket asks for them with `{type:'map', on:true}` (the client's `setMap`, kept across reconnects); with no socket asking, nothing is built or sent. Like other deltas they stay out of the replay buffer and are the first thing a slow socket skips. After a reconnect the page loads the snapshot again.

**Replay.** `GET /api/map?at=<time>` (epoch ms or ISO, within 24 hours) runs the same builder on stored rows only: a session ran when a turn spans the time (a subagent between its first and last message, a workflow agent between its call's start and end), it waited when an approval was open then or its open tool was AskUserQuestion, and usage counts only rows up to then. The scrubber under the map moves through the day; Live comes back.

**Layout.** `features/map/layout.ts` is pure and tested on 300 random hubs: no mark or label touches another. The hub's children stack in bands left and right, balanced by rows, and each subtree grows outward in columns. Every leaf gets a row of its own and a parent sits at the middle of its children, so rows never collide; a node with children carries its label above it, a leaf beside it on the outer side. Rows spread apart until the map is about the shape of the screen, and each side bends gently around the hub, less when a bend would make two things touch. Labels are measured at their widest state word, so a state change never moves the map. Phones put everything on the right of the hub in tighter columns, and open at zoom 1 on the hub and its busiest project (most running and waiting, then most agents) so every label reads at 12px or more (the short id and a conflict's file name are 12px there, not 11); when the two are wider than the screen the hub's side stays in view, a map that fits whole at that zoom opens whole, and Fit shows all of it (`view.ts` startView, tested in `map-layout.test.ts`).

**Streams.** `features/map/streams.ts` keeps particles in typed arrays on one canvas. A running node emits at a rate that follows its tokens a second (a tool or a request in flight still trickles), and each particle follows the curved link to its project and on to the hub, where it fades. A tool call sends one bright pulse the whole way. Lanes narrow at every node so the streams gather there. Full, Quiet (a third) and Lines (no particles; working links are tinted) are a switch remembered per device; reduced motion is always Lines. The draw measures its own frame time and lowers the share of particles when frames get slow, and the loop stops when nothing moves and in background tabs.

**Alerts.** A node's `stuckSince` draws a dotted amber ring and "No progress 6m" in its label; the snapshot's `conflicts` draw a dashed link in the fault color between two agents with the file's name on it. A live snapshot takes them from the alerts of section 28 (`liveAlerts`), and the page loads the snapshot again when an alert comes or goes; a replay has none, since alerts live in memory. The web mock fills both with `?alerts=1`.

Where it can fail: the token rate is an estimate from characters, so a provider that sends large chunks makes the streams pulse; a session that ran on another hub before an import has no turns, so a replay guesses its span from its messages; an approval the hub never closed (it stopped) counts as answered once the session went on; a hub with more than 80 recent nodes leaves the oldest finished ones out; on a phone the map opens on the hub and its busiest project with labels at their set size (12px and up), so the rest of a larger hub is a drag or Fit away. The map's screenshots use the mock's map data on the demo hub. Android draws the same map on a Compose Canvas (Map, first under More) from a port of the layout, the start view and the streams in `:client` (`client/.../map`), tested like the web's.

## 30. Repo sessions

**Why.** Claude Code on the web starts from a GitHub repository, works on a branch of its own and ends in a pull request, with nothing to set up on a laptop. The owner wanted the same on their own hub, with their own models and devices. The code is `packages/core/src/github`; the contract is `core/src/client/github.ts`.

**The token.** A fine-grained token is the hub secret `github` in `secrets.json` (Settings, GitHub, or `conclave github login`, which reads it hidden or from stdin), else `CONCLAVE_GITHUB_TOKEN`. The hub checks it with `GET /user` before it keeps it, and a token GitHub refuses is not saved. It needs Contents read and write, Pull requests read and write, and Metadata read. Settings shows who it is and lists the repositories it can see, with a search. `GET /api/github` never returns the token.

**Where the token goes, and where it never goes.** Only two things use it. API calls run in the hub process with the token in the Authorization header. Git commands that reach GitHub (clone, fetch, push) run on the session's device through its Machine, the hub's own or a paired one, with the token on that one command's stdin. The script moves stdin to fd 3 and gives every command /dev/null; a credential helper passed with `git -c` answers `get` for the expected host only, with the line it reads from fd 3. Fetch and push run in a fresh bare repository in a temp folder that borrows the clone's objects (`GIT_OBJECT_DIRECTORY`), with `GIT_CONFIG_GLOBAL=/dev/null` and no system config, so the clone's own config, which the agent can write, never reaches a command that holds the token: no `url.insteadOf`, credential helper, proxy or hook planted there can see it. Hooks are off, redirects are not followed, only the configured scheme is allowed, and trace variables are unset. Nothing puts the token in an argument, a variable, a file, a URL or a log; text that leaves the module has it replaced with `***`. The agent's shell is another process tree, the hub's `CONCLAVE_*TOKEN` variables never reach it, and `secrets.json` is now out of reach of tools like the CLIProxyAPI folder: reads, writes, searches and shell commands that name it are refused (`machine/private.ts`). That guard now also reads the Bash tool's command, which it hands over in `__CONCLAVE_CMD`, and a background shell's arguments.

**Clones and worktrees.** One clone per repository per device. The hub takes, in order: the clone it made before, a folder the projects service (section 17) knows for this repository on that device, `~/repos/<owner>/<repo>` when it is already a clone, else a new clone there (`github.reposRoot` moves it). A folder that is there but holds something else is refused, not overwritten. Fetch and push always use the address `<gitUrl>/<owner>/<repo>.git`, never the folder's own remote, so a clone whose origin is SSH works the same. Each session gets a worktree under `~/.conclave/worktrees/gh/<owner>/<repo>/` on a new branch `conclave/<slug>-<four letters>`, made from the base fetched fresh just before (the default branch, or one the owner picks) and kept under `refs/conclave/base/`. The session's folder is the worktree, and the projects service learns it as a folder of the repository's project at once, so checkpoints, the write gate, file conflicts and the Map treat it like any session folder. A line in the transcript says where it works, and a note on the first message tells the agent to commit on its branch and not push itself.

**Push and pull request.** Push, Open pull request and Clean up are hub actions: routes under `/api/sessions/:id/repo`, buttons in the apps, `conclave sessions push|pr|cleanup`, and the PullRequest tool for the agent. The tool goes only to repo sessions, never to subagents or untrusted sessions, and asks the owner itself on every push and every pull request, in any permission mode, with no "always allow", so no rule, mode or hook answers for the owner. A push sends the session's branch commit to the same branch name and nothing else: the refspec has no `+` and there is no `--force`, so a branch GitHub moved is refused with a sentence, and a branch that is the default branch or not under `conclave/` is refused before git runs. With a commit message, files not committed yet go in a commit first, with the device's git identity or the GitHub login, and the message ends with the trailer `Committed-by: Conclave (<session model>)`. No AI is ever an author or a `Co-authored-by`, so none shows up as a GitHub contributor; GitHub does not read `Committed-by`. Open pull request pushes first, then opens it with a title and body drafted from the session (its title or the one commit's subject, the last answer with the worktree's paths made relative, and the commits), which the owner edits. A pull request opened on github.com for the branch is adopted. The hub reads the pull request and its checks (check runs and commit statuses as one state) every `github.pollSeconds` (120) while it is open, at Check now, and before a Clean up. A change to merged or closed is a line in the transcript. Sessions carry a summary in `meta.repo` (repository, branch, base, pull request, checks, cleaned), so lists show the repository and branch without another request.

**Clean up.** After a merge or close, Clean up removes the worktree; the branch stays on GitHub and is never deleted there. The local branch goes too when GitHub has it as it is. Uncommitted files, or a pull request still open, need force. Archiving a repo session offers Archive and clean up. Deleting a session removes its worktree when nothing in it is uncommitted.

**Apps.** Web: Settings, GitHub; on Home, Session (Code on a phone) gains From GitHub, a searchable repository and the branch to start from, on the hub unless another device is picked; a line under the session's header says where the branch and the pull request stand, with the actions. Phones: the Where should it work? sheet has Folder and GitHub, the options sheet has the repository and branch, one action sits over the composer, and the conversation sheet has the rows and the rest. Android does the same as the web on a phone: Folder and GitHub in the Where should it work? sheet, one action over the composer, and Push, Open pull request, View pull request, Check now and Clean up in the conversation sheet. CLI: `conclave github login|status|repos|logout`, `conclave sessions new --repo owner/name [--base main] [--device x]`, and push, pr, cleanup and repo.

Where it can fail: the hub's user can read what the agent can, since tools run as the same user, so the guard on `secrets.json` stops a mistake or a web page's instruction, not a script that tries hard (the same as the CLIProxyAPI folder); while a git command runs, a process of the same user could read its fd 3. Git over SSH is not used, so a token is required even where the owner has SSH keys. A repository with Git LFS gets pointer files in the clone, since the hub does not fetch LFS objects. Paired devices need a POSIX shell, `mktemp` and git 2.32 or newer (`GIT_CONFIG_GLOBAL`); Windows devices are not supported. A fine-grained token without Commit statuses read shows no checks on a private repository. A branch someone else pushed to cannot be pushed again from the session; the session has to take their commits first. The poll reads at most 20 open pull requests per round.

**Run in a worktree (any git folder).** Why: the owner wanted several agents on one repository at once without them clashing, for any git folder on any device, not only GitHub repositories. With the toggle on (web "+" menu and phone options, Android's "+"; shown only when `GET /api/worktrees/folder` says the folder is in a git repository), `POST /api/worktrees/sessions` makes the session through the same repo session code: a worktree under `~/.conclave/worktrees/dir/<folder name>-<8 hex of its path>/` on that device, outside the repository so tools never see nested copies and refused under a Syncthing folder, on a new branch `conclave/<slug>-<four letters>` from the folder's current branch HEAD. The row in `repo_sessions` has `source = 'folder'`, the repository's top folder as its clone, the base branch and base commit; `repo` is owner/name when the origin is on GitHub (Push, Open pull request and the PullRequest tool then work as above), else the folder's name. The header line shows the branch, commits ahead and uncommitted files. Merge into the base (`POST /api/sessions/:id/repo/merge`, `squash` optional) runs in the main checkout and is refused while the worktree or that checkout has uncommitted tracked changes, or that checkout is on another branch; a conflict is undone with `git reset --merge` and refused with a sentence. Clean up is offered after the merge and removes the worktree and the branch. Discard (`cleanup` with `discard`) removes both, merged or not; the apps ask first and say what is lost, and uncommitted files need force. The worktree-add and merge steps are `addWorktree` and `mergeBranch` in `workflows/worktrees.ts`, which workflow `isolation: 'worktree'` calls use too. The file-conflict warning is per absolute path, so sessions in different worktrees never warn each other.

Where it can fail (worktrees): a folder on a detached commit or with no commits is refused, since there is no branch to merge back into. Merge does not run the repository's hooks (hooks are off for the hub's git commands). Workflow merges are now refused into a checkout with uncommitted tracked changes too. Untracked files in the main checkout that a merge would overwrite make git refuse, and the hub reports git's words. A squash merge's commit ends with the `Committed-by` trailer like a push commit. The base branch must exist on GitHub for Open pull request.

## 31. Maps

**Why.** The owner wants the assistant to find places, say how long a trip takes and when to leave, and show a map in the chat. The code is `packages/core/src/maps`, the tools `core/src/tools/maps.ts`, the routes `server/src/routes-maps.ts`, the cards `web/src/features/maps`.

**Two providers behind one service.** Google Maps Platform has ratings, opening hours, public transport and traffic, and needs a key with billing. OpenStreetMap needs neither: Nominatim for search and addresses, OSRM for routes, tiles for map pictures. When this was built the owner's Google billing setup failed (OR_BACR2_59), so OpenStreetMap is the default until a Google key is saved, and Settings > Maps picks one. Both answer the same four tools and fill the same cards. A card leaves out what its provider does not have: stars, open now, price and transit are Google only.

**Tools.** PlaceSearch (text, or a type around a point), PlaceDetails, Directions (from, to, mode, departAt or arriveBy) and MapImage (markers, a route id from Directions, size). They only read, so they never ask. The assistant and the chat agent have them; untrusted agents never do (UNTRUSTED_DENY), so a web page can neither spend the quota nor learn where home is. A chat with web search off has no maps either. The model gets short text with ids and a line saying the owner sees a card; `meta.maps` on the result carries the card for the clients.

**The key stays on the hub.** It is a hub secret, `providers["google-maps"]` in secrets.json, written by `conclave secret google-maps` or Settings > Maps; `GOOGLE_MAPS_API_KEY` in the environment works too, and tool shells never inherit it. Places and Routes get it in the X-Goog-Api-Key header; Geocoding, Time Zone and the Static API in the query string of a URL built at call time. Results, cards, errors and log lines are scrubbed of it. A map image is kept as a spec (size, markers, the route line), never as a URL: `GET /api/maps/image/:id` fetches the PNG from Google, or draws an SVG from OpenStreetMap tiles, on the hub, and sends only the picture, with the hub token like any call. A refused Google key answers 502, so an app never reads it as a bad hub token and signs out.

**Free tier and politeness.** Field masks ask Places and Routes only for what the cards and the model use: name, address, location, rating, hours, link and price; duration with and without traffic, distance, the line, the ends and the transit lines. A daily cap per hub (`maps.dailyCap`, default 300, 0 turns maps off) counts every outbound call; a cache hit does not count. Each day's count is a kv key (`maps.usage.<date>`), and a day's first call deletes every one older than a week. The cache is small and in memory: searches 10 minutes, routes 5, details an hour, addresses a day, pictures an hour. Nominatim and OSRM get at most one call a second each, with a User-Agent that names Conclave and the owner's contact email (`maps.osm.email`, required for the public servers). Tiles load two at a time and stay on disk for a week, and every picture carries "© OpenStreetMap contributors".

**Errors in plain words.** Google's reasons become sentences: billing off, key restricted to other APIs, API not enabled, key only for some sites or addresses, bad key, quota. OpenStreetMap's: refused, no route, no contact email. The Test button makes one call per API and shows each answer.

**Leave by.** For the day's calendar events with a place, the hub works out the trip from home in the default mode, arriving at the start: "Leave by 17:40". DayPlan's text ends with these lines, so the morning brief has them, and Home's Today lists them. Calendar data comes only through `CalendarPort` (`maps/leave-by.ts`). Until a calendar module calls `setCalendarPort(engine, port)` the stub has no events and nothing shows.

**Clients.** The web draws a place card (name, rating, open now, address, Open in Google Maps, Directions), a route card (time, mode, leave-by, distance, lines) and a map card. On a phone a turn's tool calls fold into one line and the cards sit under it. Links open Google Maps or Apple Maps by coordinates (`maps.links`). Android draws the place and route cards, with Open in Maps as a geo: link any maps app takes, and the map card: a PNG as it is, the OpenStreetMap SVG read into shapes and tiles on a Canvas.

Where it can fail: the public OSRM demo routes cars only, so OpenStreetMap walking and cycling times come from the road distance at 4.8 and 15 km/h unless foot and bike routers are set; OpenStreetMap has no transit, so transit becomes a walk with a note; Nominatim finds kinds of places less well than Places; each leave-by time is one routes call and needs a home; a picture viewed more than an hour after it was made is fetched again and counts toward the cap.

## 32. Calendar and mail

**Why.** The assistant is modelled on Meta's Muse, which schedules workouts, plans meals, finds meeting times and books them, blocks work time and reads mail. Before this, calendar and mail came only through catalog MCP connectors (Google Workspace, Microsoft 365), so the morning brief could not count on a calendar and nothing knew which writes were safe. The owner syncs one set of calendars to Nextcloud, iCloud and Google and wants Gmail and Outlook to sign in like claude.ai does. Now the hub has its own calendar and mail, and every write is a proposal the owner approves.

**Accounts.** Settings, Calendar and mail (`/api/pim`, `core/src/pim/`):

- **CalDAV** with an app password: Nextcloud (`https://<host>/remote.php/dav`), iCloud (`https://caldav.icloud.com`), Fastmail (`https://caldav.fastmail.com/dav/`) or any server. Discovery finds the principal (the address given, else `/.well-known/caldav`), the calendar home, the scheduling outbox and the owner's address, and keeps the collections that hold events. Google is not a CalDAV preset: Google ended password access to CalDAV (DAVx5's notes say June 2023 for CardDAV, and app passwords have not worked for Google CalDAV since), so Google Calendar comes with Sign in with Google.
- **Sign in with Google**: Gmail (`gmail.readonly`; `gmail.compose` only when the owner turns on drafts) and, if wanted, Google Calendar (`calendar.readonly`, plus `calendar.events` to propose events) through the REST APIs, OAuth 2.0 with PKCE. Which client: the project's shared Desktop app client (`mail/oauth-clients.ts`, `docs/design/OAUTH-APPS.md`) with a loopback redirect, from a browser on the hub machine (the hub's own `http://127.0.0.1:<port>` callback) or from the desktop app (its own loopback, then it hands the code to the hub); the shared iOS client from the phone's system browser with the app's custom scheme, the phone handing over the code or a refresh token; or the hub's own Web application client with the hub's https address (a tunnel, an own domain, a ts.net name); or the project's shared Web application client through the relay, from any browser, the desktop app or a phone with no setup and no https address: its one redirect URI is a static page on the project site (`https://conclave.kaivalyaahir.com/oauth/google/`, `site/oauth/google/`), the state carries the hub address the page uses (`<random flow id>.<base64url of the callback>`, checked against the hub's own addresses and the request's origin), and the page shows "Finish signing in to Conclave at <host>" and sends the code on to exactly `<origin>/api/pim/oauth/google/callback` only when the owner presses Continue. Settings picks, in order: the hub's own Web client at its https address, the relay when the shared Web client is set, loopback on the hub machine, else loopback with the `127.0.0.1` address pasted back. The shared Web client's secret ships like the Desktop one: PKCE on every sign-in with the verifier only on the hub, the redirect fixed to the relay at Google, a click and the host shown before any code moves, so the risk is the same as the Desktop client's (`docs/design/OAUTH-APPS.md`, The relay). Google refuses plain http redirects other than loopback and does not allow Gmail scopes in the device flow, which is why there is no device code for Google.
- **Sign in with Microsoft**: Outlook.com, Hotmail and Microsoft 365 mail through Graph (`Mail.Read`, `Mail.ReadWrite` only for drafts, `Mail.Send` only for sending, `offline_access`), the device code flow from any device with a multi-tenant public client. Outlook.com no longer allows IMAP with a password, so this is the only working path there.
- **IMAP** with an app password for every other provider and for Gmail without a Google client (iCloud, Fastmail, Gmail, Yahoo presets). Read only: `EXAMINE` and `BODY.PEEK`, so nothing is marked read. Drafts go in with `APPEND` to the folder marked `\Drafts`. SMTP (465 or STARTTLS on 587, never a password in the clear) only when the owner turns sending on.

Passwords, refresh tokens and the hub's own client secrets are hub secrets (`secrets.json`, mode 600), read only at the moment a request goes out; access tokens live in memory and refresh a minute early, one refresh at a time per account (Microsoft rotates its refresh token, so the new one is stored). Nothing secret is in kv, in `/api/pim`, in a tool result, in a transcript or in a shell's environment. Disconnect revokes at Google; Microsoft has no revoke for one app's token, so the hub forgets it and the page says where to remove the app's access. Each calendar has Read and Write switches; writing needs reading and a calendar the server lets the account write.

**Reading.** CalDAV is written out over fetch (`calendar/caldav.ts`): PROPFIND, calendar-query with a time range, GET, PUT with `If-None-Match: *` for new objects and `If-Match` for changes, DELETE, and the outbox POST for other people's free/busy. Redirects are followed by hand so Basic auth only goes to the provider's own hosts (`caldav.icloud.com` to `p42-caldav.icloud.com`) and never downgrades to http. XML is read by namespace, not prefix (`calendar/xml.ts`). iCalendar goes through **ical.js 2.2.1** (pinned, MPL-2.0, no dependencies), because RRULE expansion with overrides, EXDATEs and VTIMEZONEs is where hand parsers break. Each occurrence is turned into an instant through its own zone: an IANA TZID (also inside Mozilla-style paths, and the common Windows names) through Intl, else its VTIMEZONE, floating times in the owner's zone; repeats step in wall time, so a weekly 18:00 stays 18:00 across a DST change. A wall time the clocks pass twice is the first one, and one they skip takes the offset from before the change (RFC 5545). Overrides (RECURRENCE-ID) and EXDATEs find their occurrence by the instant they name, not by clock text, so one written in another zone than the series (UTC, or London for a New York series) still takes its place, and a change or a delete of that occurrence replaces it instead of adding a second. A series is cut off at the range and after 50,000 steps. All-day events block time only when marked busy; cancelled and free ones never do. Google Calendar expands repeats itself (`singleEvents=true` in the owner's zone). Reads are cached 90 seconds per calendar and range.

**Free/busy and suggestions.** `calendar/freebusy.ts` merges busy blocks over the readable calendars and the attendees whose calendars an account can see (Google's free/busy API, or a CalDAV server's outbox for its own users), cuts the free slots inside a daily window ("08:00-20:00", weekdays only on request), and picks up to three meeting times: the earliest fit per day first, then later ones an hour apart. Attendees nobody can see come back as unknown; the model asks them and passes their busy times back in.

**Proposals.** `CalendarEvent` (create, update, delete; for a repeating event one occurrence or the series) and `MailDraft` never write (one exception: with the account's `autoDraft` setting, Save drafts without asking, on, a `MailDraft` that is not `send: true` is stored and applied at once through `approve`, saving a draft with no card and no notification. It never sends; `send: true` always waits for a card, plan mode and an account without Drafts on still get a card, and the email agent never has `MailDraft`. A draft saved this way can come from text in a message the email agent reported, so with the setting on the owner reviews Drafts before sending; nothing is ever sent without approval). They store a proposal in `pim_proposals` with exactly what will be written (for an event the title, time, calendar, account, location, attendees and whether the server sends invitations; for a message the account, to, cc, subject and body) and return. The owner gets a notification and a card on Home's Today (web), `/today` (phones) and the Android Today screen, with Approve and Decline. Approve claims the row (two taps cannot write twice), writes it once and stores the result or the error; a change re-reads the event and writes with its ETag, so an edit made elsewhere fails instead of being lost. A change keeps what the proposal does not cover (alarms, the free mark, other apps' lines, attendees' answers, notes longer than a proposal carries), and a change to a whole series made from one occurrence moves the series by the same step in its own zone, so its earlier weeks and its count stay. A write the hub stopped in the middle of fails at the next start with a word to check, and is never tried again. A decided proposal (applied, declined or failed) is deleted 30 days after the decision, at start and by a daily job, for every account; a pending one stays until the owner decides. The session hears the outcome as a note before its next turn and as a line in its transcript. This holds in every permission mode, under any allow rule and in unattended routines, where an ordinary approval would be refused; so the tool call itself asks nothing and counts as read-only. Sending a message needs both the account's Sending switch and `send: true` on the proposal; saving a draft is the default.

**Mail stays untrusted.** `MailSearch` and `MailRead` are opt-in tools that refuse to run outside an untrusted session. The new built-in `email` agent (untrusted, `tools: [MailSearch, MailRead, TodoWrite]`, the small model) is the only agent that names them, so mail text reaches a model only there, wrapped in `<untrusted_mail_content>` with framework tags defused, under the untrusted rules of section 10 (every call asks unless a routine allow rule covers it, no memory, no other tools). The assistant asks it with Task and gets its report, defused again. `CalendarList`, `CalendarFreeBusy`, `CalendarEvent` and `MailDraft` join `UNTRUSTED_DENY`, so neither the email agent nor anything it starts can touch the calendar or draft a message. Event text from calendars (invites from strangers) is defused and labelled as data in tool results.

**The assistant.** `DayPlan` includes the day's events, the proposals still waiting and which mail accounts exist; with `guide` it returns how to run plan my week, a meal plan, a meeting or time booking (`agents-defaults/guides/flows/`, short prompt files like the life-area guides). The morning brief reads the calendar through DayPlan, asks the email agent about unread mail from people, and proposes its focus block; installed copies of its old prompt upgrade (allow gains `MailSearch` and `MailRead` for the email agent). Time booking is calendar blocks with a project (`CATEGORIES` and `X-CONCLAVE-PROJECT`, or a Google private property); `CalendarList project` sums the hours.

**Tests.** In-process fakes (`core/test/pim/`): a CalDAV server (discovery, rights, time-range queries, ETags, the outbox), an IMAP server (literals, special-use folders, search, partial fetch, APPEND) and an SMTP server, and fake Google and Microsoft endpoints (token with PKCE checks, revoke, Gmail, Google Calendar, device code, Graph). A fetch that refuses every host but 127.0.0.1 keeps tests off the network.

Where it can fail: the first real sign-in with Google and Microsoft has not been tried from the build machine, which cannot reach them. A Gmail account on the shared Google app sees Google's "unverified app" screen, and the app is capped at 100 users until Google verifies it. The shared Microsoft app does not exist yet, so Microsoft needs the owner's own Entra app for now. The shared Google Web client for the relay is not registered yet (`google.web` is empty), so until it is, a browser away from the hub machine pastes the `127.0.0.1` address back; once it is, a relayed sign-in needs a browser that reaches the hub at the address the page used. Free/busy for other people works only where the server knows them. CalDAV writes are UTC times, so an event Conclave creates shows in UTC in a raw `.ics` view (clients show local time). Proposals for a repeating event can move one occurrence or the series, but not create a new series. The iPhone app does not run the in-app Google sign-in yet, and the Android app is not compiled in this environment.

## 33. Logs

**Why.** The owner wants to run the hub for a few weeks and then hand its logs to a developer to see whether everything works as it should. Until now the hub wrote only to stdout (`docker compose logs`, journald), which nobody keeps, the apps' errors stayed on the phone, and a device's daemon log stayed on that device. The code is `packages/core/src/logs`; the contract is `core/src/client/logs.ts`.

**Files.** `logger()` (`core/src/util/log.ts`) keeps writing to stdout and now also hands every line to a tap; a running hub installs one (`HubLogs` in `logs/index.ts`, started by `startServer`) that writes JSON lines to `<home>/logs/hub-YYYY-MM-DD.jsonl`, the UTC day: `time`, `level`, `component`, `msg`, `fields`, and `client` on lines an app sent. Writes are synchronous, so the line before a crash is on disk; `installCrashLogging` writes an uncaught exception or rejection with its stack and then exits with 1, as Bun would have. Files older than `logs.keepDays` (28) go when a day starts. When all files pass `logs.maxMB` (500) the oldest days go first; when today's file alone fills it, info and debug lines are dropped with one line saying so, warnings and errors still go until 10% past it, and the next day says how many were dropped. A write that fails never reaches the caller; it is reported once and tried again a minute later. `logs.debugUntil` keeps debug lines until a time: Settings, Logs and `conclave logs debug <hours>` set it, so debug turns itself off.

**What is logged, and how.** Each event is written where it is known, with ids, names, counts, durations and outcomes only. Turns: the runner writes one line per user turn with the session, agent, model, provider, time, model calls, tokens, cost (from the usage rows since the turn started), how it ended and the error. A failed turn's line is a warning; the runner's own "turn failed" line is the one error, with the stack. Engine events (`logs/events.ts`, a bus listener): tool calls (name, time, ok, exit code, never input or output), approvals and questions asked and answered with the wait, routine and workflow runs, import batches, alerts, provider limits, and error notices not about a session. The server: device connects and disconnects with the daemon and protocol, friends' messages in, out, delivered and failed, app sockets, and every 5xx answer with its method, path (no query string) and time. GitHub and memory connection failures, and a bus listener that throws, are logged where they happen. Busy events (tool calls, sockets, app lines) go to the files only, the rest to stdout too. The names agree with the reader's counts through `logs/names.ts`.

**The backstop.** Every line passes `cleanFields`: each string through the memory secrets filter, fields named like secrets (`token`, `apiKey`, `password`, `authorization`...) replaced by `[redacted]`, fields named like content (`text`, `prompt`, `input`, `output`, `content`, `body`...) replaced by `[omitted]`, strings and depth capped, a line at most 16 KB. stdout gets the same filter. Lines read back for a tail, the errors report and the export pass it again, for lines an older hub wrote. Tests plant a fake key and chat text in every path (a logger call, an error and its stack, nested fields, a turn through a real engine, tool input and output, an approval's command, an app's batch, an old line in a file) and check that neither reaches a file or the zip.

**Apps.** The web app (and so the desktop and iPhone apps) queues its own events in `lib/clientLog.ts`: connects and reconnects, failed requests with their status and the path with its ids folded, render errors from an error boundary (the page shows Reload and Try again instead of going blank), script errors, and push and notification failures. Batches go to `POST /api/logs/client` every 30 seconds, when 20 wait, and when the app goes to the background; at most 60 a minute and 200 waiting, the same event within 10 seconds counted once. Android has the same sender in `:client` (`ClientLogs.kt`), fed by the client's failed calls and its live connection and started with one line in `HubRepository.start`. The hub caps each client again: 50 events a batch, 120 a minute, 1000 an hour, 64 KB a body, with one line a minute counting what it dropped. A member's apps get 100 an hour all together, and their lines never make room at the size cap (docs/design/ACCOUNTS.md 2). App lines carry the paired client's id and name, and the app, version and platform the batch names.

**Devices.** Protocol 3 adds `logTail`: the TypeScript and Rust daemons keep the lines of their run in a ring of 1000 (status lines and, in the TypeScript one, logger lines), add the end of `~/.conclave/logs/daemon.log` where the service writes one, and filter secrets on the device. The export asks each online device that speaks protocol 3, with an 8 second limit; older daemons keep working and are named in the summary as too old to send a log.

**Export.** `GET /api/logs/export?days=1|7|28` streams a zip (`logs/zip.ts`: deflate, sizes in data descriptors, so no file is held whole): `summary.md` (version, uptime, hub starts and crashes, devices, providers set up by name, harness commands missing on the hub, turns by outcome and model, tool calls, approvals, routines, devices, friends, imports, app lines, a row per day, errors and warnings per component, the 20 most frequent errors with ids and numbers folded, and the last 30 errors and warnings in order), `config.json` (backup's `redactConfig`, every `env` and `headers` value as `[set]`, the secrets filter on the rest), the files of those days, and `devices/<name>.log`. Settings, Logs (after About) has the size, days kept, errors today and this week, the debug switch with its time left, and Download logs. The CLI has `conclave logs`, `tail [-f]`, `errors`, `export` and `debug`; with the local hub stopped, tail, errors and export read the files directly. Routes: `GET /api/logs`, `/api/logs/tail` (a cursor `day:offset` to follow), `/api/logs/errors`, `PUT /api/logs/debug`, all with the usual token.

Where it can fail: the days are UTC, so a day file does not match the owner's day. A turn's tokens and cost are the session's usage rows since it started, so a background subagent's calls in the same session would count, and a harness that reports no usage shows none. Subagent turns and workflow agents have no turn line of their own; their work shows as the Task or Workflow tool call. Tool failures are counted, not explained, since the explanation is tool output. App lines that wait in a closed tab are lost, Android sends no batch when it goes to the background (only every 30 seconds), and an app on a hub from before this change stops sending after the first 404. A device that is offline at export time has no log in the zip, and a daemon's ring holds only its current run. The secrets filter is a pattern list: a secret in a shape it does not know, under a field name that does not look secret, would pass. The files are readable by anyone who can read the hub's data folder, as the database is. stdout is bounded apart from the files: Docker keeps 30 MB of it, `conclave serve --detach` starts `logs/hub.log` over past 10 MB but only when it starts the hub, and the daemon's `daemon.log` (macOS, Windows) is not rotated.

## 34. Watches

**Why.** The owner's example from another assistant app: "I asked it to look at some cars, it used the browser to check Facebook Marketplace, and now it pings me daily with new cars and whether the old ones are gone or still available." A routine could already search on a schedule, but each run starts fresh, so it cannot say what is new or what went. A watch is a routine with a memory of what it saw. How to use it: `docs/ASSISTANT.md`, Watches. The code is `packages/core/src/watches`, the tools `core/src/tools/watch.ts`, the routes `server/src/routes-watches.ts` and `routes-browser.ts`, the screens `web/src/features/watches` and Settings > Browser.

**A routine with a memory.** `Routine.watch` holds the search address, the browser profile, the fields to read, the filters (price range, distance, keywords, words to leave out), how it notifies and a cap. A run reports items with WatchReport (a stable id, title, price, place, link, photo, fields, and sold or gone when the item's page says so). The hub keeps the reports until the run ends, then compares them with what it kept (`diff.ts`): new, gone, price down or up, other changes, still there. An item from the last run that the run did not report counts as gone, so the run is given every listed item in a data block and WatchReport's reply names the ones it has not reported yet; the run opens their links to check. A run that reports nothing changes nothing and fails with a sentence, since an empty search after a full one is far more often a login wall or a changed page than every listing going at once. Items and runs live in two tables the module creates itself (`watch_items`, `watch_runs`), outside the shared migration list; each item keeps its last 30 history entries, a watch its last 60 runs and at most `cap` items (200 by default), gone ones dropped first; a search that lists more than the cap keeps the items it has, so the ones that do not fit are not news every run. A deleted routine takes its rows and photos with it (the `routine.deleted` event, and a sweep at start).

**From a chat.** The assistant searches once with the hub's browser and calls WatchReport; in a chat that shows the items as cards and keeps them as the starting point of a watch made from the chat (read back from the transcript after a restart). On "Watch this daily" it calls WatchCreate: a routine on the chat's agent, on the hub, with the schedule in the owner's timezone, a prompt that needs no memory of the chat, the profile the chat browsed with (or the one signed in to the site), the fields and the filters. Its first run then reports what changed since the chat. The browser and the two watch tools are opt-in tools, so they cost nothing for agents that do not browse; the assistant names them in a new agent field, `optInTools`, which adds opt-in tools on top of the default ones without a full tools list.

**Only reading.** A watch run may browse and read, never post, message or buy. Three layers make that so. The run's session is untrusted (section 10), so it is offered only what its routine's allow list names: the reading browser tools, `browser_navigate` limited to the watch's site, and WatchReport. A runner extension takes away the tools that type, pick, run page code or switch profile, even when an allow rule names them. And the session's browser pages are read-only (`BrowserManager.setReadOnly`): every request other than GET, HEAD and OPTIONS is aborted, form posts, fetches and beacons included, and every WebSocket is closed, with a note in the next tool result. The run reads a results page with `browser_links`, which lists the links with their text and photo in one call, hub code rather than page code. A test proves it against a fake marketplace whose item pages send a beacon and open a WebSocket on load and have "Message seller" and "Buy now": the same page in a normal session sends both, a watch run sends nothing, even with an owner's rule that allows typing.

**Signing in.** The browser manager already had a takeover surface (a screencast of a session's tab and input events), but nothing used it. Settings > Browser now does: Sign in to a site opens the site in a profile under a view id, the app polls the newest frame (a screencast frame, or a screenshot when the page is still) about twice a second and sends clicks, scrolling, keys and text back. A phone gets the page at a phone's width. Done records the site for the profile in a file inside the profile's folder; `browser_profile` lists it, and WatchCreate picks that profile for the site. The view is not read-only, since signing in posts a form; nothing typed is logged or audited, the audit says only which profile signed in where. Done first waits up to ten seconds for a page that is still loading, since the login's answer is what sets the cookie; Chrome 156 can leave a tab that closes while a form post loads half closed, so a tab that does not close in 3 s is closed from the page (Page.close). Each browser step of the view has a bound (CDP sends, closes, the launch, screenshots), and a step that runs out answers 504 with its name instead of leaving the app waiting. What the owner types there goes to the site only; to let the assistant log in by itself, the owner saves a login instead (section 49).

**Notices and photos.** A watch says what changed itself, after the compare, so the routine's own done notice is skipped. By default it speaks only when something changed ("3 new, 1 gone, 1 price drop", then a line per item); `notify: daily` sends a summary every run. The notice goes through the routine path, so message hours hold it, and it carries the changed items, which the app's toast shows as photos with prices. Photos always come through the hub: it fetches an item's photo once, keeps it (40 MB per watch), and serves it with a policy that lets nothing in it run. Sites' photo links expire, and the app's page rules allow only https pictures. The hub fetches a photo on a private address only when the watch's own site is there.

Where it can fail: a site that changes its pages breaks the run until the prompt or the site settles, and the run then fails with "reported no items" rather than calling everything gone; a login that expires or a site's check (a code, a puzzle) needs the owner in the sign-in view again; Facebook loads more results by POST, which a read-only page blocks, so a run sees what a page shows on load, usually the first page of results and each item's own page; a service worker's own requests and the first request of a popup are not routed through the page's guard; a GET that changes something on a site is not blocked; a run that does not recheck an old item counts it gone (the prompt and WatchReport's reply ask it to, but a model can skip it); a CloakBrowser profile does not start on a hub that runs as root, so a watch that needs one runs on a hub started as a normal user; each recheck is a page and a model call, so a watch with many items that leave the search costs more; a chat card's photo on a private address is fetched when the item's own link is on that address, so a page that makes the model report such an item can make the hub send one GET inside the network; items are not in hub backups yet; the Docker image and the LXC setup ship no browser, and Settings, Browser installs one (section 42).

## 35. Accounts: several people on one hub

**Why.** The owner asked whether a friend could use the same hub with an account of their own, for their own work, without the owner's memory setup. Until now everything on a hub was the owner's: one password, the hub token, every app, every device and every row. The full design is docs/design/ACCOUNTS.md; the code is `core/src/people`, `server/src/route-policy.ts`, `server/src/scope.ts` and `server/src/routes-people.ts`.

**An owner and members.** `hub_accounts` holds the owner (the fixed id `owner`) and members (`acc_...`), each with a name to sign in with, an optional email, a password hash or an open invite, and settings: which of the hub's provider keys they may use with a monthly budget, and their own defaults. A member has their own sessions and messages, approvals, questions and Inbox, memory and memory connections, goals and the assistant's preferences, routines, tasks, usage, devices and apps, projects, imports, workflow runs, GitHub token, connected apps and provider keys. Calendar and mail are per account too: each has its own CalDAV, IMAP, Google and Microsoft accounts, secrets and proposals, and leave-by reads the calendars of the account the work runs for; the hub's own OAuth clients are shared. The hub's config, its keys, the hub device, remote access, extensions, MCP servers, hooks, friends, shared projects, gateway keys, maps (settings and tools), watches and the browser sign-in, the log files and backups stay the owner's. Every owned table has `account_id TEXT NOT NULL DEFAULT 'owner'`, so the migration is one `ALTER TABLE` per table, every old row and token is the owner's, and code that knows nothing about accounts keeps working as the owner. A child table (messages, routine runs, workflow calls) is scoped through its parent. Every table is in one of three lists in `people/tables.ts`, and a test fails on one that is in none.

**Sign in.** The hub token is the owner's. A pairing code, a device code and an invite carry the account of whoever made them, so the app or device that uses one is that account's. `POST /api/login` takes `account` with the password; without it, it is the owner, so a hub with one person and old apps work as before. A wrong name and a wrong password get the same answer in the same time. The owner adds a person with a password or an invite link (`<hub>/invite/<secret>`, 7 days, good once), sets their access, sets a new password (their apps sign out) and removes them (their tokens, devices, sockets and rows go).

**One table for every route.** `route-policy.ts` names each `/api` route as `public`, `hub`, `self`, `admin` or `own(kind)`, and one middleware enforces it. Members are refused `admin` routes and any route not in the table. For `own`, the id in the path is looked up before the handler runs, and someone else's id answers 404, for the owner too. `self` handlers list and create for the caller's account; ids in bodies go through `ownSession` and `ownDevice`. A sweep test lists every route the app has: each must be in the table, every list must answer a member without a word or an id of another account, every route with someone else's id must answer 404 and change nothing, and every owner route must answer 403.

**Events.** The bus stamps each event with its account when it is emitted (the event's own account, or its session's, routine's, device's). A socket gets its own account's events and the two hub wide ones; the replay after a reconnect filters the same way; an event nobody can place is the owner's.

**The hub machine.** Tools run as the hub's OS user, so a member's agent on the hub could read the owner's files. Members get no shell or file tools on the hub: a member's session there gets a machine that refuses every call, and no approval is asked for a call that cannot run. Every machine the registry hands out is also wrapped in a guard that reads the account the current work runs for (`AsyncLocalStorage`, set for every request, turn, routine and job) and refuses the hub to members and a device to anyone but its account. Members get no hub MCP servers, hooks, browser, watches, maps, learned skill writes or "always allow" rules; their WebFetch, memory connections and calendar and mail servers refuse addresses on the hub's network; Basic Memory for a member runs in their own folder with a bare environment. They code on devices they pair. The owner can give them a workspace on the hub machine: a device code and the commands for a daemon under its own OS user or in a container, paired to their account, so the hub itself never needs root.

**Keys and budgets.** A member's calls use their own key first, then the hub's where the owner allows it. `streamCompletion` is the only path to a model API: it picks the key for the call's account, checks the month's spend on the hub's key against the budget before anything is sent, and records who paid. Chores count too.

**Memory and recall.** Each account has its own memory store over the same tables, filtered by `account_id`, with its own connections. Recall, extraction, MemorySearch, SessionSearch, the daily digest and Conclave's own MCP endpoint (which serves the account of the token or of the app's grant) read the account's own rows only.

**Clients.** Web: the login asks for a sign-in name or email when the hub has several people, an invite page, Settings, People for the owner, Your account for everyone, a member's own Providers page, and the account menu on the sidebar's account row with switch, add and sign out. A member does not see the hub's settings, Extensions, Friends or Remote access. CLI: `conclave people` and `conclave login --password --account`. Android: the client takes an account at login and reads `/api/me`; the app asks for the sign-in name or email next to the password. Desktop: the first page has Password next to Pairing code and Token, so a member with only a name and password can set up their own computer; it shows the hub's fingerprint before it keeps the token, as the web does.

Where it can fail: the owner can read everything on the machine, which the invite page says; this is for a household or friends, not hosting. A `self` handler that forgets the caller's account would show everyone's rows; the sweep catches it only for routes it calls with data in place. DNS rebinding could let a member's fetch reach a private address between the check and the connection. Web search and embeddings run on the hub's keys for everyone and are not counted against a member's budget. A member's Claude Code chats are not imported by the hub's import watch unless they turn it on, and only from their own devices. Friends stay the owner's: a member cannot have friends of their own yet.

## 36. The desktop app as the hub

**Why.** The owner wants the desktop app, on Windows, macOS or Linux, to be the hub at one click: someone with one laptop and no server should not need Docker, a container or a terminal to start. How to use it: `docs/INSTALL.md` 1d. The code: `packages/desktop/src-tauri/src/local.rs` (every decision is a pure function with tests there), the glue in `main.rs`, the switch on the app's bundled page (`packages/desktop/src`).

**A download, not a sidecar.** The hub is the `conclave` CLI: a Bun binary of about 90 MB with the web app (`web/`) next to it, 40 MB as a release archive. Bundling it would add that to every installer, though most desktop installs connect to a hub on a server; it would need the web build and a Bun cross-compile in each of the four desktop jobs, and a folder of resources next to the sidecar in each bundle format. The release already builds, packages and checksums exactly the files install.sh uses, one per system. So the app downloads the one of its own version (`v<app version>`, from the releases repository), checks it against its `.sha256` before anything is unpacked, unpacks it with the system's `tar` (on Windows 10 and later that bsdtar reads the zip) into `<data>/hub-bin/v<version>`, and marks the folder complete last. After an app update the matching hub is downloaded at the next start; when that fails, the newest hub already there keeps running and the state says so. Offline matters little: only the first start (and the first after an update) downloads, and the hub needs the network for its models anyway. `release.yml` gains only a comment that these file names are a contract now.

**The child.** `conclave serve --port <p>` with `CONCLAVE_HOME=<data>/hub`. Its environment is the app's, without what would point it at another hub (`CONCLAVE_TOKEN`, `_HOST`, `_PORT`, `_HUB`, `_HOME`) and without an AppImage's mount (its libraries would break the hub's shells), plus the login shell's PATH, asked once per run of the app: an app started from a menu has a short PATH, and the hub runs git, claude and codex for sessions on its own computer. stdout and stderr go to `<home>/logs/hub.log` (started over past 10 MB, one old copy kept), next to the hub's own day files (section 33); the folder is 0700 and the files 0600, set again at each start for a folder made before, and a detached hub (`CONCLAVE_DETACHED`, which the app sets) prints its Login line without the owner token. On Linux and macOS it gets its own process group. It listens on 127.0.0.1 (`--host 127.0.0.1`) unless the app's **Let phones on this Wi-Fi connect** is on: switching the hub on must not open it to every network the laptop joins. With the setting on, the app leaves the address to the hub (every address), and the hub's own Devices on this network decides; turning it on or off starts the hub again.

**Stopping it.** Windows has no SIGTERM, and a hub must not outlive an app that crashed. So the child gets a pipe on stdin and `CONCLAVE_STOP_ON_STDIN_END=1`, the one change in the hub (`packages/cli/src/commands/serve.ts`, additive and off without the variable): when stdin ends, `conclave serve` runs its usual shutdown and logs `reason="stdin closed"`. Off and Quit close the pipe and wait up to 12 seconds (the hub gives itself 10), then SIGTERM, then kill: on Unix its whole process group, on Windows its tree (`taskkill /T`), so what it started (CLIProxyAPI, a tunnel, MCP servers, shells) does not hold its ports against the next hub. A hub that does not answer in 2 minutes after a start goes the same way. When the app dies, the system closes the pipe and the hub stops by itself. Quit in the tray, and a quit from the Dock or the system, stop the hub first.

**Restarts.** A hub that stops on its own starts again after 1, 2, 4, 8, 16 and 32 seconds. A run of a minute counts as healthy and starts the count over; after six quick stops in a row it waits for Try again. The state carries the last error, from hub.log after the app's last start mark: the CLI's `Error:` line, else the hub's last ERROR line, else a line about an error; with none of them, how the process ended ("stopped by signal 9").

**Ports, and a hub that runs here already.** The hub wants the port it had, 7717 the first time. A port is free when 127.0.0.1 binds and does not answer; only loopback is bound, so no firewall asks about the app itself. When something answers, the app asks it to sign a fresh nonce (`GET /api/identity`, which needs no token, section 14) and checks the signature against the public key of each home of this user it can read: the app's own (`<data>/hub/hub-key.pem`) and the CLI's (`$CONCLAVE_HOME` or `~/.conclave`). The first time, a hub of the CLI's home is this user's own `conclave serve`: the app uses it instead of starting a second, empty hub, saves that choice, and never starts or stops it; while it is down the app waits for it. A signature proves that some program can reach a hub with that key, not that it listens on the port asked: another user's program on 7717 could pass the nonce on to this user's hub on another port and get its token. So the CLI's hub counts only on the port its config.json sets (`server.port`, else 7717), where nobody else can listen while it runs. Only the app runs a hub with the app's own key, on the port it saved. Once the app's own hub has data, anything else on the port moves it to the next free one of the next 20, which it keeps from then on, and the state says so. Its own hub still answering (stopping, after a quick restart of the app) is waited for, up to 15 seconds. A port that looked free but that the hub could not bind (a program on one other address only) is avoided in the next round.

**The owner, with no code.** The hub writes its owner token into `<home>/config.json` (mode 0600) on its first start, and the app makes the home folder 0700 (on Windows it is in the user's own local app data). The app reads the token only after the hub on the port proved it holds that home's key, so the token is never sent to another user's program on a loopback port. It goes only to 127.0.0.1, and nothing serves it. The app keeps it as its hub token (settings.json, 0600, as for any hub), reads it again at every start of the hub, so a changed token follows, and loads the hub page with it in the fragment; the web app's setup takes over from there. Each time the hub becomes ready (a start, a restart after a stop, another port), a window that shows the hub loads it again, so it never keeps a page from while the hub was away. The owner token, not a paired client token: on a laptop hub the app is the owner, and only the owner revokes a lost phone, sets the hub password or puts keys in a backup. This computer's daemon pairs with the same token (`pair --app-token-stdin`, section 23), and is kept when it is already a device of this hub; it moves to this hub from any other, as with Change hub.

**Phones.** A laptop hub is reached through remote access, and from the same network when **Let phones on this Wi-Fi connect** is on. The app's Settings shows a pairing QR code made by the hub (`POST /api/pairing`; the SVG is shown as an image, so nothing in it runs) and says from where phones can reach the hub, judging by the addresses the code carries; Remote access opens the hub's own Settings > Remote access. The tray's first line follows the hub's state.

**The hub's pages cannot start it.** As for the daemon (section 23): the commands that start and stop the hub belong to the app's bundled page only, and the hub's pages get no new IPC.

Where it can fail: the first start needs GitHub; the app uses `HTTPS_PROXY` (not for loopback or `NO_PROXY` hosts), but a proxy that inspects TLS with its own certificate authority is refused, since the app trusts only the public roots it carries. The checksum comes from the same release as the archive, so it catches a broken download, not a release someone replaced (install.sh has the same limit). An app built by hand or by a run of the workflow (0.0.N) has no release of its version; `CONCLAVE_HUB_BIN` names a binary instead. Windows before 10 (1803) has no `tar`. Phones lose the hub whenever the laptop sleeps or is off. A phone that paired on the same network before the port moved keeps the old port until the hub's address list reaches it. With **Let phones on this Wi-Fi connect** on, anyone on that Wi-Fi can reach the hub's pairing and login routes; they are rate limited as at home, but a laptop that travels is safer with it off (the default) and a tunnel. The daemon paired with the laptop hub guards its own `CONCLAVE_HOME` (`~/.conclave`), not the app's hub folder, so a session on that device could read the hub's `secrets.json` by accident; the hub's own device ("local") guards it, and the two both stand for this computer on the Devices page. An adopted `conclave serve` is waited for, never run by the app on its data; to run the app's own hub instead, turn the switch off and on while it is stopped (the app's hub then starts empty). A hub binary the app downloaded has no download flag on macOS, but stricter Gatekeeper settings or Windows Defender may still stop an unsigned binary. The real runs were on Linux and headless: a download from a local server, start, the owner token, pairing the Rust daemon and its reconnect, kill -9 and the restart, a clean stop, a port in use, adopting and leaving a `conclave serve`, and a parent that dies. The windows, the tray and the installers on macOS and Windows have not run with it yet.

## 37. Effort

**Why.** The owner wanted the chat's Thinking control (off, low, medium, high) to be Effort, as in Claude Code, with the levels each model really has. The provider layer already spoke five levels; the control offered four, the same four for every model, and Off on a Claude 5 model still sent adaptive thinking. The code: `core/src/providers/effort.ts` (the one helper), `planAnthropicThinking` in `providers/anthropic.ts`, `engine.thinkingFor`, `acp/adapter.ts` `applyEffort`, and in the web app `lib/effort.ts` with the picker in `ComposerParts.tsx`.

**One table.** `effort.ts` says, per model and wire, which levels it takes (`low`, `medium`, `high`, `xhigh`, `max`), whether Off exists and its default. Claude follows Anthropic's docs: the Claude 5 family and Opus 4.8 and 4.7 take all five, Opus and Sonnet 4.6 have no xhigh, Haiku 4.5 and older have no Effort control. The default is high, medium on Opus 5.5 and Haiku 5.5. Opus 5.5 and Fable cannot turn thinking off, so they offer no Off. Mythos 5.1 is not in the docs' list and is treated as Fable 5.1. Other wires get what their adapters send: OpenAI reasoning effort (low to high, xhigh from GPT-5.2 on, never max), OpenRouter low to high, Gemini 3 thinkingLevel (Pro low or high, Flash low to high), Gemini 2.5 a budget, Anthropic-compatible gateways and DashScope a token budget with Off, Z.ai and DeepSeek on Chat Completions one switch (On or Off). The registry puts the result on every model it lists and resolves (`ModelInfo.effort`), so the web app, Android and the engine read the same thing.

**What is sent.** `chat.thinking` takes `off` and all five levels; old stored values stay valid. Unset uses the agent's level, then (coding agents) medium on models that take an effort level, then the model's own default. A level the model lacks is sent as the nearest one it has, the lower on a tie (xhigh on Opus 4.6 is high); Off on a model that cannot stop thinking is its lowest level. Anthropic: a level is adaptive thinking with `output_config.effort`, never `budget_tokens` on the models that refuse it. Unset is adaptive thinking at the model's default effort, now on Opus and Sonnet 4.6 to 4.8 too (they thought only when asked before). Off is `{type: "disabled"}` with no level (Opus 5 and Haiku 5.5 take it only at high or below), `{type: "between_tools"}` and nothing else on Sonnet 5.5, and no thinking field on 4.6.

**The control.** Web: the model and its effort are one picker in the composer's quiet row ("Opus 5.5 Medium", section 40); its Effort row lists only the selected model's levels with the default marked, and a model without Effort shows none. Picking another model keeps the level when it has it, else moves it to the nearest one. Home's session start and a session's composer use the same picker, with the agent's own level as the unset choice; the start's picks keep all levels and send the clamped one. The /model sheet sets a running session's level the same way, and the agent editor calls the setting Effort. Android reads `ModelInfo.effort` from the hub and has the same picker under its composer, the Effort row on top of the model list (`logic/Effort.kt` `words` and `follow`).

**Harnesses.** Claude Code over ACP (`@agentclientprotocol/claude-agent-acp`) offers an Effort option (an ACP select of category `thought_level`) with the levels the model has. A harness turn sets it to the session's level (else the agent's), at the nearest level offered, and back to the harness's default when the level is cleared. The turn also says which levels the harness offered; the hub keeps them per harness model (`harness.effort` in kv) and announces `models.updated`, so the model list, the session start and the /model sheet offer exactly those. A harness without the option (the default command still runs the older `@zed-industries/claude-code-acp`, which has none) offers none and the control stays hidden.

Where it can fail: the table is written by hand from the docs and goes stale when a model changes; the OpenAI, Gemini and gateway rows say what our adapters send, not what each model accepts, and defaults there are left out where they are not known. A harness model shows Effort only after one turn has run on a hub with an adapter that has the option.

## 38. Importing chats from a computer when it pairs

**Why.** A computer's Claude Code, Codex and Gemini CLI chats were imported only when the owner went to Memory > Import and picked it. The owner wanted the hub to ask once, when a computer pairs. The code: `core/src/import/offers.ts`, the routes in `server/src/routes-import.ts`, and in the web app `features/import/OfferCard.tsx`.

**The trigger.** `POST /api/daemon/register` marks a device that is new (a desktop app pairing its computer again keeps its device and is not new). The first time that device comes online, the import scan reads it (`ImportService.newChats`, as its account) and counts the chats the import would bring by default: not imported yet, not too short, not automation or subagent threads. With some, one offer opens: an Inbox item, a notification and the `import.offer` event, "Found 12 chats from Claude Code and Codex on studio. Import them?". Import opens the import sheet with that device picked, which shows the cost estimate first; nothing is imported until the owner starts it. That scan is the device's cached scan for the next minute, so the older single import (`POST /api/import`) reads the device again when the chat it names is not in it.

**Once per device.** The offer stays in the Inbox and on the device in Devices until an import from that device starts (from the sheet, the CLI or the import watch) or the owner says Not now. A device that was dismissed, imported or had nothing to bring is never asked again, and a device the hub knew before this release is never asked. A scan that fails is tried the next two times the device comes online. A member's device is offered to that member only: the offer, its event and its notification carry the device's account, and only that account lists or dismisses it.

**The desktop app.** After pairing, the app loads the hub's web app at its root. A hub that is set up shows Home, so the Inbox item and the notification are the offer; the app has no first run screen of its own after pairing. A brand new hub opens onboarding, whose Devices step is left as it is.

Where it can fail: the count is from the first scan and does not follow chats added later; the offer is kept in the kv table, one row per device, and a removed device's row goes with it, so the same computer paired again as a new device is asked again.

## 39. Updates

**Why.** The owner should never reinstall by hand. Before this the hub updated by running its install script again (or `conclave-lxc.sh update`, or a Docker pull), the desktop app was installed over itself, a daemon without the app was replaced by hand, the Android APK was sideloaded again, and only the web app and the iPhone home screen app came along with the hub. How to use it: `docs/INSTALL.md` 14.

**One key, one file.** Every file an updater installs is signed with one minisign key, the format of the Tauri updater: a prehashed Ed25519 signature ("ED", over the file's BLAKE2b-512) and a second signature over that one and its trusted comment. Tauri's own updater needs that format for the desktop app, so everything else uses it too, and `tauri signer sign` signs every file in CI. The public half is `packages/core/src/update/update-key.pub`, the one file every updater reads at build time: the hub and the TypeScript daemon import it as text (`core/src/update/key.ts`), the Rust daemon and the desktop app `include_str!` it, and the Android build puts its key line in `BuildConfig.UPDATE_KEY`. It holds the owner's key (id E7C55DB954A18353, since v0.4.2); a build with the old placeholder refuses to install anything and says why, and its desktop app shows nothing and logs why. The check is written three times (TypeScript `core/src/update/minisign.ts` with node:crypto, Rust with the `minisign-verify` crate, Kotlin `client/update/Minisign.kt` with Tink's Ed25519 and a BLAKE2b of its own, since Android has none); a signature made by `tauri signer sign` with a throwaway key is a test vector in all three, so they agree with the real tool. Legacy ("Ed") signatures are refused, as Tauri does.

**Signing in CI.** The secrets are `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. In Release, the desktop job turns on Tauri's updater bundles only when the secret exists and update-key.pub is not the placeholder (`scripts/releases/updates.ts tauri-config`, merged through `TAURI_CONFIG` with the committed public key, so the bundler also refuses a secret that does not match it), and tauri-action signs them; a new `sign` job signs the CLI archives and the daemons and uploads each `.sig`. Without the secret it signs nothing and the release title says "(unsigned)". Publish public signs what is still unsigned (the APK, which the Android workflow builds) and writes two manifests next to the files on the public release: `conclave-update.json` (version, notes, date, `signed`, and per file its URL, SHA-256, size and signature: `hub` by release target, `daemon` by Rust triple, `desktop` by Tauri platform, `android`) and `latest.json` in the Tauri updater's shape. `signed` is true only when every hub, daemon and APK file has a signature. A tag from before this has no manifest, so no updater ever sees it. The private key is only in those two workflows' environment and in the Tauri CLI they start; the script never prints it and strips long base64 runs from the CLI's error output.

**The hub.** `UpdateService` (`server/src/update/service.ts`, routes in `routes-update.ts`, the owner's only) looks at `releases/latest/download/conclave-update.json` once a day (not under `bun test`; `updates.check: false` turns the daily look off) and when the owner opens Settings > About. How it may update depends on how it was installed (`core/src/update/install.ts`), read from what the process can see: Docker (the image sets `CONCLAVE_INSTALL=docker`), the desktop app's hub (`CONCLAVE_STOP_ON_STDIN_END`), a checkout (not a compiled binary), Windows, or a release folder (`conclave` and `web/` next to each other) run by a systemd unit whose name says conclave, found in `/proc/self/cgroup`. Only the last updates itself; the others get the command that updates them. **Update now** downloads the archive for this system into `<home>/updates` and checks its size, SHA-256 and signature, so a bad file fails here, with progress in About. Then it writes `request.json` and starts the finisher (`conclave update finish`, `core/src/update/finish.ts`) outside its own service: `systemd-run --user` for the install script's user unit, `systemd-run` for a hub that runs as root, and for a hub in a container set up by `setup.sh` (user `conclave`, code owned by root) the `conclave-update.path` unit, which starts `conclave-update.service` as root. The finisher trusts only the version and the file name in the request: it copies the archive into a folder of its own next to the install (so the hub cannot change the file after it is checked), checks size, SHA-256 and signature again with the key built into itself, unpacks with `tar --no-same-owner`, asks the new `conclave --version` (it must say the version asked for and be newer than the finisher's own), swaps the folders with two renames on one disk (the old one stays as `<install>.prev`, an older `.prev` goes), restarts the unit and waits 90 seconds for `/api/health` to answer with the new version. When it does not, `<install>.prev` comes back (the new one stays as `.failed` to look at), the unit restarts, and the state says "went back". A request naming any unit that does not start with `conclave` is ignored, so a hub cannot make the root finisher restart something else. Every step goes to `<home>/updates/state.json` (given to the hub's user by a root finisher); the hub shows it and writes the audit line once, by job id in the kv table, the old hub for a failure before the swap, the new one or the rolled back one after a restart.

**Automatic updates.** "Install updates automatically" (`updates.auto`, off unless set, the owner's) installs a new release between 03:00 and 05:00 on the hub's clock, when no session is running, at most once per version, and in the same window sends the devices' daemons the hub's version.

**Device daemons.** Protocol 4 adds the `selfUpdate` RPC: the hub's version and that release's manifest (the one of the hub's own version, not the newest, so a device matches its hub). The daemon picks its own file (the hub archive of its target for the TypeScript daemon, `conclave-daemon-<triple>` for the Rust one), checks it with its own key, asks the new binary its version, and swaps it in, keeping `.prev`; it answers, then exits, and its service starts the new one (systemd `Restart=always`, launchd `KeepAlive`; the Rust daemon on Windows starts the new binary itself, since the Run key starts it only at sign in). The first two checks (a version, and that it is newer) come in the same order in both daemons and the conformance test compares them. In its hello a daemon says how it updates (`self`, `app` for the desktop app's copy, found by `bundled.stamp` next to it, or `manual` with why) and its last update, read from `daemon-update.json` by the new binary, so the Devices page shows the result after a restart of either side. The hub calls the RPC only on protocol 4 daemons that say `self`, with a 20 minute timeout, and counts the update done when the device comes back with the new version, failed after 10 minutes without it.

**The desktop app.** `tauri-plugin-updater` with `latest.json` (`src-tauri/src/update.rs`); the key is set at run time from the built-in file, and `tauri.conf.json` carries an empty one only because the plugin's config needs the field. It checks on start and once a day on a thread of its own, and puts **Update to X and restart** in the tray menu and on its settings page. Installing stops the hub on this computer cleanly first. The hub the app runs and the daemon it carries are already tied to the app's version (sections 23 and 36). Linux updates itself only as an AppImage; a `.deb` or `.rpm` is updated by the package manager.

**Android.** `AppUpdater` (`app/update/AppUpdater.kt`) reads the manifest on start and once a day, offers only a newer, signed release APK (a test or debug build has another signing key and is never offered one), downloads it with DownloadManager into the app's own files, checks size, SHA-256 and signature in one read (`client/update/AppUpdates.kt`, tested on the JVM), and opens the system installer through the app's FileProvider. Android makes the person allow installs from Conclave once (`REQUEST_INSTALL_PACKAGES`) and tap Install each time; that is the platform's rule for apps that are not from a store. The release APK keeps the signing key of the installed one, so it updates in place. A ready update asks once per start in a dialog ("Conclave X.Y.Z is ready", a short what's new line, Update now, Skip this version, Don't show at startup); a skipped version stays quiet until a newer one, and with the dialog off the update shows as a dot on the side panel's account row and in Settings, About, where a switch turns the dialog on again (`app/update/UpdateDialog.kt`, the rules in `client/update/UpdatePrompt.kt`). The last manifest read is kept, so the dialog does not wait for the next daily look.

**Web and iPhone.** The hub serves them. A page that was open when the hub's version changed (the store reloads `/api/info` after the socket comes back) shows "Conclave was updated." with Reload, once per new version (`web/src/components/UpdateBanners.tsx`). For the owner, a newer release opens a popup when the app starts (every surface of the web build: browsers, the iPhone app, the desktop app's window): "Conclave 0.5.0 is ready", the first line of its notes, **Update now** (or How to update where the hub updates another way), **Skip this version** (no popup and no dot until a newer one) and a "Don't show at startup" checkbox. Members never see it: updating the hub stays the owner's.

Where it can fail: builds from before v0.4.2 carry the placeholder, so each hub, daemon and app must be updated by hand once to v0.4.2; after that updates install themselves. The manifest is not signed itself, only each file; a changed manifest can at most point at another genuine signed file, and the version checks (the new binary must say the version asked for and be newer than the running one; Android refuses a lower versionCode) stop an old one being sent back. The daily look needs github.com; a hub behind a proxy that inspects TLS fails the check and says so in About. A finisher killed halfway (a power cut between the two renames) can leave no `<install>` but a `<install>.prev`; the service then fails to start and the owner renames it back by hand, as `INSTALL.md` 14 says. The health check is the hub answering `/api/health` with the new version within 90 seconds; a hub that answers and then breaks later is not rolled back. Disk space for two copies of the release (about 200 MB) is needed during the swap. A daemon that cannot start its new binary at all is not rolled back by itself (its service keeps restarting the new one); `conclave-daemon rollback`, or renaming `.prev` back for `conclave daemon`, puts the old one back. A daemon run by hand in a terminal, and the TypeScript daemon on Windows, update by hand. A user unit restarts only while the user's systemd manager runs (`loginctl enable-linger`, which the install guide already asks for). The Android installer needs the person's tap, so an update is never silent there. The real runs were on Linux: the hub update through the API with a fake release server and the finisher in the test process (swap, restart, health check, rollback), the Rust daemon replacing a running test binary from a local server, and the signing of real files with `tauri signer` and a throwaway key. The desktop updater, the systemd-run hand-off, the root path unit and the Android installer have not run against a real signed release yet.

## 41. Discover installs what an item needs on the hub

**Why.** A Discover card that said "Needs serena on the hub" (or uvx, semgrep) only showed a command to copy, so the owner had to open a shell on the server for a one line `uv tool install`. The `SetupStep` type already said "the hub may run it only after a confirm, and only where `on` says", but nothing ran them. Now the card and the preview's setup step have an "Install on the hub" button when the hub can do it itself. The code: `core/src/catalog/hub-setup.ts` (what may run and in what order, pure, so the web mock uses it too), `CatalogService.runSetup` (the run), `POST /api/catalog/items/:id/setup` in `server/src/routes-catalog.ts`, and in the web app `features/extensions/discover/hub-setup.ts` and `HubSetup.tsx`.

**What can run.** A fixed table and the shipped list, nothing else. uv and uvx come from astral's install script for a pinned release (`UV_VERSION`, the release's own `uv-installer.sh`, with `UV_NO_MODIFY_PATH=1` so no shell profile changes), which needs curl. A need that names its Python package (`CatalogNeed.uvTool`) installs with `uv tool install`. A hub step (`on: 'hub'` with `run`) of an item whose definition ships with Conclave runs as written, and `gives` names the programs it puts on the PATH, which is how a missing need finds its step (Serena, Semgrep, Zotero, radare2 MCP). Prerequisites go first: the first program of a step's command (uv for `uv tool install ...`) is put in place before the step, through the same rules. The service plans from the shipped definition by id, never from a cached copy, and a step with `sudo` or a placeholder such as `<tailscale ip>` is refused even when shipped.

**What cannot.** Steps and configs from GitHub search, the MCP registry, marketplaces or the feeds are text from the internet: they stay as commands to copy, and the route answers 403. Programs that need root (docker, Chrome, Node.js and npx, curl, radare2 and other system packages) never get a button; the card says so in one line and shows the Debian command to copy (`sudo apt-get install -y docker.io`, Google's own `.deb` for Chrome). A need on a device, or a step that runs on one, is not the hub's: it keeps its copy and says where to run it. A Windows hub runs nothing.

**How it runs.** As the hub's own user, in its home, through the hub's own machine (`engine.devices` "local", `LocalMachine.exec`), whose environment drops the hub's secrets like hook commands do (`isHubSecretEnv`), with `~/.local/bin` in front of PATH so the second command finds the uv the first one installed. The commands run one after another and stop at the first that fails, with 10 minutes for the whole run; the answer keeps the last 200 lines of output, both streams in order, each command after a `$` line. The owner's only (route-policy.ts, `admin`): a member or an app without owner rights gets 403. One run at a time per item (409). The confirm sends the commands it showed; when the hub would now run something else (uv appeared meanwhile) it answers 409 with the new offer instead of running. Before the run the audit log gets the item, the user, the folder and the command line; after it, the result. Then every `command -v` answer is checked again, so other items that wanted uvx turn ready too, and the card refreshes; Add then works as before.

Where it can fail: the readiness check reads the hub's own PATH, so a program that lands in `~/.local/bin` on a hub whose PATH lacks it (the Docker image) still reads as missing; the result says so and names the folder to add. The LXC unit has it on PATH. uv's script downloads from GitHub and `uv tool install` may download a Python, so a hub without internet fails there, with the output to show why. Commands that ask a question on a terminal get no input and fail. A first install that takes longer than 10 minutes is stopped, with its output. The installs are not undone by Remove; `uv tool uninstall` does that by hand.

## 42. The hub's browser: install, engines and the proxy

**Why.** On the owner's hub (a Proxmox container running the release binary as `conclave`) Settings, Browser said "Chromium, playwright-core is not installed". The release binary keeps Playwright out (`scripts/build-cli.ts`) and finds it only "installed next to the binary", in `/opt/conclave`, which root owns and the hub cannot write. Nothing put it there, CloakBrowser had to be installed and pinned by hand, and there was no proxy. The owner wanted the anti-bot browser to work with no shell, and a proxy they buy for when they ask for one.

**Install on the hub** (`browser/setup-plan.ts` plans, `browser/setup.ts` runs, `POST /api/browser/setup`). The same rules as Discover's hub setup (section 41): the owner only, as the hub's own user, never root, the exact steps shown and confirmed, a changed list refused, every run audited before and after. Every version and hash is pinned in code: playwright-core 1.64.1 checked against `bun.lock`'s sha512 (a test keeps the three in step), Playwright's own Chromium installer for the revision that version names, and CloakBrowser 146.0.7680.177.5 from CloakHQ's release, its archive checked against the signed `SHA256SUMS` and its `chrome` against a second pin before it moves into place and `browser.cloak` is set. Downloads run in the hub (fetch, hashed while they stream, renamed into place only on a match), so no curl; unpacking and Playwright's installer run as commands through the hub's machine. Everything lands in `<CONCLAVE_HOME>/browser`, a folder the hub's user owns. `loadPlaywright` tries the app's playwright-core and then that folder by its full path, which a compiled binary can import; browser discovery looks in its `ms-playwright` first. The page names missing system libraries (`ldd`) and missing fonts as one apt-get line for root; with the root helper (section 45) it installs them itself, through sudo and a fixed action. The Docker image takes `--build-arg BROWSER=1` for them.

**Engines.** Each profile shows its engine in a select, CloakBrowser disabled until installed. A new profile (no engine set, no browser has run in it) gets CloakBrowser when it is installed, written to the config before its folder exists, so a failed first launch keeps it. Moving an old profile asks first, since the sites then see another browser.

**The proxy, when asked or when blocked.** The owner's rule (changed 2026-10-23): pages load from the hub's own address; when a site blocks that address, the request is retried once through the proxy, in the country of the hub's own public IP (`tools/blocked.ts`: `looksBlocked`, the country from Cloudflare's trace page once per process, else the proxy's configured one). WebFetch, WebSearch and `browser_navigate` do this by themselves and say so in one line; a member's call never uses the owner's proxy. No profile is always proxied. The browser tools also have a `proxy` input for when the owner asks for a proxy or a country, or a watch's or routine's own instructions do; the agent passes `true`, a country, or `false`. The manager then gives that session a throwaway browser through the proxy (`useProxy`, a fresh folder under the cache, deleted on close), so the profiles' saved logins never go through it, and the session's calls stay there until `false` or another country. A test checks that a call without the input does not read `browser.proxy`, any secret or the network. Providers: DataImpulse (HTTP, `gw.dataimpulse.com:823`, the country as `__cr.<cc>` in the user name) and one custom URL. Chromium answers an HTTP proxy's login through Playwright; it cannot send a SOCKS5 login, so a custom SOCKS5 proxy with one goes through a relay on 127.0.0.1 that logs in upstream (`browser/proxy-net.ts`). Logins and passwords are hub secrets; the app, the audit and the log see labels only.

Where it can fail: the hub's network may block the downloads (GitHub for CloakBrowser, `cdn.playwright.dev` for Chromium, the npm registry for playwright-core); the step fails and says so, and nothing half unpacked is put in place. Playwright's Chromium download is not checked against a hash of ours, only pinned by version through playwright-core. CloakBrowser keeps its sandbox, so it needs a non-root hub with user namespaces (nesting on in Proxmox; Docker's default seccomp profile blocks them). The pinned CloakBrowser is Linux x64 only. DataImpulse's own docs were not reachable from the build machine, so its format comes from its public tutorials; a rotating proxy can show a different exit address to the page than to the check. Proxied pages start with no logins, so a site that needs one is not for the proxy.

Read-only takes its file-editing tools away (`toolsFor`) instead of putting it in plan mode, which refused the read-only commands explore needs; on a harness, which takes no tool list, a read-only profile keeps the `forHarness` rule (no shell: plan; a shell: bypass runs as default). **Clients.** A Delegate call is a subagent row ("Code on MadX Arch: Find names in the capstone PDFs, reading notes.pdf") with its time, and it is in the running tasks list while it works. The web and Android map the tool to Task (`workName`, `Work.name`) and find the child by the call id it carries in `meta.delegate` (or `meta.movedFrom`, below); the device's name comes from the result or the child, else as the call wrote it. ## 44. Switching models: the price first, and a short handover

**Why.** A switch used to set `session.model` and add a notice, so the next reply read the whole active chat on a model with no cache of it. Prompt caches belong to one model: the first request after a switch writes all of it again. Moving a 100K token chat from Opus 5.5 to Sonnet 5.5 in an interactive session writes 100K tokens at the 1 hour price ($4/M), about $0.40, where staying would read them for $0.02. Conclave showed that as $0.25, because it priced every cache write at the 5 minute rate. A research pass (Anthropic's pricing and caching pages, the Handoff Tax paper, JetBrains' study of trimming old tool output, Anthropic's context editing) and the plan in SPEC.md 11.2.5 led to four changes. The owner put quality first: the full history stays the default.

**Costs that match the bill.** The Anthropic adapter reads `usage.cache_creation.ephemeral_1h_input_tokens` and `ephemeral_5m_input_tokens`: `cacheWriteTokens` stays the total and `cacheWrite1hTokens` is the 1 hour part. The catalog gives every Claude model a `cacheWrite1hPrice` of 2 times input (LiteLLM's `cache_creation_input_token_cost_above_1hr` wins when it names one, and a new input price moves it), and `computeCost` prices the 1 hour part at it and the rest at the 5 minute price. Sonnet 5.5 reads cost $0.10/M (0.05 times input), as on the pricing page of 2026-10-22; the catalog had $0.20. Opus 5.5 ($4, $5 at 5m, $8 at 1h, $0.20 read, $20 out) and Sonnet 5.5 ($2, $2.50, $4, $0.10, $10) were checked there. Haiku 5.5 and the GPT-5.6 and GPT-5.5 prices were not (OpenAI's page could not be read), so they keep their values with a note. Session stats count `cacheWriteTokens` and `/usage` shows cache reads and writes.

**The price before a switch** (`core/modes/switch-cost.ts`, the arithmetic in `switch-math.ts`, `GET /api/sessions/:id/switch-estimate?model=`). The tokens are what the target would read: the stored messages as `buildProviderMessages` sends them to it (cleared output stubbed, other models' thinking dropped), the tools and about 3K of system prompt, or the last reply's own count when that is larger (chars / 4 undercounts code). The first reply on the target costs those tokens at its first turn price: 2 times input for Claude with the 1 hour cache of interactive sessions, 1.25 times when headless, the catalog's write price elsewhere (GPT-5.6 1.25 times), plain input where writes are free or caching is off. Staying costs the same tokens at the current model's cache read price. A later reply is the history read warm, 3K new input written and 2K output; the switch pays back after the extra first reply divided by what each later reply saves. The worked example, pinned by tests: 100K from Opus 5.5 to Sonnet 5.5 is $0.40 once against $0.02, $0.042 a reply against $0.084, so about 9 replies; with a short handover, the Haiku summary ($0.005) plus about 35K tokens at $4/M is $0.145, about 3 replies. Ask once is one second opinion from the target (the brief, the answer and the transcript, about 11K tokens in and 1.5K out). The estimate asks for the step (`confirm`) only over `context.switchBriefAt` (default 50,000 tokens; 0 never) and never for a cheap target: a fast tier model or a full replay under 5 cents, where it costs about a cent. It suggests the short handover in a quiet line when it saves $0.20 or more. The web picker and the Android sheet show it (docs/design/CHAT-AND-MOTION.md 2.12).

**Full history (default).** Exactly what a switch did before: the model changes, a notice says "Switched from Opus 5.5 to Sonnet 5.5.", and nothing is summarized or cleared.

**Short handover (opt-in)** (`core/modes/handoff.ts`, `POST /api/sessions/:id/handoff` with `brief: true`). It runs only when the estimate offers it and no reply is running; otherwise the switch keeps the full history and the notice says why. It runs the existing compaction (`maybeCompact`, trigger manual) with the target's window and instructions to keep the goal, the decisions, exact identifiers, the open asks and the next step, so the new model reads the summary, the user messages it quotes and the newest 10K to 25K tokens. The summary's meta records the switch. The turns kept word for word after it go without thinking, even the target's own, because Anthropic's prefix check fails thinking kept after a summary the harness wrote; the new model's own thinking after the summary is kept. Since v0.4.13 every compaction does this (section 46). Then old tool output is cleared in one batch (`applyClearing` with a 12K token window and no batch threshold, against the usual 50K kept and 30K batches), keeping the `CLEAR_EXEMPT` tools whole; the marks are stored, so later requests stay cacheable, and ReadToolOutput still reads every output. The new model's cache is empty anyway, so the clearing costs no extra cache miss. Nothing stored is deleted: the summary shows like any compaction summary, with Show summary, and the notice reads "... with a short handover: a 3K token summary and the recent turns, 9 old tool outputs cleared." The clearing never happens with Full history.

**The switch marker** (`core/modes/switch-marker.ts`). When the model of a session with history changes (a switch, a PATCH, a chat's picker), the engine records `meta.switched = { from, to }`, keeping the first model across several switches and dropping it on a switch back. The next user turn carries one reminder, "You took over this conversation from Claude Opus 5.5. Continue from where it stopped instead of planning again; its private reasoning is not available, so check the current state before you repeat an action.", stored with that message and never edited, so the cached prefix holds. Jury and debate turns skip it.

**Rate limit fallbacks.** A fallback model reads the whole chat again with no cache too. When the limit resets within 5 minutes, the chat holds `context.switchBriefAt` tokens or more and auto-resume is on, `handleLimit` parks the session until the reset instead of falling back, and the notice says it did not switch. `limits.waitShortResets` (default true) turns it off. It never summarizes and never changes what the model sees.

Where it can fail: the token count is chars / 4 or the last reply's count, so a tokenizer that counts 30 percent more (Claude 4.7 and later) makes the first reply dearer than shown. The short handover's size before it runs is an estimate (summary, quoted asks and the cleared tail); the real one depends on the summary. Quality after a short handover is not measured in Conclave: details older than the kept turns live only in the summary, which is why it is opt-in. The 1 hour price applies to Claude models only; another provider's 1 hour write would be priced at 2 times input.

## 45. The root helper: system packages without a root shell

**Why.** On a hub in a Proxmox LXC (the release binary as `conclave`) Install on the hub put CloakBrowser in place, and then the page said the browser needs libX11, libnss3, libgbm and more, plus fonts, and showed an `apt-get install` line "to run as root on the hub's machine (in a Proxmox container, open its console first)". Two complaints: Conclave is an agent and should resolve this itself, and the line did not say whether to run it on the Proxmox host or inside the container. Giving the hub root, or a sudo rule for `apt-get`, would let anything that runs as the hub's user (every agent's Bash tool, every hook, every MCP server it starts) install any package, which is root. So the hub gets a helper that can do a few fixed jobs as root and nothing else, installed once by the owner. How to use it: `docs/INSTALL.md` 16.

**What runs as root.** One file, `/usr/local/libexec/conclave-root-helper`, a POSIX sh script, root:root 0755, written by `conclave system-helper install` from the text in `core/src/system/root-helper.ts`. It takes exactly one argument, an action name from a list written into it, and nothing else; a second argument, an unknown name or none is refused (exit 2) before anything runs. What each action does is in the file: today only `browser-deps`, which runs `apt-get update` and `apt-get install --no-install-recommends` for the browser's libraries and fonts. The package names are written into the file too, two lists (Debian 13 and Ubuntu 24.04 rename six libraries with `t64`), each every package `browser/packages.ts` can name, so whatever `ldd` finds missing is in them; a test keeps them in step. It picks the list from `ID` and `VERSION_ID` in `/etc/os-release`, read with sed, never run; another system (Fedora, a derivative) or one without apt-get is refused with a line that says so. It sets its own PATH (`/usr/sbin:/usr/bin:/sbin:/bin`), umask and locale and reads nothing else from its environment; the only value it takes from sudo is `SUDO_USER`, for its log line, and only when it is a plain name. It asks dpkg first and does nothing when every package is there. It logs what it did, and every refusal, with `logger -t conclave-root-helper` (syslog, or the journal).

**Who may run it.** `/etc/sudoers.d/conclave`, root 0440: `conclave ALL=(root) NOPASSWD: /usr/local/libexec/conclave-root-helper browser-deps`, one entry per action. sudo matches the arguments too, so `sudo ... browser-deps x` or `sudo ... other` is refused by sudo before the helper starts; the helper's own check is the second fence. The rule is written under a name sudo ignores (`.conclave.new`, it has a dot), checked with `visudo -cf`, then the helper is written, and only then is the rule renamed into place; `visudo -c` checks the whole configuration with it and takes it out again if that fails. A rule visudo refuses changes nothing. The user is the hub's: from its systemd unit (`User=` of `conclave-hub`, or any `conclave*` unit whose ExecStart is `conclave serve`, never `conclave-update`), else the owner of a running `conclave serve`, else the `conclave` user; `--user` overrides. A name sudoers would read as more than one user (`ALL`, `Defaults`, an upper case alias, `%group`, anything with a comma, colon or space) is refused. A hub that runs as root gets the helper and no rule. Every folder on the way (`/usr`, `/usr/local`, `/usr/local/libexec`, `/etc/sudoers.d`) must be root's and not writable by others, or by a group the hub's user is in, since whoever can write there could swap the file. No password is stored anywhere: NOPASSWD is for this one file and these words.

**Why that is safe.** The hub's user, and so any agent or program running as it, can make root do exactly one thing: install a fixed list of Debian packages from the machine's configured apt sources, at most once per run, and that changes nothing when they are there. It cannot name a package, a path, an option or a source; apt's own configuration and keys are root's. The file it runs is root's, in folders that are root's. The cost: an agent can trigger an `apt-get update` and up to about 150 MB of packages, which the owner agreed to when installing the helper, and which the audit log and the system log record. Adding a job means a new action in `root-helper.ts`, a new release, and the owner running `system-helper install` again: the helper on disk never grows on its own. `system-helper status` shows the file, its version and actions, the rule, sudo, the hub's user and whether sudo lets it run, and says when the installed helper is older than this Conclave's.

**The hub's side.** `system/host.ts` reads the file (root's, not group or world writable, its `# actions:` line has the action), sees the drop-in is there (it cannot read it), and asks `sudo -n -l <helper> browser-deps`, which needs no password and runs nothing; the answer is kept until either file changes. It also reads `NoNewPrivs` from `/proc/self/status`: a service with `NoNewPrivileges=yes` cannot use sudo, and the page says so. Only when all of that holds does Settings, Browser offer **Install system libraries**, whose one step is `sudo /usr/local/libexec/conclave-root-helper browser-deps`, run like Install on the hub's steps: the owner only, shown and confirmed (a different line is refused with 409 and the fresh one), audited before and after, through the hub's machine as its user, with 20 minutes for apt. Then `ldd` runs again and the page says Ready, or what is still missing.

**Where it runs, in words.** The same file finds where the hub runs, to word every "run this as root": `systemd-detect-virt -c` (else `/run/systemd/container`, else pid 1's environment) for LXC, Docker, Podman and the rest; `--vm` for a VM; otherwise a machine of its own. For LXC the page says "inside the hub's container, not on the Proxmox host", with `pct exec <CTID> -- <command>` for the host shell and the CT's Console in the web UI. The CT id is not visible inside a container, but Proxmox names its disk after it, and the root mount in `/proc/self/mountinfo` shows that name (`pve-vm--100--disk--0` on LVM-thin, `subvol-100-disk-0` on ZFS and btrfs); without it the page shows `<CTID>` and says it is the container's number. Docker gets the rebuild with `--build-arg BROWSER=1`. The install command itself is the one that works there: `conclave system-helper install` with setup.sh's command, which now keeps root for `system-helper` (it runs everything else as the conclave user); `/opt/conclave/bin/conclave system-helper install` where that command is older; the binary's full path for an install-script hub, whose `~/.local/bin` is not on root's PATH.

**New installs.** `conclave-lxc.sh` asks on the host's terminal (the root helper, default yes; the browser's libraries, default no, about 150 MB) and passes the answers to `setup.sh`, which asks the same when run by itself and keeps the answers for later runs. With yes it runs `conclave system-helper install --user conclave`, and replaces the helper with the new version on every later run; the libraries come from `conclave system-helper run browser-deps`, the same script run once as root without installing it. `install.sh` run as root ends with the one-line tip.

**Removing it.** `conclave system-helper remove`, as root, deletes the rule first (sudo stops at once) and then the helper. sudo and the packages stay. By hand: `rm /etc/sudoers.d/conclave /usr/local/libexec/conclave-root-helper`.

Where it can fail: `apt-get update` needs the network and working sources; a broken source fails the run, with apt's output in the result. A machine with another package manager gets the refusal and the page's own command. An `apt` held by another run waits up to 5 minutes for the lock. The hub cannot stop a run that went past its 20 minutes: sudo's child is root's.

## 46. Thinking after a summary

**Why.** Anthropic's newer conversation check (on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1, enforced by default for accounts created on or after 2026-08-31) ties each thinking block's signature to everything before it: the system prompt, the tools and every earlier message. Ordinary auto compaction and `/compact` keep the newest turns word for word after a summary Conclave wrote, so the thinking in those turns was produced with the full history in front of it and fails the check once the summary replaces that history. On an enforced account that is a 400 on every later request. The switch's short handover (section 44) already left that thinking out; the ordinary compaction did not.

**What changed** (`core/session/transcript.ts` `thinkingAfterSummary`). After any summary (auto, manual, a switch's handover, or one written without the model), the turns stored before the summary go without `thinking` and `redacted_thinking` blocks; their text and tool calls stay. Turns written after the summary keep their thinking, since they were produced with the summary in front of them. The rule reads only the stored summary, so every later request and a restart send the same bytes, and what is removed is a leading run of thinking blocks, which the check allows. The stored messages keep their thinking. Older summaries that carry `dropTailThinking` read the same; the flag is no longer written. This matches the guidance in the Claude API docs (preserved thinking, `shared/model-migration.md` "Breaking change 3"): keep-tail compaction has no append-only form without the on-demand compaction beta, and the recommended client-side fix is to strip thinking from the retained turns as a deterministic, recorded strip. Conclave compacts synchronously, between tool rounds, so no assistant turn waiting on its tool result loses its thinking.

**`drop_block` is not sent.** `thinking.block_binding.prefix_mismatch_behavior: "drop_block"` would make the API drop a mismatched block instead of failing. It is a beta (`thinking-binding-controls-2026-08-01`): without the header the field is a 400, partner routes may not forward the header (CLIProxyAPI, Z.ai's Anthropic endpoint, Bedrock), Sonnet 5.5's `between_tools` and Haiku 5.5's `disabled` thinking refuse it, and any value opts every request into enforcement, so an older account that passes today would start losing reasoning. The docs call it a stopgap with an output token cost, not a fix. With the strip in place there is nothing for it to catch at a compaction, so it stays off.

Where it can fail: other edits still break the check, such as a tool list that changes mid-session (an MCP server that connects later) or old tool output cleared by Conclave's own clearing batches; those are the next ones to measure. Losing the kept turns' reasoning once per compaction costs a little quality and some output tokens on the next reply.

## 47. Refusal fallback ("safety priority")

**Why.** The owner keeps several accounts and models (two Claude plans, GLM, a ChatGPT plan) and wants a refused turn to go to the next one they trust, in their order, without retyping it. They call it "safety priority"; the UI calls it Refusal fallback.

**Marked plans first** (`refusal: true` on an account in `models.accounts`; Settings > Models > Accounts, "Use when a model refuses"). Building the list was too much work for the common case: the owner's personal Claude plan is verified for the cyber program and refuses less, and he wants a refusal to go there, nothing more. So any signed in plan or API key can carry the switch, with the hint "A refused reply is tried again here first, same model." After a refusal the walk first runs the same model, with the same messages, on each marked account of that model's vendor, in the owner's account order for the model (`AccountsService.refusalAccounts`), skipping the one that refused and any that is off, not signed in, paused, at a limit or resting, or that does not offer the model. A plan runs by its prefix (`cliproxy/<prefix>/<model>`), a key on its own provider, pinned like a list entry. Then the list runs as before, from the entry after the one that matches what refused first. A mark alone is enough: with no list the plan has only the marked accounts. "Try the next model on its own" still decides: off, the refusal stands with the button, and the button takes the same order. A refused reply stores where it refused (`meta.refusalStep`: `tagged` or the list index), so the button on a reply a marked plan or an entry refused goes on after that step instead of starting over.

A marked plan must be reachable alone, so it needs a short name. When the owner marks a plan that has none, the hub gives it the suggested one itself (`suggestPrefixes`, then `CliproxyManager.setPrefix`, in `PATCH /api/accounts/:id` with `{ refusal: true }`): the owner never names it. Without CLIProxyAPI's management key the hub cannot write a prefix, so a plan's switch is off with the note short names use, and the route answers 409; an API key needs neither. The Refusal fallback page starts with one line naming the marked ones ("Tried first: personal-claude on Claude.", a plan by its short name, a key by its name) with a link to Accounts, or, with none, how to mark one.

**The list** (`models.refusalFallback` in config.json; Settings > Models > Refusal fallback). `entries` is an ordered list of `{ model, account? }`, where `account` is an id from Settings > Models > Accounts. `enabled` (default false) walks the list on its own; `stay` (default false) keeps the model that answered for the next turns. An agent can replace the list in its frontmatter, or turn it off (docs/EXTENSIONS.md, Agent tiers). Off and empty by default. A member's sessions never walk it: the list names the owner's accounts.

**What counts as a refusal.** Only a stop reason the provider signals (section 7): Anthropic's `refusal`, OpenAI's refusal content or `content_filter`, Gemini's SAFETY, PROHIBITED_CONTENT, BLOCKLIST, SPII, RECITATION and their image kinds, LANGUAGE, or a blocked prompt, and Z.ai's `sensitive` (documented for its Chat Completions API; the same value is mapped on its Anthropic endpoint). A harness turn counts when its ACP agent ends it with `stopReason: "refusal"`.

**What happens** (`core/session/refusal-fallback.ts`, run by `runner.ts`). The refused reply is dropped (apps get `message.deleted`) and the same request runs on the next entry: the same stored messages, converted for the new model the way a switch converts them (other models' thinking dropped, calls it cannot express flattened to text). Nothing is added: no reminder, no switch note, no rewording, never an instruction meant to get around a model's rules. It only picks the next model and account the owner listed. The walk starts after the entry that matches what refused (model and account), or at the top when none does, and skips entries it already tried and ones that cannot be called (provider off or without a key, account paused). It goes on until one answers or the list ends. An entry with an account is pinned to it (`StreamPin`): an API key's own provider, or a signed in plan by its CLIProxyAPI prefix (`cliproxy/neu/claude-opus-5-5`); the owner's account order does not move it, and a limit or refused sign in is not passed to another account. A plan without a prefix cannot be pinned: CLIProxyAPI picks among the plans that have the model, and Settings says so under the row and points to the plan's short name in Settings > Models > Accounts. An entry that cannot answer (a limit, an error) gets its own notice and the walk moves on.

Each step is one notice, written as it starts and finished when the entry answers: "Opus 5.5 (neu) declined. Trying Opus 5.5 (personal)." becomes "Opus 5.5 (neu) declined. Answered by Opus 5.5 (personal)." The usage rows name the account that answered, and so does the turn row. If every entry refuses, the last refusal stands with one notice: "GLM-5.3 declined. No model is left in Refusal fallback." The answering model keeps the rest of the turn; the next turn goes back to the session's model unless `stay` is on.

**Try the next model** (`POST /api/sessions/:id/next-model`, optional `{ messageId }`, answer `{ model, label }`; `engine.tryNextModel`). A refusal notice carries `meta.type: "refusal"` and `canTryNext` when a marked account or the list has a step after the model that refused; the web shows a button under it while nothing runs. Pressing it drops the refused reply and its "Not run" results and runs the turn again from the entry after it, with no new user message, whether or not `enabled` is on. Android can call the same route; its button is left to the reply actions work there.

**Harness turns.** Claude Code and Codex over ACP are covered only where the refusal is visible to the hub: the ACP agent's `stopReason: "refusal"`. The refused harness reply goes when it only spoke and stays when it ran tools (those changes happened), and the turn continues in the hub's own loop on the next entry, as after a switch from the harness. A harness that answers a refusal as a normal end of turn is not caught, since Conclave does not read reply text. The harness's own session does not learn the fallback's answer; its next turn resumes it as after any switch away and back.

Where it can fail: a plan without a short name (prefix) may answer from the same plan that refused. A fallback model reads the whole chat again with no cache, so a big chat's step costs what a switch costs (section 44). Some refusals come with nothing written, others mid-reply; both are dropped the same way.

## 48. Model lists from the account

**Why.** The owner's ChatGPT account offers a model ("Daybreak") that Conclave's lists did not show: the Codex harness listed only `default`, and the CLIProxyAPI provider listed only its shared `/v1/models`. New models should show without a Conclave release.

**Harnesses** (`core/acp/adapter.ts` `harnessModels`). An ACP agent reports its models in its model option (a select of category `model`) or the older `models.availableModels`. Every turn emits them (`models` harness event); the engine keeps the last list per harness in kv (`harness.models`) and the registry lists them after the configured `models` (the static fallback, `default` when empty), by the harness's own name when no catalog knows the id. `codex/daybreak` resolves like any harness ref and the adapter picks it through the same option.

**CLIProxyAPI.** Each signed in account's list (`credentials/models`, read on sign-in, every 10 minutes and on Refresh) joins `providers.cliproxy.models` after `/v1/models`, with the account's prefix when it has one. In 8.0.32 (checked against its binary and source) that list is CLIProxyAPI's catalog for the account's type, and for a ChatGPT plan for its plan (`codex-free`, `codex-plus`, `codex-pro`, `codex-team` in its models.json, which it reads from router-for-me/models every 3 hours); it never has more than `/v1/models`. Once a plan has a prefix it names each model twice (`gpt-6-astra` and `work/gpt-6-astra`): the hub shows each once, and that is also how it learns the prefix, since the credentials list never carries it (`management.ts` `splitPrefixed`).

A ChatGPT plan's own list is ChatGPT's Codex models address, as the Codex app reads it (`GET https://chatgpt.com/backend-api/codex/models?client_version=0.160.0`, the `codex-models` entry of the api-call allowlist, with the `$TOKEN$` placeholder and the account id; models marked `hide` are left out). CLIProxyAPI refuses any model its catalog lacks before it asks ChatGPT ("unknown provider for model daybreak", 400 `model_not_found`), and an alias only renames a model the catalog has. What lets one through is the catalog itself: `models.catalog` in its config takes a file path, and then it reads nothing else. So for the CLIProxyAPI the hub runs (builtin) the hub reads the same official catalog, adds each model a plan's own list has and the catalog lacks to that plan's section (with the capabilities of the section's first model), writes it as `<home>/cliproxy/catalog-<hash>.json` and points CLIProxyAPI at it (`PUT /v8/management/config/models/catalog`). CLIProxyAPI registers the models again at once; the hub reads its lists again, so daybreak shows on that plan, in the picker and in Settings, Subscriptions, and routes. With nothing to add the hub sends `DELETE` and CLIProxyAPI goes back to its own sources; the official part is read again every 3 hours, and a failed read keeps the last one and waits 10 minutes (`cliproxy/catalog.ts`). An external CLIProxyAPI serves other tools: the hub leaves its catalog alone, and a model only a plan's own list has stays out of the picker there.

**Refresh models** (`POST /api/models/refresh`, owner only; Settings > Models > Subscriptions, Models, Refresh models). The hub reads `/v1/models` and every account's list again, starts each harness that is on in the hub's home folder to read its model option (`AcpAdapter.listModels`, 60 seconds at most each), drops the cached listings and answers the new model list with what could not be asked. What could not be asked keeps its last list, then its configured one.

Where it can fail: the Codex models address leaves out models that need a newer Codex client than the version the hub names, so the constant (`CODEX_CLIENT_VERSION`) moves up with CLIProxyAPI's pins; an added model borrows its section's first model's limits until the official catalog has it; a harness started for Refresh may need a sign-in on the hub, and then only says so.

## 49. Saved logins, Forget and Delete profile

**Why.** Settings, Browser listed a profile as one line ("Signed in to facebook.com 2d ago"), had no way to remove a profile made by mistake (the owner's "marketplace") or to sign a profile out of one site, and every login meant the takeover view. The owner asked to give a site's username and password once and have the agent log in by itself when a task needs it. Until now the design said "Your password goes to the site only; the hub does not keep it." That stays true for Sign in to a site; a saved login is the owner's choice to keep one on the hub, encrypted. How to use it: `docs/EXTENSIONS.md`, Browser sites and saved logins. The code is `core/src/browser/logins.ts` (the vault, the origin rule, TOTP), `autofill.ts` (the fill), `manager.ts` (`login`, `forgetSite`, `deleteProfile`), the `browser_login` tool in `tools.ts`, the routes in `server/src/routes-browser.ts`, and `web/src/features/settings/sitesLogins.tsx`.

**The list.** Each profile shows one row per saved login and one per site signed in to without one, merged by host: the account, Signed in and Login saved, last used, and Edit login, Forget, Delete login. `GET /api/browser` carries the logins on each profile with `password: true` (the hub can read it) and `totp: true`, never the values, plus `isDefault` and `usedBy` (watches on the profile and routines whose prompt names it as a profile) for the Delete profile confirm.

**The vault.** The list is a file of its own (`browser-logins.json`, mode 600) with no secret in it; the password and the 2FA key are hub secrets (`browser.login.<id>.password`, `.totp`). Plain hub secrets sit in `secrets.json` as written, mode 600; these two are sealed with AES-256-GCM under a 32 byte key in `browser-logins.key` (mode 600), the secret's name as associated data, so a value moved to another login does not open. The list and the key are marked hub-private, so file tools and shells refuse them like `secrets.json`. Backups leave the list, the key and the sealed values out, keys or not: a backup file holds no usable password, and a restored hub shows each login as one to save again.

**The fill** (`autofill.ts`). The hub, not the model, logs in. It reads the login form from the tab's own document and its open shadow roots with one evaluate: the visible password field (refused when there are two or more: a sign-up or change form), the username field before it (autocomplete, type, then the field's words), a one-time code field (`autocomplete=one-time-code`, or words such as code, OTP, 2FA; split boxes are filled a digit each), the form's button, and where the form sends (the button's `formaction` or the form's `action`, read with `Element.prototype.getAttribute` so a field named "action" cannot stand in). Before each fill it checks the tab's top-level origin against the saved one, and the form's target too. Values are set with `HTMLInputElement.prototype`'s value setter and input and change events in the page; the password is an argument of one evaluate that also checks `location.origin` and the field's type, never of `locator.fill`, which writes its value into Playwright's call log and from there into error messages. The button is clicked (Enter in the field when there is none), the page settles, and a username-first site gets the password on the next page. A code comes from the 2FA key (RFC 6238, SHA1 by default, the `otpauth://` link's digits, period and algorithm when given), or from the owner through a question card, whose free answer is the code; "Sign in myself" or "Stop" leave it to the takeover view. After the submit a password field that still holds the password is cleared, and the tab is listed as signed in when no password field is left.

**Who may.** The tool refuses a member's session ("Saved logins are the hub owner's"), an untrusted one (session/untrusted.ts: a watch run, a mail agent, a webhook run and their subagents), a read-only session and a session on the proxy, whose throwaway browser has no saved logins by design (section 42). Watch runs never get it (`WATCH_NEVER`). The login must be in the session's profile; `browser_profile` lists each profile's saved logins, and WatchCreate counts a saved login when it picks a profile for a site. The assistant names the tool in `optInTools`. It is not read-only, so in the default mode every call asks for approval, unless the owner allows one site (`browser_login(domain:facebook.com)`).

**Forget and Delete profile.** Forget clears a site's cookies (its own domain and its subdomains, and the parent domain cookies it gets) with `context.clearCookies`, and its stored data with `Storage.clearDataForOrigin` for http and https on the host, `www.` and the cookie hosts; a closed profile's browser starts for it and closes again. Delete profile closes the profile's browser, removes its folder (only a folder right under the profiles folder, by a checked name), its `browser.profiles` entry and its saved logins, and points sessions on it back at the default profile. The default profile is refused (400); a profile a session or a sign-in view has open is refused (409) until the owner confirms Close and delete (`?close=1`), which closes the views first.

**Security note.** What it guards against: a page that tells the agent to log in somewhere (origin binding: the hub fills only on the saved site's origin, or its subdomains when the owner ticked them, never an IP's "subdomain"); a hostile frame on the right page (frames are never searched); a form on the saved site that sends elsewhere, from an injection (the target check); the model reading the password (it is never in its context; results replace it, as is, JSON or YAML quoted and URL encoded, with `[saved password]`, for the whole session); a leaked copy of `secrets.json` or a backup (the values are sealed and the key is elsewhere). What it does not: the saved site's own scripts get the password, as with any password manager, so an XSS on that site can read it; page code the agent runs on that site later (`browser_evaluate`) could read a copy the site kept in the page in some encoded form the scrub does not know; a process running as the hub's user can read the key and the secrets together (the private-path guard stops a model's tools, not a script that tries hard); a site that asks for a puzzle or a new device check still needs the owner in Sign in to a site.

Where it can fail: the form finder is heuristic, so a login built from custom elements without real inputs, a password field inside a frame (some single sign-on pages), or a site that wants real key presses to enable its button needs the takeover view; a site that refuses the password keeps the form, and the result says so instead of retrying; Forget clears storage only for the origins it can name, so data a site kept under another subdomain stays until Delete profile; a watch or routine on a deleted profile runs in a new, empty profile of that name until the owner picks another; the TOTP code uses the hub's clock, so a hub whose clock is off by more than a period sends a code the site refuses.

## 50. The window starter

**Why.** A plan's 5 hour window starts with the first request after a reset. When nobody uses the account right after a reset, no window runs until the next request, and that window resets later than it could have. The idea, the timings and the safeguards come from Lamplighter (github.com/PosvdM/cpa-plugin-lamplighter), a plugin that does this inside CLIProxyAPI. Conclave does it from the hub, with what it already reads (`core/src/accounts/starter.ts`).

**Per account, off by default.** `models.accounts[].starter`: `enabled`, `model` (empty: the cheapest the plan offers), `start` and `end` (default 07:00 and 22:30) and `tz` (default the owner's zone from Settings > Assistant, else the hub's). An end before the start runs past midnight. Only signed in plans have it; an API key has no 5 hour window.

**How the reset is learned.** Nothing new polls. For a Claude account the hub already has the `anthropic-ratelimit-unified-5h-*` headers CLIProxyAPI kept from the account's last real response (read every 60 s from `/credentials`) and the OAuth usage page (`five_hour.resets_at`, every 5 to 10 min). For a ChatGPT account, the `x-codex-primary-*` headers and `wham/usage` (`primary_window`). The newest reading wins. The starter adds reads of that one account (`CliproxyManager.readAccount`): 30 s before a reset it acts on (credentials and usage), and after its own request (credentials at 5 and 15 s, then the usage page too at 30, 60 and 75 s). The headers of its own response arrive through the first of those, since CLIProxyAPI keeps them as that credential's signals. Other plans (Google, Grok, Kimi) have no usage read in Conclave, so their starter waits for a reading and says so.

**The request.** 3 s after the reset, inside the hours, one call on the gateway provider: "Reply with exactly OK and nothing else.", no tools, no system prompt, thinking off, at most 4 output tokens. The model is the newest Haiku for Claude (then Sonnet), the newest Luna for ChatGPT (then nano, mini, other GPT), Flash for Gemini, from the account's own model list, or the owner's choice. A reset outside the hours waits for the next start. It goes straight to the provider (`sendStarter`), not through the session path, so there is no account fallback and no retry inside the call. Its usage row has `source` and `purpose` `starter` and names the account, so the Usage page shows it as Window starter, apart from chats.

**Pinned to the account.** CLIProxyAPI has no request header that picks a credential; Lamplighter uses the plugin host's pinned execution, which is not reachable from outside. So an account with a prefix is asked as `prefix/model`, which only credentials with that prefix serve, and the prefix must be its own. An account without one is asked by the bare id only when no other credential CLIProxyAPI serves offers that model (a prefixed credential serves bare ids too). Otherwise the starter says "Cannot reach this account alone. Give it a short name in Settings > Models > Accounts." and sends nothing.

**Success** counts only once the 5 hour window shows a fixed reset in the future, read after the request. A reading from headers is fixed, since a request starts the window. The usage page can show an unstarted window as a reset about 5 hours ahead that moves with every reading, so a usage reading counts only when two readings agree on the reset, and two readings whose reset moved by the time between them mark the window as not running (Lamplighter's rule and tolerances).

**Safeguards** (`decide` and `failed`, kept per account in kv `accounts.starter`, so they hold across restarts):

- A sign-in failure, a 429, a model the plan refuses (after trying the next candidate once; the refused one rests a day) or a window that does not start stop the account until the next start of its hours, with one notice: "Window starter stopped: Account 1", "429. It tries again tomorrow at 07:00."
- Network, server and busy errors try again after 5 and then 15 minutes; the third stops it for the day.
- A short CLIProxyAPI cooldown (`model_cooldown` with `reset_seconds`, up to 10 min) is waited out once without counting; a credential cooldown the hub reads also moves the request past it.
- A used up weekly window that limits the model pauses it until that resets; then the account is read once before the next request.
- A plan whose windows show no 5 hour window never gets a request. One with no reading yet waits.
- No token or credential passes through the starter; errors are kept as a few words, never a response body.

**Scheduling.** One durable job per account (`accounts.starter`, dedupe key `starter:<id>`), planned again whenever the accounts change and after each run. A restart picks up a request that was being confirmed.

**Where it shows.** Settings > Models > Accounts: under each plan, a Window starter switch ("Start the next 5-hour window automatically"), its line ("Next start 14:03. Started 09:00.", "Stopped until tomorrow: 429.", "Paused: weekly limit used up until Tue 10:00.") and Change for the model, the hours and the zone. The first time the owner turns one on, a note says: "Some providers limit automated use of subscription accounts. This sends one tiny request per window. Use at your own risk." Android has no accounts screen; its Usage limit card shows the same line, read only, from the limit state's `starter`.

Where it can fail: it starts windows only for plans CLIProxyAPI serves and Conclave reads (Claude, ChatGPT). Several accounts of one vendor need short names (prefixes) to be reached one by one. When the usage page is in its 429 backoff and the headers carry no 5 hour reset, a request that did start a window can read as "No window started" and stop the account for the day. A provider may treat automated requests on a subscription as against its terms, which is the owner's call.

## 51. Platform awareness

**Why.** The owner asked for every chat, assistant and code agent to know its own platform: what Conclave is for, what it can do, and what an agent can and cannot do here. Agents knew their tools but not their platform: which mode they were in, what the other modes do, where a setting lives in the app, or what is set up on this hub. The chat in section 43 that told the owner to press Continue as a session, instead of handing the job on, is the kind of answer this is meant to stop. The code is `core/src/platform` (`card.ts` renders, `facts.ts` reads the live state, `docs.ts` indexes the docs) and `core/src/tools/conclave-help.ts`.

**The card.** Every primary session (depth 0, not a subagent, a delegated job or a workflow step) gets two system blocks. The card follows the agent's role: what Conclave is, the hub's name, version and where it runs ("madx, Conclave 0.4.14, on Linux x64 in an LXC container (CT <ctid>)"), the three modes and how work moves between them (Delegate, Task, Workflow), where things are in the app (Memory, Routines, Inbox, Usage, Extensions, Settings > Models, Settings > Browser, GitHub and the rest), what an agent cannot do here (settings, keys, sign-ins, pairing, installs), and the rule for "can you do X": answer from the card and the tools, use the feature (Delegate, Task, Workflow, the browser, a routine) rather than send the owner to do it by hand, within permissions, and call ConclaveHelp before explaining Conclave itself. The live block is the last block of the system prompt: this session's mode and agent, its tools by group, what it lacks and where Delegate sends it ("Delegate hands those to Code (files and the shell, workflows) or the Assistant (the browser, routines, watches)"), the MCP servers it has (loaded or behind ToolSearch), the devices online and offline, whether the hub's browser is ready and on which engine, and the default model, the model accounts and the harness engines that are on. Both come from live state, not text written into a prompt. Together they stay under 700 tokens (650 on a hub with eleven devices, ten MCP servers and eight accounts; about 600 on a usual one), which a test pins.

**Who gets what.** A subagent, a delegated job and a workflow step get two lines: Conclave and the hub, and that the session that started them talks to the owner (plus ConclaveHelp when they have it). So does a session that reads untrusted input (a watch run, the email agent, a webhook run): text from outside should not get a map of the owner's devices and accounts to aim at. A member's session gets the card without the hub's settings, accounts or browser, and only their own devices.

**Cache.** The system prompt is a snapshot (section 5). The card's parts are read with the instruction files once per user turn and compared, so the prompt changes only when the live state does: a device comes or goes, an MCP server connects, the browser is installed, an account is added. Nothing in it reads the clock or counts anything, and lists are sorted, so a turn with no change sends the same bytes (a test runs two turns and compares them). A device that flaps costs one cache write on the next turn, the same one Delegate's device list already costs. The card sits after the role and the live block last, so a change rewrites the end of the system prompt only.

**ConclaveHelp.** A read-only tool that searches the docs that ship with the hub: INSTALL, EXTENSIONS, MEMORY, ASSISTANT, WORKFLOWS, this log and the round specs in `docs/design` (the motion, brand and component specs are left out). Each file is a text import from `docs/`, so `bun build --compile` embeds it in the binary and a release hub needs nothing on disk; run from source it reads `docs/`, which the Docker image now copies. The files split at their `##` and `###` headings (headings inside code blocks are not headings), and BM25 over stemmed words ranks the sections, a heading's words counting three times and the guides a little above the log. A long question must share at least a third of its words with a section. A hit returns the section's path, its id and the paragraphs that match best (about 1,600 characters, or the whole section when it is short); `section` with an id reads one section whole. No match returns no sections and says so. "How do I set up a second Claude account" lands on INSTALL.md, Accounts and their order, whose "A second Claude account" paragraph is the answer. The chat agent names it in its tools; agents without a tools list have it as a built-in.

**Switches.** `agents.platformCard` in config.json (default true) turns the card off for every agent. An agent's frontmatter `platformCard: false` turns it off for that agent; the agent editor has it as Platform awareness under Instructions, and a built-in agent is changed through a copy, as for every other field. ConclaveHelp stays either way; take it away with the agent's tools.

Where it can fail: the card names pages and features as of this release, so a page that moves needs the card's text moved too (ConclaveHelp reads the docs, so it follows them). The live block says what is set up, not whether it works right now: an account at its limit or an MCP server that fails mid-turn still shows. The device list follows the account, so a hub with many computers lists eight online and counts the rest. Search ranks words, not meaning, so a question in words the docs never use ("laptop" for a paired computer) finds weaker matches; the agent can search again with the feature's name. The docs are English only.

## 52. Usage and costs: what was billed, and what a plan's use was worth

**Why.** Calls through a signed in plan (the hub's CLIProxyAPI accounts for Claude Max, ChatGPT and the rest, providers with `subscription` set) bill nothing per token, so their usage rows cost $0 and the Usage page said "plan". The owner wanted to see what that use would have cost on an API key. The tokens and the model's API prices are both known, so the hub can say it.

**Two numbers per row.** `costUsd` stays what was billed: $0 for a plan, the API price for a key, a price the provider reported (OpenRouter) when there is one. Beside it each usage row keeps `apiValueUsd` (column `api_value_usd`): the same tokens priced with the model's API rates from the catalog (`computeCost`: input, output, cache read, cache write, and the 1 hour write at its own rate), ignoring the plan's zero prices (`usage/value.ts`). For a key, and for any call no plan served, the value is what was billed. A plan call is one whose provider has `subscription` and no price override for the model (an override is the price the owner pays), or whose account is a signed in plan; a second account's model (`neu/claude-opus-5-5`) is priced as the model. The value is written when the row is recorded, so a later catalog change does not move it.

**Rows from before.** Rows written before the column have none. Reads price them from today's catalog with the same rule and say so: a summary bucket carries `estimatedUsd` (the part that was priced on read), a recent row carries `apiValueEstimated`. Nothing is written back. Gateway and OTLP rows, which go straight to the table, are priced the same way on read.

**Where it shows.** `GET /api/usage` buckets (totals, per day, model, source, purpose and account) carry `apiValueUsd`, and the summary carries `savedUsd`: the API value of the range less what was billed, which only plans make. On the Usage page the tables get an "At API prices" column next to "Billed" when a plan served some of their rows ("same" for a key), the day readout says what the day was worth, recent requests say it per call (marked est. for old rows), and a line at the top says "Your plans saved you about $Z this month" with what the calls were worth and what was billed under it. It always reads this calendar month, whatever range is picked. Limits and windows are as before. Session stats keep `apiValueUsd` beside `costUsd` (a session from before starts from its bill plus what its usage rows say plans saved), and the session's cost places (the context card, `/cost`, the conversation sheet, the context ring, the chat menu) add "worth $Y at API prices" when a plan served it. The status line under the composer says only "plan" there and leaves the worth to the ring beside it; workflow agent rows and subagent lines say "plan" with no worth, since their rows carry no API value. The CLI's `/cost` and `/usage` do the same, and `/usage` prints the saved line. The Android Usage screen shows the saved line, Billed and At API prices, a By account list, and the worth per model and per day.

Where it can fail: a model the catalog does not know is worth $0 at API prices, so a plan's call on it shows no value; harness rows (Claude Code over ACP) use whatever cost the harness reported, and their model names (`opus`) are priced by the catalog's nearest match.

## 53. Members' own plans

**Why.** Subscriptions and Accounts were the owner's alone, so a person on the hub could use a Claude or ChatGPT plan only through the owner's grant. Now a member can sign in plans of their own, and only their chats use them. The design, the routes and the limits are in `docs/design/ACCOUNTS.md` section 12.

**How.** The hub runs one CLIProxyAPI per member, in `<home>/accounts/<id>/cliproxy/`, on `127.0.0.1`, with its keys in the `hub` part of the member's `secrets.json`. It starts on the first sign-in and at hub start, and it goes with the member, and with the last plan unless another sign-in is still in progress. A member can retry it when it stopped with an error. A member's `cliproxy` call goes to their own plan when it lists the model, else to the hub's only if the owner granted `cliproxy`. A call on their plan never moves to the hub's mid-call. A member never sees the program, its version, its path or how the hub reaches it. Another person's plan id gets 404. The owner's calls never reach a member's plan. The owner sees only a count (`ownPlans`).

**Files.** `packages/server/src/cliproxy/member.ts` (`MemberPlansManager`, `plansFor`), `packages/core/src/people/plans.ts` and `access.ts` (routing), `people/secrets.ts` (`hubValue`), `people/events.ts` (`PLAN_EVENTS`), `server/src/routes-subscriptions.ts`, `routes-accounts.ts` and `route-policy.ts`, `core/src/machine/private.ts`, `web/src/features/settings/member-plans.tsx`.

Where it can fail: see ACCOUNTS.md section 12.

## 54. Tools: Read opens Office files, and Docling when it is there

**Why.** Read refused docx, xlsx and pptx as binary, so an agent fell back to Bash and whatever converter the device had, often none. PDFs went through `pdftotext -layout`, which loses table structure and has nothing for a scanned page except attaching the PDF.

**How.** OOXML and OpenDocument files are zip archives of XML. Read loads the bytes through the session's Machine (so a file on a paired device works the same), unzips them in-process with `node:zlib` (stored and deflated entries, no ZIP64, each XML part capped at 32 MB) and walks the XML with linkedom, already a core dependency. docx gives headings (from the style names, so localized style ids still work), paragraphs, bullet lists and tables as Markdown tables; xlsx gives each sheet as a table, shared and inline strings and booleans, capped at 500 rows with a note; pptx gives one section per slide with its title, text, tables and notes, without slide numbers; odt, ods and odp go through one walker. The Markdown is numbered and paged like a text file (offset, limit, the output budget). Files over 64 MB are refused. The result carries no read mark, so Write never takes the zip for a text file it read. Legacy .doc, .xls and .ppt stay refused, with the `soffice --headless --convert-to` line.

With `documents.docling.url` set, Read posts scanned PDFs (no text from pdftotext), PDFs whose layout text has a run of three lines in three or more columns, and docx, xlsx and pptx files to docling-serve's `POST /v1/convert/file` (`to_formats=md`, `page_range` from `pages`) and returns its Markdown. Any error, a non-success status or an empty result falls back to the built-in path, and the result says Docling failed and why. The config is the owner's, so a member's session never sends files to it. `docs/research/DOCLING-MADX.md` is the deployment preview for Madx.

**Files.** `packages/core/src/tools/read.ts`, `tools/office.ts`, `tools/docling.ts`, `config/schema.ts` (`documents`), `test/tools/read-office.test.ts`.

Where it can fail: numbered lists come out as bullets, dates in sheets show as Excel serial numbers and formulas as their last saved values; merged cells and nested tables are flattened; a sheet past 500 rows needs a CSV export through Bash; ZIP64 archives (over 4 GB, or more than 65535 entries) and encrypted files are refused; the table check on PDF text is a heuristic, so a two-column paper with ragged gaps can go to Docling and a sparse table can stay with pdftotext; Docling on CPU can take minutes on a long scan, and Read waits up to `timeoutMs` (120 s by default) before it falls back; Conclave sends no `X-Api-Key`, so the server must be reachable only from the hub.
## 55. Pause and Resume

**Why.** Only Stop existed, and Stop throws away the turn. The owner wants to hold any running work and pick it up later, also after a hub restart.

**How.** `engine.pauseSession` asks the session's runner to pause. The tool call in progress finishes; the agent loop checks the flag at the top of each step and stops before the next model call. A call still running after `PAUSE_GRACE_MS` (30 s) is cut as Stop cuts it and gets an interrupted result. The session's status becomes `paused` and `meta.pausedTurn` marks a cut turn. Status is stored, so boot neither resets it nor marks a paused Task child lost, and the update busy check skips it. While paused the queue holds new messages. `resumeSession` clears it: a top-level session runs an inference-only queue item (the transcript already holds the results), a Task or Delegate child goes on through `resumePausedSubagent` and reports to its parent as a background task, and a workflow agent wakes its call. A paused workflow run pauses its running agents, and agents made while paused stop at their first step. Shutdown keeps a paused run `paused`; boot does not auto-resume it, and Resume replays it from the journal.

**Files.** `core/src/session/runner.ts` (`pause`, `parkPaused`, `unpause`, `resumePaused`), `engine/engine.ts`, `engine/subagent.ts`, `engine/background.ts`, `tools/background-tasks.ts`, `workflows/run.ts`, `agents.ts`, `service.ts`, `server/src/routes.ts`, `route-policy.ts`, web `ContextPanel.tsx`, `RunningTasks.tsx`, `ChatView.tsx`, `WorkflowCard.tsx`, Android `ui/conversation/Tasks.kt`.

Where it can fail: a harness (ACP) turn cannot stop between its own steps, so Pause waits the 30 s and cuts it; a session waiting for a usage limit cannot be paused (Stop it); a workflow agent paused across a restart is let go and its call runs again from the start.

## 56. Move to hub and Move back

**Why.** A move (section on folders across devices) finds the project's folder on the other device or clones it; it never copies files. The owner wants a session to leave a laptop and keep working on the hub with everything the laptop had: node_modules, build output, `.env`, uncommitted work. The hub gets a big drive for it.

**How.** `MoveInput.copy` with device `local` (the session menu's "Move to hub (copy folder)", `/move hub --copy`, the Android sheet). The device measures the project folder (`du -sk`, `find | wc -l`); the hub refuses when `projects.hubRoot` has less free than the size plus 5% and 64 MB. The device runs `tar -c` through `Machine.spawn`, whose stdout already streams (`proc.stdout` frames, bounded on the daemon), and the hub pipes it into `tar -xpv` in `<hubRoot>/<device>/<folder>` (`-2`, `-3` when taken), so symlinks, modes and mtimes stay and nothing is held in memory. No new daemon RPC. `hubcopy.progress` events carry bytes and files twice a second; DELETE `/api/sessions/:id/hub-copy` cancels and the partial copy is removed, as on any failure. Then the hub writes a manifest (path, size, mtime, sha256 under 50 MB, symlink target) to `<hubRoot>/.conclave/manifests/`, moves the session to the copy through the normal move (remembered, so the path pair is learned) and keeps `meta.hubCopy` (device, folder, copy time, manifest file). Move back walks the copy against the manifest (added, changed, deleted; a file only touched is unchanged), lists the device's files with `find` and `stat` (GNU or BSD) and marks a file that changed on both sides a conflict, with text diffs for the first 40 files. Copy back all, or without conflicts, sends only those files with `tar --null -T -`; deletions happen only when the owner ticks "Also delete files removed on the hub". Then the session moves back and the record goes. The hub copy stays.

**Files.** `packages/core/src/projects/hubcopy.ts`, `projects/service.ts` (`move`, `withMoveLock`, `checkMovable`), `client/projects.ts`, `engine/commands.ts`, `server/src/routes-projects.ts`, `route-policy.ts`, `web/src/features/chat/HubCopy.tsx`, `web/src/features/devices/Folders.tsx`, Android `ChatScreen.kt`.

Where it can fail: a Windows device has no `du`, `find` or `stat`, so it is refused; the hub's stdin into a device has no backpressure, so Move back of a huge change set buffers on the hub; the device listing reads one line per file, so a name with a line break is misread; tar exits 1 when a file changed while it was read, which is a warning, not a failure; a file changed on the device during the copy is copied as tar read it; Move to hub and Move back are the owner's only.
